# MCP 主数据能力评估（有日期的证据快照）

评估日期：2026-09-12；独立规范复核日期：2026-09-21。本文是事实源评估，不是长期业务规则。事实源、授权范围或证据可用性变化后必须重新评估。

## 结论

Starry KOL MCP 可以提供 KOL 业务域事实，但不能替代企业组织主数据源。2026-09-12 的只读探测能够证明远端邮箱、负责人和字典数据当时可读；它不能单独证明成员任期、组织授权和当前 PEP 范围。

此前用于确认邮箱负责人的独立绑定清单在本次复核工作区中不可用，因此不能继续以“100%真实”或“已正式授权”描述整条证据链。组织 registry 中已有的 canonical 记录可以继续作为候选授权输入，但依赖缺失绑定证据的正式写操作必须重新核验。只读及不依赖该证据的工作不因此阻塞。

## 使用边界

1. MCP 返回的负责人姓名和邮箱不能单独替代组织授权。只有组织证据、可访问的邮箱负责人证据、registry 绑定及当前 MCP 结果能够共同复核时，才可把它们作为试点 PEP 的正式核验事实。
2. 邮箱品牌字典需要与 `config/brand-registry.yaml` 对账；TB 远端差异本轮按业务负责人指示豁免验收，但运行时仍保留无回退保护。
3. 远程阶段代码存在旧码（例如 `INTEREST_CONFIRMED`），必须映射到平台 canonical code，不能把远程字符串直接当平台主键。
4. 任何阶段写入、发信、解密、导入仍必须经过 Host/PEP/Gateway、确认、幂等和审计。

## 决策

Starry MCP 可作为 KOL 域事实源接入；组织 registry 可作为试点授权候选源。两者必须通过稳定外部引用、版本和时间关联。正式 PEP 授权需要组织证据、业务绑定证据和远端事实三类证据同时可复核；缺任一类时，不得把历史评估结果当作当前授权。KOL Agent 仍需通过 Agent 发布、品牌连接器、全量测试和真实阶段写入等其它生产门禁后才能升级状态。
