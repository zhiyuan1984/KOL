## 进程恢复

此前重建运行时对象的测试不能证明进程恢复。本轮在独立 PostgreSQL 库中装配测试 Agent、组织绑定、凭据与工具策略；远端是仅监听本机的 MCP 协议夹具。`backend/tests/crawl-process-recovery.test.ts` 使用正式 dispatcher、监控及结果处理器，子进程入口为 `backend/tests/fixtures/crawl-recovery-worker.ts`，拒绝打开非 `lingong_t_` 测试库。

请求到达远端、回复尚未交付时，实际终止子进程；确认退出并等真实租约到期后，执行仓库恢复，再启动全新进程。

| 用例 | 可观察结论 |
|---|---|
| 读取候选时 Worker 终止 | 同一个持久作业恢复；仅对同一 task_id 再次只读；保存完整候选；重复投递不再执行 |
| 启动请求到达远端、回执尚未持久化时 Worker 终止 | 高风险作业 uncertain；重投递不启动；缺回执监控将采集标为待核实，保留实例互斥；无全局候选读取 |
| 监控在途采集时 Worker 终止 | 同一作业恢复并继续监控原 task_id；采集成功终态事务性产生1项结果作业；新进程读取后保存 ready 候选，无新启动 |

后端3项实际子进程恢复测试在 Windows 通过。首轮 Linux 发布门禁发现测试时钟差异：模拟未来恢复也把 next_attempt_at 排到未来，Linux 新进程启动较快，因此尚不能领取；生产未部署。测试已改为等待真实租约到期，需重新验证跨平台结果。缺回执用例直接驱动既定第12轮监控，不是对真实等待一分钟的计时验收。本轮证明本平台的进程边界，不能替代外部 MediaCrawler、真实网络故障、未知 task_id 找回或管理员接管验收。
