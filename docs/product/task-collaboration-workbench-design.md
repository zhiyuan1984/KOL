# 通用任务协作工作台设计说明

版本：v1 · 2026-10-06

本说明定义员工面对“线索智能体”和“AI发现”技能时的体验，同时规定同一套任务工作台如何承载邮件起草、资料分析、报价审核、报告整理等任务。它描述员工可观察的行为和技能必须提供的内容，不替代业务规则、权限规则、阶段规则或工具接口契约。

## 1. 设计目标与边界

员工面对的是一个持续协作的任务，而不是一次模型回答或一次工具调用。线索智能体负责理解目标、组织技能、解释事实和缺口；技能负责声明能力、输入、产出、风险和执行边界；平台负责任务身份、权限、确认、状态、事件顺序、回执和恢复。MCP、API 和连接器不直接暴露给员工。

任务必须能跨会话继续，至少保存：目标、关联对象、输入快照及版本、当前阶段、事件、成果引用、待处理决定和下一步。运行记录属于任务的执行证据，不能代替任务本身。

功能不得伪造完成、联系人、来源、进度或结果。外部写入、导入、删除、解密、发信和正式状态变更必须按照 L3 闸门单独确认并产生回执；“已提出”“已提交”“已执行”“已完成”是不同状态。

## 2. 功能说明

### 2.1 通用任务能力

每项任务由目标、条件、计划、动作、运行、成果和后续决定组成。系统提供以下能力，技能按需启用：

| 能力 | 员工可见结果 |
|---|---|
| 目标理解 | 智能体复述目标、对象范围和完成标准 |
| 条件收集 | 表单、芯片或自然语言补充；保留用户输入与解析结果 |
| 条件核对 | 展示缺项、冲突、不可执行条件和实际可用参数 |
| 计划与方法 | 简短说明将如何处理，以及判断依据是什么 |
| 受控动作 | 草稿、检索、采集、导入、发送等动作独立显示风险和确认要求 |
| 持续运行 | 排队、执行、等待、部分完成、失败、停止、重试和人工接管 |
| 成果 | 结果列表、文档、草稿、比较表或结构化记录，均带来源和时间 |
| 决定与后续 | 待员工决定的选项、影响、下一步和可恢复入口 |

### 2.2 AI发现任务

AI发现使用“线索智能体 + AI发现技能 + 采集运行”的组合。典型顺序为：展示技能和边界，填写或补充发现条件，展示条件快照，核对实际执行参数，等待确认，提交采集请求，持续显示真实运行事件，展示候选及证据缺口。

用户条件与执行参数必须分开。例如地区、粉丝范围、均播和期望人数可能是候选筛选条件；远端平台、模式、关键词和任务标识才是采集调用参数。远端不支持的条件不能被写成远端硬限制，也不能静默丢弃，应标记为“采集后核对”或“无法核验”。方向选择不能覆盖人工关键词。

候选到达后，右栏原位更新真实候选；每项显示来源、采集时间、指标是否可核验、匹配理由和缺口。采集完成只代表候选准备完成，不代表正式入库、建联、发信或阶段推进。后续导入必须是独立动作和独立确认。

### 2.3 其他任务的通用映射

| 任务 | 复用的工作台能力 | 技能特有部分 |
|---|---|---|
| 邮件起草 | 目标理解、输入核对、草稿产物、L2 标记、修改与版本 | 收件人范围、主题、正文、附件和发送前确认 |
| 报价审核 | 条件核对、证据、差异、待决定项 | 报价版本、有效期、审批和金额计算规则 |
| 资料分析 | 资料来源、分析过程、结论、引用和缺口 | 分析维度、指标定义和报告结构 |
| AI发现 | 采集确认、异步运行、候选结果、来源核验 | 平台、关键词、候选筛选和导入门槛 |

## 3. 交互说明

### 3.1 中栏事件顺序

中栏是一条按发生时间和稳定序号排列的任务事件流。推荐顺序是：任务目标与技能上下文 → 输入引导 → 条件卡 → 解析与缺口 → 实际参数或草稿预览 → 确认卡 → 执行回执 → 结果摘要 → 待决定项与下一步。技能不需要的节点不渲染，不能用空卡片占位。

解释性内容可以流式输出；结构化卡片在数据完整后一次呈现。服务端权威事件负责状态和回执，模型文字不能改变任务状态。迟到事件保留其实际发生时间并标注补充记录；重复事件按稳定 ID 去重。

### 3.2 提问框与确认

提问框始终可用，用于补充条件、追问结果和请求下一步。当前唯一主动作放在当前阶段：条件阶段是“核对条件”，确认阶段是“确认并开始”，草稿阶段是“保存草稿”或“申请发送”。确认卡必须展示对象范围、参数快照、风险、确认版本和取消入口；参数变化会使旧确认失效。

员工上滚阅读历史时，新事件不能强行把视口拉回底部。待确认事项在提问框上方提供单一提示入口，点击后定位到完整确认卡；决策完成后折叠为一行回执。停止、重试、导入、发送等动作各自生成独立动作和回执。

### 3.3 右栏成果

右栏只承载当前任务成果与状态，不重复中栏过程。候选、草稿、报告和比较表都支持原位更新、展开详情、来源和版本查看。失败或停止时保留已产生的成果，并显示下一步；空态必须区分“尚无结果”“服务不可用”和“筛选无结果”。

### 3.4 可用信息的优先级

每次输出优先回答：我理解了什么；哪些条件已确定；将怎样处理；依据是什么；现在需要员工决定什么；已经得到什么；还有什么不能确认。内部工具名、MCP 名、技能 ID、未经整理的日志和隐藏推理不直接作为员工信息。

## 4. 技能要求

每个已发布技能必须同时提供机器契约和员工契约。机器契约声明输入 schema、输出 schema、调用资源、权限、风险等级、异步性、幂等性、取消/重试能力和失败状态；员工契约至少声明：

1. 员工标题、用途、适用场景和一句话能力边界；
2. 需要员工提供或确认的输入及默认值含义；
3. 解析后可执行条件、只能事后核验的条件和明确不支持的条件；
4. 过程中的有意义事件、状态和恢复入口；
5. 产物类型、来源要求、时间新鲜度和不确定性表达；
6. 每个动作的 L1/L2/L3 风险、确认文案和回执字段；
7. 失败、部分成功、取消、超时和人工接管方式；
8. 员工可以继续追问或执行的后续动作。

技能说明面向员工的文字不得直接暴露内部字段名。引擎所需的 `mcp`、工具 ID 和内部 schema 保留在机器契约中，由平台映射成“采集”“读取来源”“生成草稿”等可理解的名称。技能不能自行决定像素、布局、权限、业务阶段或确认绕过方式。

## 5. 视觉说明

视觉以 [`docs/DESIGN.md`](../DESIGN.md) 为唯一数值来源。本说明只规定信息关系：左栏保持导航和任务入口，中栏承载有序事件与提问框，右栏承载成果；页面外层不滚动，最多保留左栏、中栏 feed、右栏三个滚动轴。

任务状态始终同时使用文案和非颜色信号。事件节点按信息密度使用列表行或单层卡片；确认、风险和错误需要清楚的标题、原因、范围、动作和回执，不使用大面积营销式空态。技能身份、任务状态、风险等级和知识来源不能只靠色彩区分。

视觉验收必须覆盖：流式追加时底部跟随与历史阅读不互相打断；确认卡可达且不重复；宽度、高度和输入模态分别适配；窄容器单列；长文本可换行；键盘焦点和读屏顺序与视觉顺序一致；减少动效偏好下仍保留状态和新内容提示。

## 6. 宪法审查记录

需求：为线索智能体与 AI发现建立通用任务体验，并适配其他技能。主责角色：平台产品经理、智能体产品经理、UI/UX 专家；技能字段由相应业务专家维护。

结论：符合。依据为 `CONST-02`（平台与业务分离）、`CONST-03`（Agent 组合技能并由平台执行边界）、`CONST-05`（授权与确认）、`CONST-07`（Agent 交互）、`CONST-08`（审查程序）、`CONST-10`（可验证交付），以及 `PRODUCT.md` 的 `PROD-AGENT-03/08/09`、`TECHNOLOGY.md` 的事件和异步作业要求、`DESIGN.md` 的视觉不变量。下一步是把员工契约加入技能发布校验，并将通用事件流与 AI发现现有投影逐步收敛到同一渲染契约。
