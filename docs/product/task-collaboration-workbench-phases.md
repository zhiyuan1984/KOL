## 1. 什么叫“每期闭环”

每个 Phase 在其声明的场景、对象和来源范围内，都必须允许员工完成实际工作，并在失败时知道发生了什么及如何继续。闭环包括：

```text
明确入口与范围 → 保存任务现场 → 获得事实/执行事件 → 人机协作
→ 形成产物 → 核对与受控提交（或明确不执行） → 真实结果与回执 → 可恢复
```

“明确失败并可恢复”是异常闭环，不替代正常路径的成功验证。只证明取消正常、只返回说明文字或只有模拟数据，都不足以宣布一个 Phase 完成。

### 1.1 统一完成定义

| 门禁 | 必须提供的证据 |
|---|---|
| 产品范围 | 本期支持/不支持的场景、对象、来源和动作；入口及完成条件明确 |
| 规则与契约 | 审宪记录、Agent/技能绑定、风险、来源、状态、权限、版本与错误契约 |
| 正常路径 | 从真实入口到当前范围终态的完整记录；产物和回执可重新打开 |
| 异常路径 | 失败、取消、未知结果、冲突、权限变化、断线/重启后的可恢复状态 |
| 客户端 | 导航、返回、条件恢复、键盘/焦点/滚动与 DESIGN 三轴适配 |
| 工程质量 | 本期相关契约、类型、集成、E2E、模型评价、回滚验证；失败分类清楚 |
| 发布验证 | 区分隔离夹具、真实 harness、已授权外部集成；缺一种不得用另一种代替 |
| 运营交接 | 发布开关、监控、处理积压、接管责任与回滚路径 |

`not_started → in_progress → verified → released` 沿用技术基本法登记方式。`verified` 必须写明验证环境和范围；只有真实试点、证据归档与交接完成，才标记 `released`。规则未定、外部环境不可用时记录具体阻塞；不能以缩小验收口径暗中宣布完成。

### 1.2 每期的共同约束

- 仅在本期涉及的代码和契约上实施必要修改，沿用 PostgreSQL、现有持久执行链和统一 Codex harness。
- 新查询、缓存、推送、分析和回执读取均先核验当前权限；不能等最后一期才补租户隔离。
- 每期都包含其范围内的恢复与新鲜度表达，可靠性不是最后单独补建的一期。
- 前端不重写权限、审批或阶段规则；L3 显示准确对象与范围，受控动作携带版本、幂等键和回执。
- 发布开关只控制新增入口、分析触发或提交；关开关不关闭已发生任务的监控、回执读取与接管。
- 外部写入验证使用已明确授权的测试对象及范围；不得为了验证只读上下文向真实 KOL 发信。缺授权时开发与测试继续，真实外部闭环保持待验证。
- 不增加“P0 只搭平台”作为前置大工程。必要的对象映射、持久化和权限在 P1 的用户场景内实现最小集合。

## 3. P1：修复 AI发现，交付第一个完整工作现场

### 3.1 用户故事与闭环

员工从今日任务切换 AI发现，填写平台、地区、方向、关键词及已定义门槛，查看线索智能体整理的采集范围，确认后持续看到进度；结束后查看有真实来源的候选简报。返回来源页、刷新或再次打开任务，都能恢复条件和当前结果。调整条件形成新提案/新运行，不覆盖旧回执。

**关联需求：**TW-01–05、TW-10 最小范围、TW-18–20。

**本期完成边界：**候选与简报可复核，不包含自动入库、建联或发信。必须完成任务级结果读取和基本条件核对；只启动/停止爬虫、只有 task_id、或只显示一段模型建议，不能作为正常闭环交付。

### 3.2 范围和状态

首个真实验收平台采用支持列表内的 YouTube，查询目标使用明确授权的范围。Instagram/Facebook 可保留已验证能力；未通过对应契约测试的组合不标为支持。只读候选缺少地区、播放或粉丝证据时标“无法核验”，不得伪装为全部匹配。

状态链为：条件编辑→待确认提案→执行排队→采集中→结果整理→候选简报可用/真实空结果。旁路包括：提案拒绝、执行失败、请求取消、已取消、结果待核实。聊天运行结束不能将失败覆盖为“待命”；远端结果未知时只允许核对/接管，禁止自动重启。

### 3.3 实施步骤

| P1-D1 复现与契约盘点 | 固定版本复现条件消失、模板丢失、错误身份、返回错误、侧栏无响应；查当前真实工具 schema 与本地闸门 | 前端 / 后端 / 测试 | 原因与证据矩阵；点击无响应单独记录，不沿用未证实归因 |

### 3.5 验收、发布和回滚

| ID | 前提与操作 | 必须观察到的结果 |
|---|---|---|
| AT-01 | 有历史失败的员工从今日任务进入新 AI发现 | 条件和模板可编辑，不自动恢复旧失败；同步字典失败不丢已输入条件 |
| AT-02 | 修改平台/地区/方向并提交，随后返回、刷新和重开 | 条件卡、正文、服务端快照一致；线索身份正确；恢复同任务；侧栏每个本期相关入口可达 |

| AT-04 | 确认一项允许的采集并重复点击确认；另一窗口同时尝试启动 | 首项只有一次执行与稳定 ID；第二个运行受排他控制；可查看真实候选或已核验空结果 |

| AT-06 | 故障注入启动响应丢失、候选读取失败、无 task_id 查状态 | 显示结果待核实/读取失败/未启动；不全局取数；不盲重启；修复后恢复读取或人工接管 |

**正常演示脚本：**今日任务→AI发现→调整条件→查看并确认采集→观察真实进度→打开候选与证据→返回→重开同任务。另演示一次失败恢复。测试夹具不足以代替真实 harness 的工具使用检查；至少一个有候选的授权运行和一个受控空结果用例分别取证，不为追求命中扩大采集范围。

**退出条件：**AT-01–06 全部通过；正常候选链完成；导航失效完成复现定位并修复/证明验证范围内已排除；真实集成及取消/对账证据齐备。缺少结果后处理或真实候选证据时，本期仍未完成。

**回滚：**关闭新的发现提交，保留条件、历史运行、监控、取消/接管和回执读取；回退到已验证兼容版本，不恢复绕过确认的旧采集入口。已执行采集不能通过删记录“回滚”。

## 4. P2：一封新邮件到当前回复任务的完整闭环

### 4.1 用户故事与范围

员工正在处理一个合作关系的回复任务。新邮件进入后，中栏及时展示原文变化，Agent 解释意图及对当前草稿的影响；员工比较建议、保留人工修改，核验最新依据后完成授权发送，并看到真实回执。

**关联需求：**TW-06–10、TW-18–20。首期只选择一个确定的合作关系和已授权邮箱来源；不以全量历史重分析为前置。不自动批准延期，不修改正式阶段，不要求先完成 P3 的新审批联动。

**退出条件：**AT-07–12 全过；一个真实 harness 的影响分析有可核验原文；已授权测试发送成功并取得回执；不同权限用户交叉测试、模型失败和源滞后行为通过。无法获取授权测试对象时，记录已完成开发/隔离验证，不能报告发送闭环已发布。

**回滚：**暂停新增自动影响分析与新提交入口，保留原文、已保存稿件、回执与现有安全网关；关闭自动分析不放开过期确认。事件保留，可从游标恢复，不重复发信。

## 5. P3：审批与关联工单真正影响当前工作

### 5.1 用户故事与范围

员工的当前动作正在等待特定审批或前置工单。审批通过/驳回/撤回、前置工单完成/重开时，中栏解释变化，当前工单重新计算可执行性；员工完成对应动作及工单验收，结果反馈关联任务。

**关联需求：**TW-11–13、TW-10/18–20。首批绑定一个现行已发布审批类型和一个明确的前置→后续工单关系；不得用“任意审批通过”解锁全部动作。该类型与规则在 P3-D1 固定并纳入证据包；不新造审批链、费用阈值或完成条件。

### 5.2 实施步骤

| 步骤 | 具体工作 | 责任角色 | 可检查产物 |
|---|---|---|---|
| P3-D1 绑定范围 | 选定发布审批类型、动作与内容版本映射，确定工单依赖/验收规则；核对 Task/WorkOrder 权威 ID | KOL 业务 / 审批产品 / 架构 | 一张具体类型与规则映射表；未决定不能编造可用链 |
| P3-D2 接入变化 | 审批决定、撤回及工单变更事务提交后产生持久事件，关联当前任务 | 后端 | 有来源、版本、操作者、前后状态；重放去重 |
| P3-D3 影响与建议 | 规则计算阻塞；Agent 解释后果；建单/合并建议保留事件依据 | 智能体产品 / 后端 | 正式状态与 AI 建议分离；既有工单优先复用 |
| P3-D4 提交与联动 | 当前动作复核对应审批及前置工单版本；确认后排队再复核；完成后更新自己的工单记录 | 后端 | 不同内容不能复用旧审批；父任务完成需独立满足验收 |
| P3-D5 工作台 | 中栏显示原因、结果和下一步；右栏显示产物版本及可用动作；点击关联工单可返回 | 前端 / UIUX | 不复制审批处理页；只给有权限的详情入口 |
| P3-D6 验证 | 审批版本变化、前置工单重开、重复事件、越权及故障恢复 | 测试 | AT-13–17 与真实授权审批流程证据 |

**复用资产：**`backend/src/approval/review-service.ts`、`ticket-domain/task-work-orders.ts`、`work-order-verified-event.ts`、`work-order-shadow.ts`、`work-order-executor.ts`、现有工单自动化发布与事件处理机制；`frontend/src/reviews/`、`pages/Tasks.tsx`。新能力不得另建审批引擎或第二套调度器。

### 5.3 验收与退出

| ID | 前提与操作 | 必须观察到的结果 |
|---|---|---|
| AT-13 | 审批通过，随后执行其覆盖的动作 | 当前任务解除对应阻塞；仍走该动作规定的确认；有执行回执；审批通过本身不发信/付款 |
| AT-14 | 审批驳回/撤回，或已审批内容发生实质修改 | 原因明确；旧版本不能提交；修改后按规则重新申请/确认，不覆盖原决定 |
| AT-15 | 前置工单完成→后续可处理；在执行前前置又重开 | 每次按当前依赖规则重算；过期允许状态不放行；不自动完成父任务 |
| AT-16 | 同一事件重复到达、并发采纳相同建单建议 | 不重复建单/分派；可查采纳依据及幂等结果；未采纳建议不是正式待办 |
| AT-17 | 另一品牌同 KOL 审批、无权工单引用、队列重启 | 不串用审批/私有详情；拒绝信息不泄露敏感字段；恢复后状态和回执一致 |

**正常演示脚本：**进入等待中的工单→有权审批人处理审批→中栏收到结果→前置工单验收→当前动作预检与确认→执行回执→当前工单按验收完成→回到任务看到剩余工作。驳回/撤回另演示一次，不让演示等同于真实生产审批授权。

**退出条件：**AT-13–17 全过，选定类型和依赖链实际贯通；至少一次通过后执行、一次拒绝后修改重提均可追溯。审批结果仅显示而未影响执行校验，或只有工单状态镜像，都不能验收。

**回滚：**停止新增联动和自动建单，保留审批决定、工单原状态和回执；返回现有人工处理入口。执行网关继续检查审批与依赖，不能因前端功能关闭而绕过校验。

## 6. P4：阶段、期限与归属变化进入当前任务

### 6.1 用户故事与范围

员工处理履约/跟进任务时，正式阶段变化、延期申请/批准、临期/逾期以及归属变化持续进入中栏。员工依据变化修订计划或提出明确阶段变更；到期归属按已发布规则后台复核和释放，旧页面随之失去不再拥有的资格。

**关联需求：**TW-14–16、TW-10/18–20。首批明确合作及期限类型，不引入全生命周期规则重写。正式 KOL 阶段沿用 [阶段转移细则](../business-rules/stage-transitions.md) 与 BIZ-12 的确认/审批规则；工单局部阶段自动化不能被当作正式 KOL 阶段自动写入授权。

### 6.2 规则依赖与实施步骤

| 步骤 | 具体工作 | 责任角色 | 可检查产物 |
|---|---|---|---|
| P4-D1 规则及来源 | 确定期限来源、延期生效证据、临期阈值、正式阶段来源；核对有效互动和归属释放政策 | KOL 业务 / 后端 | 发布版本、来源与冲突处理；未知口径不硬编码 |
| P4-D2 展示与影响 | 接入阶段/期限/归属事件；显示正式值、请求、建议、预测的差异 | 后端 / 智能体产品 / 前端 | 同一任务能看到变化及原依据 |
| P4-D3 阶段与延期处理 | 复用独立阶段确认、延期审批/处理入口；新期限生效后重排持久定时作业 | 后端 / 前端 | 已批准期限有证据；发送不改阶段；旧作业失效 |
| P4-D4 14天归属 | 已发布完整政策后启用持久释放作业，执行前核验最新有效互动、同步完整性、当前归属和权限 | KOL 业务 / 后端 | 带政策版本的释放决定与回执；并发只释放一次 |
| P4-D5 撤权与补偿 | 归属/组织改变后使缓存、摘要、推送、规划及旧确认失效；保留允许的审计 | 后端 / 前端 | 旧员工不能继续访问私有材料；接手人不自动获得无授权历史 |
| P4-D6 验证 | 临界时间、迟到有效邮件、源不可用、换人、重启、合法阶段变更与回滚 | 测试 / 业务 | AT-18–23；授权外部状态回执 |

**规则空白处理：**没有证据证明有效往来、计时起点、日历/时区、排他范围已发布时，P4-D4 保持未启用；P4-D2/D3 可完成独立里程碑，但整个 P4 不能因此标记完成。现有 `days >= 14` 或“最新邮件时间”不构成完整政策。

**复用资产：**`backend/src/stage-judgment.ts`、`stage-transitions-graph.ts`、`gateway/ownership-release.ts`、现有阶段动作、归属服务和持久调度；`config/stage-transitions.json`；相关 Policy。只在原生 PostgreSQL 路径扩展，不用浏览器计时器驱动正式到期动作。

### 6.3 验收与退出

| ID | 前提与操作 | 必须观察到的结果 |
|---|---|---|
| AT-18 | 邮件建议推进阶段；员工提出明确目标并完成所需确认/审批 | 建议与正式值分开；正式值只依据成功回执变化；发送邮件不顺带改阶段 |
| AT-19 | 延期申请→批准/驳回→新期限生效 | 各步独立；批准前旧期限仍按规则有效；生效后旧提醒失效，不产生矛盾催办 |
| AT-20 | 按已发布时区/日历模拟14天边界及续期 | 边界前不释放；有效互动后旧释放作业失效；只产生一次合法释放 |
| AT-21 | 到期前源同步失败/不完整，或迟到邮件的发生时间早于释放检查 | 不将未知当成无互动；按已发布规则核验/接管；发生时间与接收时间分别留存 |
| AT-22 | 重新分配、两个 Worker 并发、释放后旧页面提交 | 旧归属版本不能解除新关系；当前权限阻止旧提交；公海不公开私有邮件/价格 |
| AT-23 | 任务进程重启、阶段远端超时、提醒反复投递 | 持久恢复；阶段未知结果先对账；提醒与副作用去重；等待有原因和接管入口 |

**正常演示脚本：**履约任务收到延期申请→核对/审批→正式期限更新→临期提醒正确重排→员工处理任务。另用明确授权对象和可控时钟验证14天归属释放、续期阻止释放及权限收敛；不得通过修改真实历史互动时间强行让生产 KOL 到期。

**退出条件：**AT-18–23 全过，完整14天规则有已发布证据，阶段/期限/归属三类状态分离、实际回执与权限收敛通过。仅做提醒或仅展示倒计时不等于归属闭环。

**回滚：**停用新增自动作业，保留事实、回执与人工接管；已释放关系不静默重新领取，已改阶段不以数据库回写假装未发生。需要恢复归属或业务补偿时按现有授权动作执行并另留回执。

## 7. P5：工作规划与实际工作形成反馈闭环

### 7.1 用户故事与范围

员工查看今日任务/我的待办，能看到由已发生业务变化支持的优先级和阻塞原因。点击建议进入原任务并恢复工作现场；完成实际工作后，计划更新，不再继续建议处理已经完成或失效的事情。

**关联需求：**TW-17–20。复用 `agent:workspace-planner` 和 `today_plan`、`todo_plan`、`today_analyze`。范围是本人获准查看的工作区摘要；不新增外部连接器、不重新读取所有 KOL 原文、不自动创建正式任务。

### 7.2 实施步骤

| 步骤 | 具体工作 | 责任角色 | 可检查产物 |
|---|---|---|---|
| P5-D1 摘要契约 | 将任务目标、真实状态、期限依据、阻塞、变化、下一步和可访问入口投影为统一摘要 | 平台产品 / 后端 | source/context version 明确；按权限先过滤 |
| P5-D2 增量更新 | 关键事件标记规划过期；员工请求或已发布触发规则启动规划；合并事件窗口 | 后端 / 智能体产品 | 不逐封邮件无限重规划；旧计划可读且标过期 |
| P5-D3 规划解释 | 输出顺序改变的原因、证据引用和实际可执行入口 | 技能实施 / 前端 | 不凭模型生成假截止日期、假审批或假任务 |
| P5-D4 采纳与返回 | 已有任务“开始处理”复用原 ID；新建议采纳调用正式建单契约；保存返回位置 | 前端 / 后端 | 不重复建单；任务完成/取消回流规划 |
| P5-D5 验证 | 多任务变化、跨用户隔离、模型失败、去重、成本与闭环演示 | 测试 / 平台产品 | AT-24–28、真实规划 harness 与试点指标 |

**复用资产：**`agents/workspace-planner/manifest.yaml`、`backend/src/host/today-plan-context.ts`、`today-plan-run.ts`、`planning-types.ts`、前端 Today/Scope 工作台。保留业务与规划边界，KOL 事实解释由业务侧完成后提供有来源摘要。

### 7.3 验收与退出

| ID | 前提与操作 | 必须观察到的结果 |
|---|---|---|
| AT-24 | 一项任务因审批通过可执行，另一项因有效延期不再紧急 | 规划依据当前摘要调整顺序，解释两个变化；不虚构源未提供的期限 |
| AT-25 | 点击已有任务建议，处理后返回计划 | 恢复原工作现场；完成后建议收敛；不产生平行会话/任务副本 |
| AT-26 | 同一新建议被双击采纳、多个事件重复触发 | 正式任务只创建一次；未采纳仍是候选；规划本身无外部写权限 |
| AT-27 | 撤权或转交后重新规划；访问他人摘要和旧计划链接 | 当前范围重新过滤；旧链接拒绝或安全降级，不泄露旧摘要 |
| AT-28 | 模型失败、预算硬停、来源部分过期、事件密集到达 | 旧计划保留并标状态；当前业务任务照常可处理；有重试/恢复且无调用风暴 |

**正常演示脚本：**查看计划→某任务收到业务变化→规划标注变化并重算→选择原任务→完成工作→回计划看到真实结果。必须包含真实 harness 规划和实际任务状态回流，不能只录制排序动画。

**退出条件：**AT-24–28 全过；至少一次真实跨任务变化→规划→原任务处理→回流演示通过；权限、预算和重复采纳通过；声明接入来源与实际发布清单一致。

**回滚：**暂停自动重规划，保留已发布任务列表、原任务入口、手动规划和历史说明；不删除已采纳任务。原任务事实仍独立于规划服务运行。

## 8. 跨 Phase 测试策略与发布证据

### 8.1 测试层次

| 层次 | 验证什么 | 不代表什么 |
|---|---|---|
| 纯函数/契约 | 状态映射、参数支持、版本差异、依赖选择、事件幂等 | 不证明源已接入或模型会正确调用 |
| PostgreSQL 集成 | 原生事务、竞争、权限过滤、持久化、重启恢复、outbox | 不证明真实远端结果 |
| 前端 E2E | 入口→协作→结果→返回，异常恢复、焦点/键盘/三轴 | 网络桩通过不证明真实业务闭环 |
| 真实 harness 评价 | 正确技能、参数、证据引用、意图及影响质量、不可信输入 | 模型正确不证明正式动作有权限/已执行 |
| 授权外部集成 | 真实来源、准确范围、远端回执、状态与产物一致 | 单个对象成功不代表所有平台/品牌均支持 |
| 回滚与值守演练 | 停止新提交、保留在途作业、恢复游标、未知结果接管 | 不可逆外部动作不会因代码回退而消失 |

### 8.2 验证执行依据

实施时按实际变更选择并执行仓库脚本，不为纯文档改动运行外部写入：

- 后端：`backend/package.json` 的 `validate:contracts`、`validate:registry`、相关类型检查、隔离 PostgreSQL 集成测试、相关模型评价和发布门禁。
- 前端：`frontend/package.json` 的类型检查、构建、相关 E2E；UI 验收按 DESIGN §13。
- 发布：`.github/workflows/release-gate.yml`。每期新增的闭环 E2E 必须被相关发布门禁实际执行，不能只提交一个未被运行的测试文件。
- 确认既有失败是否影响本期；区分基线失败、环境问题和新回归，保存复现证据。不得降低权限、移除断言或用模拟通过隐去本期缺陷。

### 8.3 真实 harness 评价样例集合

各期从下列主题选取涉及项，逐条列出输入、合法动作、禁止行为、证据和结果：正常信息、字段缺失、真实空结果、冲突证据、相同长度修订、迟到事件、超长邮件历史、人工改稿、错误对象关联、提示注入、工具参数拒绝、来源失联、取消、远端结果未知、审批版本改变、归属撤销。

关键失败（越权、伪造事实/执行、绕过确认、重复副作用）任一出现，阻止该范围发布。模型解释质量阈值由业务角色在样本清单上确定，不能用平均分掩盖关键失败；相关事实引用可回查是硬验收项。

## 9. 指标、依赖与责任

指标定义见 PRD §11。P1 建立工作现场恢复率、重复副作用、导航失败及采集闭环基线；P2 增加来源时效、分析延迟、过期依据拦截和人工稿保留；P3 增加审批/依赖错放行与重复建单；P4 增加错误释放、旧定时任务与撤权收敛；P5 增加重复建议、计划过期时间、采纳到完成的转化。不能用模型运行次数代替用户完成工作。

| 职责角色 | 决定 / 交付内容 | 不能替代的责任 |
|---|---|---|
| 平台产品经理 | 范围、闭环定义、目标指标与平台入口 | 不定义有效往来和业务审批权 |
| 智能体产品经理 | 技能入口、上下文/影响输出、角色协作与规划关系 | 不以模型建议授予正式权限 |
| KOL 业务专家 | 来源、关联、阶段、期限、有效互动、审批/工单业务规则 | 不替后端设计并发事务 |
| UIUX / 前端专家 | 工作台布局、导航、恢复、编辑与无障碍 | 不在页面决定业务资格 |
| 架构 / 后端专家 | 数据映射、契约、权限、持久事件、执行、恢复 | 不从旧实现猜现行规则 |
