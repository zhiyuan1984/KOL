# AI 发现结果页：基于 Median Crawler 与 Starry KOL 的线索转化设计

**作者：Manus AI**  
**版本：v1.0**  
**日期：2026-09-24**

## 1. 设计结论

AI 发现的结果页不应被定义为“爬虫结果列表”，而应被定义为**KOL 线索的转化决策页**。员工打开结果页后，需要在一分钟内得到四个确定答案：这位红人是否符合本次 Brief；采集数据是否足以支持判断；是否已经满足入库到 Starry 的条件；入库后将进入哪一个可继续跟进的工作面。

> **Median Crawler 提供可复核的表现证据；评分将证据转化为优先级；Starry KOL MCP 承接已确认的档案与公海状态；结果页负责让人完成“筛选—复核—确认入库”的决策。**

因此，结果页应将“匹配度”“表现质量”“数据可信度”“入库可行性”拆开呈现。一个内容表现很好的候选人，不应因为没有邮箱、稳定外部 ID 或负责人映射而被显示成“可立即入库”；反过来，一个数据样本较少的候选人，也不应被假装成低价值，只能被标记为“需要人工复核”。

本设计以右栏展开后的共享宽度为基础。桌面端结果栏最大宽度为 **820px**，并与今日任务保持一致。该宽度足以容纳高密度的结果清单；复杂证据只在展开详情或抽屉中展示，避免首屏成为不可扫描的字段堆。

## 2. 真实数据与业务边界

### 2.1 目标转化链路

用户定义的来源是 **Median Crawler**。当前实现已经保存平台、平台内账号 ID、粉丝数、最近播放样本、均值、中位数、稳定度、播放/粉丝比、采集时间、来源链接、匹配词和原始联系邮箱等字段。系统以最近播放样本推导 `view_median`、`view_mean`、`view_follower_ratio`、`stability` 与评分，再投影为发现候选人。[1] [2]

用户确认入库后，后端不会直接发送邮件、领取跟进、修改合作阶段或写入活跃跟进关系。它先通过 Starry `addKolProfile` 创建或找回红人主档，取得 `kolUid`；随后调用 `importKolProfilesFromCrawler` 补齐平台账号字段，并把本地公开档案写为公海状态。这个动作有 L3 确认、幂等回执和失败原因，不应被包装成“自动跟进”。[3] [4]

```text
Median Crawler
  └─ 原始采集与最近内容样本
      └─ 评分与 Brief 匹配
          └─ 发现结果页：复核、补资料、选择
              └─ L3 确认
                  └─ Starry KOL MCP：建档 + 爬虫字段导入
                      └─ Starry 公海
                          └─ 后续人工筛选、分配与跟进
```

结果页的职责止于“把符合条件且可验证的线索安全地转入 Starry 公海”。后续是否分配负责人、进入合作阶段、生成邮件或实际触达，应在公海和“我的红人”工作面中另行确认。

### 2.2 当前字段能支持什么，缺什么

| 决策问题 | 当前可用数据 | 结果页应如何表达 | 需要补充或规范的数据 |
|---|---|---|---|
| 是否匹配本次发现任务 | 平台、匹配词、`match_reason`、`fit`、Brief 条件 | 显示“为什么匹配”，并把命中的方向、关键词、地区或平台证据写为短句 | 结构化匹配因子与未命中因子 |
| 内容表现是否可接受 | 粉丝、近十条播放、播放中位数、均值、稳定度、播放/粉丝比、推荐分 | 用“内容表现”分组展示，不与入库资格混为一个分数 | 指标口径版本、阈值来源、评分权重 |
| 数据是否可靠 | 样本条数、置信度、采集时间、来源链接 | 显示“样本覆盖”和“采集新鲜度”，缺失则明确说明 | `crawl_job_id`、采集源名称、来源可用性、数据过期阈值 |
| 是否能进入 Starry | 真实邮箱、平台、平台账号、来源链接、库内状态 | 显示“可入库 / 需补资料 / 已在公海 / 已跟进” | 后端预检的可入库性、阻塞原因、`kolUid`、负责人映射结果 |
| 入库后去哪里 | 当前可见三态为未入库、公海、已跟进 | 清晰地展示 Starry 公海或已跟进状态 | Starry 侧主档链接、阶段、负责人和入库回执状态 |

当前前端候选对象已包含表现与匹配字段，但只有 `libraryStatus` 三态，且没有暴露 Starry 的可入库预检结果。当前页面还把原始邮箱直接放在结果行内，并把“推荐分”“置信度”“匹配理由”“在库状态”压在同一视觉层级中。[5] [6] 这会让用户难以判断“高分”究竟意味着高内容表现，还是已经具备转化条件。

## 3. 结果页的信息架构

结果页采用“**结论优先、证据按需展开、动作只在条件满足时出现**”的三层结构。

### 3.1 第一层：发现结论与转化概览

结果栏顶端保持固定，不再重复展示冗长的运行日志。运行日志属于中栏；右栏只保留与结果决策相关的摘要。

第一行显示发现任务名称、运行完成时间与数据来源。例如：“户外电源 · YouTube · Median Crawler · 12:24 更新”。第二行给出一句结论，例如：“7 位候选中，3 位已满足 Starry 入库条件；2 位需补充邮箱；2 位已在库。”结论必须来自后端字段和预检结果，不能由模型自由编造。

摘要下方使用四个可点击的状态计数，而非只显示“原始 / 入围”：

| 状态卡 | 含义 | 默认操作 |
|---|---|---|
| 可入库 | 有真实联系邮箱、稳定外部 ID、支持的平台，并且不在 Starry 公海或跟进中 | 默认优先显示，可勾选入库 |
| 待复核 | 数据样本、匹配证据或必要资料不足，需要人工判断 | 打开复核筛选，不进入默认批量选择 |
| 待补资料 | 内容表现可能达标，但缺邮箱、来源链接或其他入库前置条件 | 打开阻塞原因和补资料动作 |
| 已在 Starry | 已在公海或已跟进，不能重复导入 | 进入 Starry 档案或显示当前状态 |

“已在 Starry”必须进一步区分 **已在公海** 与 **已跟进**。这两个状态的后续动作完全不同：前者仍可在公海筛选；后者应避免重复创建线索，并显示负责人与当前阶段（数据可用时）。

### 3.2 第二层：可扫描的候选清单

候选清单的默认排序不应只是“推荐分由高到低”。应使用 **转化优先级**：先显示“可入库且高匹配”的候选，再显示“待复核”，最后显示“待补资料”和“已在 Starry”。用户仍可改按内容表现、匹配度、采集时间或粉丝量排序。

每个候选卡只回答四件事：是谁；为什么值得看；数据是否可信；下一步能做什么。建议卡片高度为 112–136px，默认不展示完整邮箱、完整平台 ID 或全部十条播放样本。

| 卡片区域 | 默认展示 | 交互和规则 |
|---|---|---|
| 身份区 | 头像、名称、平台、账号短标识、地区（有数据时） | 名称与平台链接到来源；不以首字母占位替代真实头像，但头像缺失时保留中性占位 |
| 决策区 | 转化优先级 `P1 / P2 / P3`、入库状态、匹配度 | `P1 可入库`、`P2 待复核`、`P3 待补资料` 是状态，不是营销标签 |
| 表现区 | 播放中位数、近十均播、稳定度、播放/粉丝比 | 中位数优先于均值；所有指标旁可查看样本覆盖和采集时间 |
| 证据区 | 最多两条匹配理由，例如“命中 camping、portable power station” | 证据不足时写“内容匹配证据不足”，不能显示为普通低分标签 |
| 操作区 | `查看来源`、`详情`、多选框 | “忽略本次发现”放入更多操作；可入库候选才允许默认勾选 |

列表顶部提供三个轻量筛选：**转化状态**、**数据质量**、**平台**。不在首屏堆放复杂的高级筛选。常用筛选为“仅可入库”“仅高匹配”“样本不足”“已在 Starry”。筛选后的统计应同步更新，批量操作只作用于当前可见且可入库的候选。

### 3.3 第三层：证据、评分与转化详情

点击“详情”后，使用右侧抽屉或卡片内扩展区，而非跳离结果页。详情由四个区段组成，顺序必须服务于决策。

**推荐结论**位于最上方。它明确说明“建议入库”“需要补资料”或“建议跳过本轮”，并给出不超过三条可复核理由。示例：“建议入库：最近十条样本完整；播放中位数高于本次阈值；关键词与露营电源方向匹配。”

**评分账本**展示四个彼此独立的信号：匹配度、内容表现、数据可信度和入库可行性。推荐优先级是这四项的组合排序，而不是替代它们。每项均应显示数据来源与缺失原因。例如，“数据可信度：低，原因是仅有 1/10 条播放样本”；而不是只显示“置信度低”。

**Crawler 证据**展示平台来源链接、采集时间、样本数、播放中位数、均值、稳定度、播放/粉丝比和最近十条播放趋势。趋势可用极简柱状或折线图呈现；每个点必须可追溯到采样值。没有样本时展示“未采集到播放样本”，不得用零值替代。

**Starry 转化准备度**展示入库预检。它应列出“真实联系邮箱”“平台和稳定账号 ID”“支持的平台”“负责人邮箱映射”“Starry 重复档案”等检查项。通过项使用“已满足”，阻塞项显示具体原因与资料补齐入口。用户应在这个区域知道点击“入库”后会发生什么：创建或复用 Starry 主档、导入爬虫平台字段、进入公海；不会自动发送邮件、改阶段、领取或建立跟进关系。

## 4. 评分与状态的呈现原则

### 4.1 把一个“推荐分”拆成四个可解释信号

当前代码的 `score` 基于粉丝和最近播放样本计算，详情中也可获得中位数、均值、稳定度和播放/粉丝比。[1] 这个分数应被命名为 **内容表现分** 或 **表现评分**，而不是笼统的“推荐分”。

结果页的推荐排序由以下信号组合，但每个信号需独立呈现：

| 信号 | 数据来源 | 视觉标签 | 用户要做的判断 |
|---|---|---|---|
| Brief 匹配度 | 平台、地区、方向、匹配词与匹配理由 | 匹配度 | 这位红人是否适合此次合作任务 |
| 内容表现 | 播放中位数、近十均播、稳定度、播放/粉丝比、粉丝量 | 表现 | 内容传播表现是否达到预期 |
| 数据可信度 | 样本覆盖、采集时间、来源可访问性 | 数据质量 | 是否需要再查看来源或补采样 |
| 入库可行性 | 邮箱、稳定账号 ID、平台映射、Starry 重复和负责人映射 | 转化状态 | 是否可以安全转入 Starry |

颜色只用于状态强化，不能是唯一含义。建议使用绿色“可入库”、琥珀色“待复核”、灰色“待补资料”、蓝色“已在公海”、紫色“已跟进”；每个状态旁始终保留文字。评分不使用“红绿好坏”色，而使用数字、等级与可解释原因。

### 4.2 数据新鲜度与置信度必须可解释

“置信度低”没有转化价值，除非用户知道低在哪里。产品文案应改为“播放样本 1/10，内容表现仅供初筛”“采集于 3 天前，建议先查看来源”“来源链接缺失，不能在结果页完成复核”。

建议按采集时间定义配置化的新鲜度：例如 0–7 天为“新鲜”，8–30 天为“需复核”，超过 30 天为“可能过期”。具体天数应由业务配置，而不是前端常量。由于当前候选已保存 `collectedAt`、样本数和来源 URL，这一能力主要需要标准化服务端口径和 UI 映射。[5] [6]

### 4.3 邮箱是转化前置条件，不是普通资料字段

Starry 建档必须使用候选人真实联系邮箱；缺少邮箱时，后端会拒绝入库，不会用负责人邮箱代替。[3] 因此，结果页不应把邮箱视为一行普通文字，而应将其转换为“入库准备度”的关键检查项。

默认列表只展示“邮箱已验证”“邮箱待补充”或掩码邮箱，例如 `ver***@gmail.com`。完整邮箱属于敏感联系信息，应仅向具有导入权限的用户展示，并保留访问审计。此调整能降低结果页的隐私暴露，也能让用户优先处理真正能转化的候选。

## 5. 关键交互与转化路径

### 5.1 快速筛选：从候选列表到 Starry 公海

用户完成一次发现后，结果页默认激活“可入库”状态卡。用户快速查看每张卡的匹配理由、表现与数据质量，勾选需要进入 Starry 的候选。选择工具条显示三组数量：已选可入库、待补资料、已在 Starry。只有可入库部分进入“入库公海”操作；其余对象显示原因，不混入确认数。

点击“入库公海”后，L3 确认弹窗必须明确显示：将创建或复用多少个 Starry 档案；将导入多少个爬虫平台记录；有多少条因缺邮箱或重复而不会写入；本操作不会发送邮件、改合作阶段、领取跟进或自动建联。确认完成后，列表行即时变为“已在公海”，提供“查看 Starry 档案”与“前往公海”的链接。

### 5.2 深度复核：从数据异常到人工决策

用户发现高表现但数据不足的候选时，打开详情。详情先展示“本轮建议”，再展示播放样本趋势和评分账本。用户可将候选标记为“待补资料”“忽略本轮”或保留为“待复核”。

“忽略”不应相当于删除。它应仅隐藏于本次运行，并允许通过“已忽略”筛选恢复。这样可以减少错误操作，也让团队能够了解某类线索被放弃的原因。

### 5.3 入库后交接：不把入库误认为完成跟进

导入成功后，结果页的下一步文案应为“已进入 Starry 公海，等待筛选或分配”，而不是“已跟进”或“已联系”。如果用户确实需要进入跟进流程，应通过公海或“我的红人”页面发起新的明确动作。该动作可创建后续任务，但不能由发现结果页静默触发。

## 6. 建议的桌面布局

桌面端右栏宽度与今日任务完全一致，使用以下自上而下的结构：

```text
┌──────────────────────────────────────────────┐
│ 发现结论：户外电源 · YouTube · Median Crawler │
│ 7 位候选；3 位可入库；2 位待补资料；2 位已在库 │
├──────────────────────────────────────────────┤
│ [可入库 3] [待复核 1] [待补资料 2] [已在库 2] │
│ 筛选：仅可入库  数据质量  平台      排序：转化优先级 │
├──────────────────────────────────────────────┤
│ □ P1 可入库  Wildcrafted Veronika             │
│   YouTube · 194k 粉丝 · 播放中位数 2.3M       │
│   匹配：露营 / portable power station         │
│   数据：10/10 样本 · 今日采集 · 邮箱已验证     │
│                              来源  详情  更多 │
├──────────────────────────────────────────────┤
│ □ P2 待复核  The Solar Lab                    │
│   …                                            │
├──────────────────────────────────────────────┤
│ 已选 2 位可入库                    入库公海（2） │
└──────────────────────────────────────────────┘
```

顶部摘要在滚动时固定在结果栏内，状态卡和筛选条可吸附在摘要下方。候选列表独立滚动；选择工具条在存在选择时固定在底部。这样用户无论滚到第几条线索，都能看到当前筛选范围与可执行动作。

窄屏模式不应保留双列信息密度。状态卡改为横向可滚动的计数卡；候选卡以纵向信息排列；详情使用全屏抽屉；批量入库条固定在屏幕底部。所有横向操作必须满足触摸目标尺寸，并避免在窄屏中显示完整邮箱。

## 7. 后端与前端契约设计

### 7.1 增加后端的“入库预检”投影

前端不能仅根据是否有邮箱来猜测能否写入 Starry。稳定外部 ID、平台字典映射、联系人邮箱、负责人映射和重复档案都由后端掌握，且实际入库流程会对这些条件逐一校验。[3] 因此建议为当前运行的候选增加批量只读预检投影，例如：

```ts
type DiscoveryConversionReadiness = {
  state: "ready" | "review" | "blocked" | "in_pool" | "followed";
  importable: boolean;
  blockers: Array<
    | "missing_contact_email"
    | "missing_external_id"
    | "unsupported_platform"
    | "missing_owner_mapping"
    | "duplicate_in_starry"
  >;
  checks: {
    contact_email: "present" | "missing";
    external_id: "valid" | "missing";
    platform_mapping: "supported" | "unsupported";
    starry_record: "new" | "pool" | "followed";
    owner_mapping: "ready" | "missing";
  };
  kol_uid?: string;
  source_batch: string;
};
```

这个投影必须是只读的。它可以复用导入代码的校验规则，但不能在预检时调用 `addKolProfile`、`importKolProfilesFromCrawler`、发送邮件或改变阶段。真正的写入仍只发生在 L3 确认之后。

### 7.2 扩展候选的来源与评分解释

建议在 `HomeDiscoveryCandidate` 中补充以下只读字段：`data_source`、`crawl_job_id`、`metric_version`、`freshness_state`、`score_breakdown`、`match_evidence` 和 `conversion_readiness`。其中 `score_breakdown` 需要说明每个评分维度的原始值、权重、是否缺失与说明；`match_evidence` 需要列出命中的 Brief 条件和无法验证的条件。

不要在浏览器端以启发式重新计算评分或可入库性。浏览器只负责显示后端的事实与配置化口径，从而保证列表排序、详情解释和最终 Starry 写入使用同一套规则。

### 7.3 Starry 回执与结果同步

入库成功响应应返回每条候选的 `kol_uid`、导入状态、是否复用已有档案、失败原因和可跳转的 Starry 档案地址。当前后端已记录 `kol_uid`、`already_imported`、是否有真实邮箱和导入回执，但候选前端对象尚未完整暴露这些信息。[3] 结果页应以回执更新行状态，而不是假设批量请求成功即全部导入成功。

## 8. 分阶段开发计划

### 第一阶段：让现有结果页可转化

保持现有候选列表、详情展开、L3 确认和 Starry 导入链路。改造列表文案与视觉优先级：将“推荐分”改为“内容表现”；将“置信度”改为样本覆盖解释；将“在库”拆为公海与已跟进；在每行增加“入库准备度”状态。默认列表不显示完整邮箱，仅显示可用性。

这一阶段只使用当前字段和确定性派生状态，优先解决“好数据与可入库对象混在一起”的问题。

### 第二阶段：增加预检、筛选与可解释详情

增加批量只读预检接口和 `conversion_readiness`。实现状态计数、可入库筛选、阻塞原因、详情抽屉、评分账本与采集趋势。选择工具条只汇总可入库对象，并在确认前展示每种预检结果的数量。

这一阶段让用户从“看很多字段”变为“按阻塞原因处理线索”，直接提升入库成功率与审核速度。

### 第三阶段：完成 Starry 闭环和运营度量

把 Starry 导入回执投影回结果页，支持打开 Starry 画像、公海筛选和后续人工分配入口。加入漏斗事件：候选出现、详情打开、来源打开、标记待补资料、选择入库、确认、导入成功、导入失败、进入公海。基于这些事件衡量不同平台、关键词和数据质量下的转化率。

## 9. 验收标准

| 类别 | 验收要求 |
|---|---|
| 决策清晰度 | 用户在每条候选上能同时看见匹配、内容表现、数据质量与入库状态，不需要展开详情才能知道是否可入库 |
| 数据真实性 | 缺失播放样本、邮箱、来源或稳定账号 ID 均显示为缺失或阻塞原因；不得用零值、负责人邮箱或模型推测值填充 |
| 评分可解释性 | 每个表现分、匹配度和优先级都可在详情中追溯到数据字段与评分规则 |
| 转化安全 | 预检无写操作；导入必须经过 L3 确认；入库后不得自动发信、改阶段、领取或建立跟进 |
| Starry 一致性 | 成功、重复、阻塞和失败状态以 Starry 回执为准；成功项能展示 `kolUid` 与公海去向 |
| 隐私 | 默认列表不展示完整联系邮箱；完整联系信息遵循角色权限和审计要求 |
| 布局 | 展开右栏在桌面端与今日任务同宽；摘要与选择操作可固定，候选列表不产生横向溢出 |
| 可访问性 | 状态不只靠颜色表达；筛选、详情、来源与批量选择支持键盘操作和明确的可访问名称 |

## 10. 最终建议

结果页的最终形态应是一个**以转化为中心的 KOL 审核队列**。Median Crawler 的价值在于提供表现证据，而不是占满页面；Starry KOL MCP 的价值在于安全地承接已确认线索，而不是成为隐藏在“入库”按钮后的黑盒。产品必须在两者之间建立一层透明的决策界面：先解释价值与证据，再显示转化阻塞，最后让用户明确确认入库。

这样设计后，高价值且资料完整的红人会被快速转入公海；数据表现好但资料缺失的对象会进入可处理的补充队列；已经在 Starry 中的对象不会被重复导入；而真正的邮件触达和跟进仍由后续业务流程显式发起。
