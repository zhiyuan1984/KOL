# 候选分析与空结果状态修复审查

## 需求与责任

- 需求：修复发现页同时显示“正在分析候选快照”和“筛选无结果”，并区分尚未采集、结果未读完与权威零候选快照。
- 主责角色：前端专家；验收角色：测试经理。
- 宪法：CONST-04（前端只修交互状态，不改业务规则）、CONST-07（可靠呈现 Agent 内容）、CONST-08（记录审查）、CONST-10（验证边界）。
- 基本法：TECH-FE-01/03、TECH-TEST-01/02/03；PROD-AGENT-09。
- 实施细则：DESIGN §1.3、§8.6（等待真实、空态诚实）。
- 结论：**符合**。只改变发现页状态读取和呈现，不改模型回答、业务筛选条件、权限、确认和采集执行。

## 问题证据

1. `useDiscovery` 原先将任意已加载会话的 `agent_status=running` 返回为 `analyzing`，不要求当前回合属于候选快照分析。
2. `loadExisting` 原先在当前会话没有采集动作/快照时也将 `emptyKind` 设置为 `filtered`。
3. `DiscoveryResultPane` 的最终空态不排除 `state.analyzing`。
4. 采集动作已结束但 `result_state=running` 时，动作轮询原先可能提前停止。

## 方案与边界

- 候选分析等待仅由当前已持久化的专用分析请求与服务端运行状态，或正在提交的分析请求触发。
- 权威零候选结论需要已读取完成、完整且含候选数组的本任务快照；无快照或待确认不判为筛选无结果。
- 分析等待期间不同时显示最终空结果结论。
- 结果读取仍在进行时保留轮询和等待状态。
- 不触发采集、入库、跟进、发信或任务状态写入，不放宽任何 AND 筛选条件。
- 会话与 Home 深链原位保留；不通过重定向或重新提交消除问题。

## 验收

新增 `frontend/e2e/discovery-empty-analysis.spec.ts`，覆盖两种入口、初次思考、待确认、真正空快照、分析完成与刷新恢复、结果未读完、会话读取失败，并断言验证过程无非 GET 请求。

验证结果在 PR 与任务交付中记录；隔离 API fixture 用例证明前端状态行为，不证明外部采集能力或截图指定任务的结果。
