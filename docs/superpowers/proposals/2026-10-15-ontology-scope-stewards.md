## 3. 正式实现的设计约束

### 3.1 策略与人员绑定分离

正式实现应采用版本化、经授权发布的策略：

1. stable policy ID，例如 `ontology_change_review`。
2. 四个范围各自的负责人绑定，引用真实 user_id 或有明确授权证据的治理角色。
3. draft、published、retired 状态与版本、内容摘要、发布人、发布时间及正式授权依据。
4. 负责人应属于正确公司/组织范围，账号活跃；管理员身份不能自动推导审批权。
5. 缺失、未发布、停用、人员不存在、账号停用、组织不符或权限证据缺失时，明确拒绝或沿用当前正式策略，不能自动批准或猜测审批人。

实际数据库表、管理 API 和权限发布载体应由后端专家按现有架构审查后确定，本草案不宣称已存在相关能力。

### 3.2 正式策略发布与实际审批是两次动作

更改审批人意味着更改访问和决策权限。正式激活需展示精确 diff、四范围及人员、组织依据、生效版本、影响范围和回执，并由有权治理者按现行路径批准；不能让待指定负责人仅凭本样例自我取得权限。

当前生效规则在新规则正式授权、发布和部署前保持原样。若现有发布路径对这类规则变更有审批要求，必须走该路径，不能通过改动执行代码取消该要求。

### 3.3 新审批绑定生效策略的快照

新版策略正式生效后，新创建的 ontology_change 审批才可按该范围解析负责人。审批 payload 至少绑定：

- scope、申请人、变更说明、change_ref。
- 已发布 registry 的真实 base_version 与 content_digest。
- 待发布文件的 target_digest。
- 生效治理策略 ID、版本及摘要。
- 该版本下被授权的具体审批人及其组织/权限依据。

审批决定由真实审批者提交，后端重新校验权限与内容。身份、范围、策略或目标版本变化时不能使用旧确认盲目放行。

### 3.4 发布门禁保留

正式新版仍须核对：真实发布基线、目标内容摘要、有效治理策略及实际审批回执。不得只因为配置列出了负责人、提交了 PR 或管理员要求部署，就报告审批已经 consumed。

PostgreSQL 发布账本保持 append-only。审批创建与发布门禁应共用已发布权威基线，避免未发布代码提交推进工作树 HEAD 后导致字符串基线不匹配。
