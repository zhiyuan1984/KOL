## 1. 结论与改造原则

本次不再把 Home「今日任务 / 我的待办」中的编辑弹窗视为轻量任务编辑器，而是将其升级为**正式工单创建与编辑入口**；`tickets` 继续是唯一正式工单真相源，`task_runs` 只记录一次执行，`task_events` 只记录生命周期和运行过程，不能相互替代。

> **核心原则：事件产生事实，规则决定是否/如何成单，工单决定责任与流转，运行只产生过程与证据，验收才完成工单。**

本方案采用以下口径：

1. **一个工单，一份数据。** 今日任务、我的待办、任务中心、报表与管理端均按同一 `ticket_id` 读取投影，禁止复制任务记录。
2. **工单状态与运行状态分离。** 运行成功只代表产生可读产物；只有具备权限的人提交验收证据后，工单才进入“已完成”。
3. **组织、责任、关注者分开建模。** 创建人、受理组、受理人、工单关注人、业务负责人、审批人分别存储并保留历史，不继续以 `owner_user_id` 混用。
4. **三级组织由服务端驱动。** 前端只消费授权后的组织树和候选人；中心 → 部门/项目组 → 组 的级联、人员可选范围、上级关注者均由服务端计算并在写入时复核。
5. **自动建单/流转必须版本化。** 事件不能因为模型建议或前端按钮就直接成单；只有已发布规则能自动创建或改变工单状态。规则发布前，系统可做预览、候选和人工采纳，不冒充已自动执行。
6. **员工端做工作，管理端做治理。** 员工端不出现规则配置和组织治理；管理端不复制员工待办或第二个 Home。
7. **PostgreSQL 是唯一数据库。** 生产、开发、测试、迁移、规则评估、工单事务、审计、报表和 Outbox 全部以 PostgreSQL 为唯一运行时与唯一权威库；不再使用 SQLite 作为回退库、并行库、测试库或运行时兼容层。

### PostgreSQL-only 运行约束

- 应用启动必须要求有效 `DATABASE_URL`，未配置或不可连接 PostgreSQL 时直接失败并报告可诊断错误；不得自动创建或回落 SQLite 文件。
- 所有新字段和关系以 PostgreSQL migration 管理，使用 `uuid`、`timestamptz`、`jsonb`、外键、`check`、部分唯一索引和必要的 `btree/gin` 索引；不再新增 SQLite 方言、触发器或兼容改写。
- 并发写入使用 PostgreSQL 事务、行级锁/乐观版本号和 `FOR UPDATE SKIP LOCKED` 等原生语义；Outbox 与 Worker 继续以 PostgreSQL 事务提交、Redis/BullMQ 投递与回执更新组成可靠执行链。
- 本地开发与 CI 提供临时 PostgreSQL 实例或容器；前后端集成测试、故障注入和迁移回归均对 PostgreSQL 执行，不再把 SQLite 通过视为数据库验收。
- 已确认**不保留 SQLite 数据**：历史 SQLite 文件不得作为迁移输入、归档、测试夹具、运行时读取来源或故障回退目标；新系统只以 PostgreSQL 创建并管理数据。

## 3. 目标领域模型

### 3.1 工单主记录

保留 `tickets`，新增/规范下列字段与关系；先执行 **expand → 回填 → 校验 → enforce**，不破坏现有历史记录。

| 范畴 | 目标字段/关系 | 说明 |
|---|---|---|
| 基本信息 | `ticket_id`、标题、内容、目标 `goal`、下一步 `next_action`、优先级、风险、期限、时区 | 新建时必填项由票型决定；没有期限时必须填写“无期限原因”。 |
| 业务分类 | `business_category`、`stage_group`、`stage_code` | 与现有 `kind`（技术票型）并存：`kind` 回答“是什么工单”，业务分类回答“属于哪一业务阶段”。 |
| 关联对象 | `company_id`、`collaboration_id`、`object_type/object_id`、`project_id/activity_id`（存在时） | KOL 正式业务对象仍以 Collaboration 为锚点；不把全局 KOL 当作单一业务归属。 |
| 来源依据 | `ticket_basis_refs` | 记录业务事件、邮件、合同期限、风险事实、人工录入等来源的 ID、版本、时间与快照摘要。 |
| 组织与受理 | `ticket_org_scope`、`ticket_assignments` | 当前受理组、当前受理人及全部转办历史；不可使用一个 `owner_user_id` 代替。 |
| 关注关系 | `ticket_watchers` | 存创建人直属上级的自动关注关系、原因、组织版本、是否自动加入；可承载未来显式关注人。 |
| 生命周期 | `status`、不可变 `task_events(event_class=lifecycle)`、命令幂等回执 | 状态与事件在同一事务写入，修正以新事件表达，不更新/删除已有生命周期事实。 |
| 验收 | `acceptance_criteria`、`ticket_acceptances`、证据引用 | 完成仅由验收命令写入；运行成功不会自动完成。 |
| 自动化 | `ticket_rule_evaluations`、`automation_rule_ref/version`、去重键 | 可回放“哪条规则、基于哪个事件、为何创建/更新/跳过”。 |

### 3.2 角色与关系

```text
业务事件 ──[规则评估]──> 工单
                            ├── 当前受理组（三级组织叶节点）
                            ├── 当前受理人（受理组内合格成员）
                            ├── 创建人
                            ├── 自动关注人（创建人的直属上级）
                            ├── 关联 Collaboration / KOL / 邮件 / 合同等对象
                            ├── 运行（可有 0..n 次）
                            ├── 产物与运行证据
                            └── 验收事实（0..1 当前验收，历史可追溯）
```

### 3.3 “关注的人”规则

采用以下默认定义，待确认：

- **手工建单：** 自动关注人为创建人所在组织单元的**直属负责人**。
- **事件自动建单：** 系统账户仅是技术生产者，不作为“创建人”；先解析事件的业务责任人/被指派人作为 `accountable_creator_ref`，再取该人的直属上级作为关注人。
- **直属上级解析：** 优先取创建人所在第三级“组”的负责人；组负责人缺失时沿组织树向上取最近已配置的负责人，并在工单上显示实际取值和组织版本。
- **不可解析：** 不伪造关注人。默认采取 `422 creator_supervisor_missing`，提示管理员补齐组织成员、组负责人或用户映射后再正式提交；可保存为本地草稿，不创建正式工单。
- **转办后：** 原创建人上级继续保留为“创建监督人”；受理人的上级不自动替换，避免责任历史被改写。若后续需要“处理人上级共同关注”，以新增规则 `assignee_supervisor_watch` 单独发布，不与本规则混淆。

## 4. 三级组织级联与受理人联动

### 4.1 表单数据源与安全边界

`config/org-registry.yaml` 是当前试点来源，但不作为前端权限真相。后端建立带版本的只读组织投影，统一输出：

- 当前用户可选择的组织路径；
- 每个单元的父节点、层级、负责人、品牌/区域范围；
- 已映射且有有效 `user_ref` 的可受理成员；
- 当前组织版本、缺失字段与不可选原因。

前端不得提交任意 `owner_id` 或自行拼接关注人。提交时后端重新校验：公司、组织、品牌、区域、对象、创建人、受理组、受理人和关注人是否仍有效。

### 4.2 级联规则

| 控件 | 行为 | 校验 |
|---|---|---|
| 一级组织 | 显示可见中心；切换后清空下级 | 必须属于当前公司与创建人授权范围。 |
| 二级组织 | 仅显示该中心下的部门或项目组 | 变更时清空三级组和受理人。 |
| 三级组织/受理组 | 显示已选二级节点下的组；无三级组的分支可选二级叶节点，但显式标识“无三级组” | 受理组必须是可受理的叶节点，不接受前端伪造路径。 |
| 主受理人 | 默认显示主受理组中具有效账号、组织成员关系与对象范围的人；允许经明确“跨组受理”理由选择同公司、当前用户有授权范围的其他组成员 | 每张开放工单必须有且仅有一个主受理人；选择后写入 `ticket_assignments` 当前版本与历史。 |
| 协同受理人 | 允许从主受理组或授权的跨组成员中选择多名协同处理人 | 协同受理人不替代主受理人；处理量、验收和升级仍有明确主责任人，避免多负责人导致责任不可判定。 |
| 自动关注人 | 只读展示“由创建人组织关系带出”；显示解析链和组织版本 | 无负责人/映射时阻止正式创建，不以空值提交。 |

### 4.3 当前组织数据的前置补齐

当前注册表中 **LT 组、PQ-RO-TB 组负责人为空**，当前登录账号“鄢棽”也未配置组织单元和 `user_ref`。因此，在正式开启“创建人上级自动关注”前，必须补齐：

1. 当前建单员工的 canonical `user_ref`、主组织、任职有效期；
2. 两个三级组的负责人及其可登录 `user_ref`；
3. 需要作为受理人的成员账户映射和有效状态；
4. 组织负责人/成员变动的生效时间与组织版本。

在这些数据补齐前，界面可以展示表单和“组织信息待补齐”提示，但不能声称已正确带出关注人或正式完成派单。

## 5. Home：今日任务 / 我的待办的工单化弹窗

### 5.1 组件替换

将现有 `EditTaskDialog` 替换为统一的 `TicketFormDialog`，同一组件处理“新建工单”和“可编辑字段修改”；不允许在弹窗内自由改终态。

**表单顺序：**

1. **工单信息**：工单标题（必填）、工单内容（必填）、目标、下一步、附件/链接（若已支持）。
2. **业务关联与分类**：关联公司、Collaboration/KOL、来源依据（手工录入/事件引用）、业务大类、主阶段、票型。
3. **优先级与期限**：优先级、风险、开始日期、截止日期、时区；无截止日期时填写原因。
4. **受理与关注**：三级组织级联、受理人、自动关注人（只读）、创建人（只读）。
5. **验收条件**：结构化验收条件；无验收条件不能提交需要完成的正式工单。

**不放进普通编辑表单的字段：**

- `completed/cancelled/reopened`：走单独的受控命令、确认卡和审计回执；
- 当前执行状态、运行错误、Worker 信息：只读展示在详情；
- 自动规则版本、来源事件原文：只读依据链；
- 关注人规则来源：只读，防止人为伪造上级关系。

### 5.2 编辑与权限

| 用户动作 | 入口 | 服务端命令 | 条件 |
|---|---|---|---|
| 新建工单 | 今日/待办顶部唯一主 CTA | `POST /api/tickets` | 完整字段、组织关系、关注人和版本校验通过。 |
| 编辑可变字段 | 工单详情“编辑” | `PATCH /api/tickets/:id` 或 `commands:update` | 仅后端返回的 `allowed_actions`；带 `expected_version` 与幂等键。 |
| 分派/转办 | 详情“转办” | `commands:assign/reassign` | 组织级联、成员范围、责任历史和确认。 |
| 开始/重试运行 | 详情“执行/重试” | `POST /api/tickets/:id/runs` / `POST /api/runs/:id/retry` | 不改变工单完成状态。 |
| 验收完成 | 详情“验收完成” | `commands:complete` | 验收证据、版本、权限、审计。 |
| 取消/重开 | 详情“取消/重开” | 正式生命周期命令 | 原因、版本、权限、审计；重开生成新事件，不覆盖旧完成事实。 |

### 5.3 今日与待办排序

继续遵守 **`Today ⊆ OpenTodos`**：今日只是开放工单的服务端投影，不复制记录。

建议服务端排序键如下，且返回每一项的 `membership_reason`：

1. `waiting_approval` / `waiting_external` / 逾期（需行动）
2. 今日到期或已开始且未完成
3. 高风险、高优先级
4. 正在运行且需要人工补充/确认
5. 线索、谈判阶段的业务优先级
6. 截止时间、创建时间、稳定 `ticket_id`

“今日”最终成员谓词、时区、无期限任务和逾期升级仍以版本化业务规则发布；本方案只实现承载、解释和排序，不擅自开启 SLA/升级。

## 6. 业务分类：线索与谈判主要阶段

现有 `kind` 是技术票型（跟进、履约、风险、审批等），不能替代业务阶段。本方案新增独立业务分类，默认映射关联 Collaboration 的正式阶段码。

### 6.1 首批分类映射

| 一级业务分类 | 主阶段码 | 典型工单 |
|---|---|---|
| 线索 | `INITIAL_CONTACT`、`INTERESTED`、`EVALUATING` | 首触、回复跟进、画像补全、合作评估、风险澄清。 |
| 谈判 | `QUOTE_PENDING`、`NEGOTIATING`、`PLAN_PENDING`、`CONTRACTING` | 询价、报价确认、商务条款、方案确认、合同跟进。 |
| 履约（数据兼容保留） | `SAMPLE_PENDING` 至 `PUBLISHED` | 寄样、测试、内容、审核、发布。 |
| 结算（数据兼容保留） | `SETTLING` | 发票、结算、付款证据。 |
| 异常 | `exception` | 暂缓、争议、拒绝、流失、取消。 |
| 通用/待归类 | 无有效阶段或无 Collaboration | 仅在明确原因下使用，进入数据质量队列。 |

员工端 Home 首期重点提供**线索**和**谈判**分组；任务中心和报表保留全部分类，避免将现有履约/结算工单静默丢失。

### 6.2 分类变更原则

- 关联 Collaboration 的阶段变化不会直接完成或取消工单。
- 已发布规则可将“阶段变化”作为更新同一开放工单分类、创建候选或创建工单的依据；每次记录规则版本和来源事件。
- 手工覆盖分类须说明原因并保留原阶段映射，避免篡改业务事实。
- 无关联 Collaboration 的工单不得虚构阶段；展示“待归类”及缺失字段。

## 7. 事件 → 工单 → 自动流转

### 7.1 事件成单管道

```text
权威业务事件
  → 去重、来源版本与范围校验
  → 匹配已发布的 Event-to-Ticket Rule
  → 规则评估记录（命中 / 跳过 / 缺字段 / 不可执行）
  → 单事务：ticket + basis ref + lifecycle event + assignment + watcher + outbox
  → 独立 Worker 执行后续运行
  → 工单时间线、今日/待办、报表、管理审计刷新
```

同一事件按 `source_event_id + rule_id + rule_version + business_scope` 去重；命中已有开放工单时，规则可定义“补充依据/更新下一步”而非重复建单。模型建议只能创建候选，不能绕过规则或人工采纳直接创建正式工单。

### 7.2 初始规则模板（先草案/模拟，确认后发布）

| 事件类型 | 预期工单分类 | 预期动作 | 默认自动状态 |
|---|---|---|---|
| 已验证的邮件回复/承诺 | 线索或谈判（由关联阶段决定） | 创建或更新跟进工单 | `pending_assignment` 或 `assigned` |
| 报价、合同、样品、内容期限事件 | 谈判或履约 | 创建期限跟进工单 | `pending_assignment` |
| 已识别风险事件 | 风险票型 + 对应业务分类 | 创建风险处置工单 | `pending_assignment` |
| 审批要求或资料缺失 | 审批/跟进 | 创建待补充或待审批工单 | `waiting_approval` / `waiting_external` |

上述模板先在管理端显示**规则预览与模拟结果**；规则经发布后可按规则中明确的组织、主受理人/协同受理人和状态流转策略自动执行。任何 L3 外发、合同/费用/阶段审批、取消、重开与验收仍须人工确认并留回执。

### 7.3 工单状态机

```text
新建 / 待分派
  → 已分派
  → 处理中
  → 等待外部回复 / 等待审批 / 待补充
  → 待验收
  → 已完成

任意非终态 ──取消（原因）──> 已取消
已完成 / 已取消 ──重开（原因与权限）──> 待分派或已分派
```

- 自动化只可处理已发布规则允许的确定性转换，例如“事件满足条件后创建待分派工单”“人工接受后进入处理中”。
- 发送邮件、运行完成、收到模型结果、关闭会话均不等于工单完成。
- 任何因规则或 Worker 触发的状态变化都记录：执行身份、规则 ID/版本、输入事件、幂等键、范围快照和回执。

## 10. API 与迁移合同

### 10.1 新增/升级读取接口

| 接口 | 关键能力 |
|---|---|
| `GET /api/ticket-form/bootstrap` | 当前可见三级组织树、可受理成员、创建人上级预览、分类/阶段字典、组织版本、缺失数据提示。 |
| `GET /api/tickets?view=assigned|created|watching|completed&category=&stage=&org_unit=&assignee=&cursor=` | 工单中心服务端授权筛选与稳定游标分页。 |
| `GET /api/tickets/:id` | 工单详情、来源依据、责任/关注关系、组织版本、验收、运行摘要、allowed actions、missing fields。 |
| `GET /api/tickets/:id/timeline?after=` | 工单生命周期、业务事件、运行摘要的统一可续接时间线。 |
| `GET /api/ticket-reports/*` | 本人/组织/阶段/规则报表；明确统计口径、范围、as_of。 |
| `GET /api/admin/work-orders/*` | 治理、规则模拟、数据质量、发布历史、组织级报表。 |

### 10.2 写入接口

| 接口 | 关键约束 |
|---|---|
| `POST /api/tickets` | 创建正式工单；组织、受理人、自动关注人、来源、分类、验收条件、`expected` 输入版本和幂等键均由后端校验。 |
| `PATCH /api/tickets/:id` | 仅允许可编辑业务字段；禁止直改终态、受理历史、生命周期事件和验收事实。 |
| `POST /api/tickets/:id/commands` | `assign`、`reassign`、`accept`、`complete`、`cancel`、`reopen` 等受控命令；版本、幂等、权限、事件与审计在同一事务。 |
| `POST /api/admin/ticket-rules/*` | 草案、模拟、发布、停用、回滚；发布为 L3 治理动作。 |

所有读取返回 `request_id`、`as_of`、`schema_version`、适用的 `source_refs`；所有写入返回正式 `ticket_id`、版本、事件 ID、规则/组织版本和可安全展示的回执。

### 10.3 PostgreSQL 原生持久化交付

本项目已有 PostgreSQL、Outbox 和 BullMQ 方向的基础能力；本方案要求完成其**单库收敛**，而不是继续维护“SQLite API + PostgreSQL 翻译桥”的双语义路径。

| 交付项 | PostgreSQL-only 方案 | 禁止项 |
|---|---|---|
| 数据访问层 | 使用原生 PostgreSQL 驱动/Repository，参数化 SQL 与明确事务边界；SQL 以 PostgreSQL 语法编写。 | SQLite SQL 转译、同步桥模拟、`rowid`/`NOCASE`/SQLite 触发器依赖。 |
| 模式版本 | `schema_migrations` 记录顺序版本、校验和、执行者、执行时间；迁移只向前追加，支持预检与受控回滚脚本。 | 进程启动时隐式 `CREATE/ALTER`、按 SQLite 库形状猜测迁移。 |
| 事务与并发 | 工单、事件、分派、关注者、规则评估、Outbox 在单个 PostgreSQL 事务中提交；领取队列使用锁定与租约。 | 跨数据库补偿、文件锁、应用内存作为唯一幂等/锁状态。 |
| JSON 与检索 | `jsonb` 保存证据和来源快照；常用筛选建立表达式或 GIN 索引；长文本详情按需读取。 | 将全量大 JSON/审计 payload 透传进列表和报表。 |
| 本地/CI | Docker Compose 或临时 PostgreSQL 服务，迁移后跑 API、Worker、Outbox、故障接管和性能测试。 | SQLite 单测替代 PostgreSQL 集成验收。 |
| 历史数据 | 不保留、不迁移、不归档 SQLite 数据；工单系统只使用已在 PostgreSQL 中的权威数据和后续写入。 | 应用运行时读取 SQLite、数据库故障时回退 SQLite、保留 SQLite 数据迁移窗口或归档副本。 |

**部署门禁：** 发布前必须执行 PostgreSQL migration 预检与备份校验；应用、Outbox publisher、execution workers 均只接受同一 `DATABASE_URL`。任一服务未连上 PostgreSQL 时保持不可用/不领取作业，绝不改用本地数据库继续运行。

## 11. 分期执行与验收

### P1 — 工单表单与三级组织基础

1. 先完成 PostgreSQL-only 基座：移除 SQLite 运行时选择和 SQL 方言翻译路径；以受控 migration 建立 `schema_migrations`、原生 PostgreSQL Repository、开发/CI PostgreSQL 环境和发布预检。
2. 建立组织投影、组织版本、成员/负责人/user 映射校验与数据质量接口。
3. 建立 `ticket_assignments`、`ticket_watchers`、`ticket_basis_refs`、业务分类和阶段字段。
4. 交付 `TicketFormDialog`，替换 Home 今日/待办的编辑弹窗；普通编辑不再包含状态单选。
5. 新建/编辑/转办均带版本、幂等和审计；自动关注人由服务端解析。

**验收：** 全部新旧工单 API、Worker、Outbox 和测试只连接 PostgreSQL；中心→部门→组→受理人级联正确；创建人上级自动显示且可回放；未配置组织/上级不伪造成单；运行成功不完成工单。

### P2 — 工单中心与分类报表

1. `/tasks` 按工单中心重构：我创建、我受理、我关注、我已完成、授权范围。
2. 上线线索/谈判分类与阶段映射；兼容履约、结算、异常与待归类数据。
3. 交付详情中的依据链、责任/关注、运行、产物、验收、审计入口。
4. 交付员工个人和组织工单报表，先只展示已定义的原始口径。

**验收：** 同一 `ticket_id` 能从 Home、任务中心和报表回查；多页无漏项；员工看不到越权组织/人员；报表数字与列表同源。

### P3 — 事件转工单与规则化流转

1. 建立事件→规则评估→工单的事务链、去重键与回放记录。
2. 先交付规则草案、模拟和数据质量报告；经确认后发布首批线索/谈判规则。
3. 按已发布规则开启事件自动建单、更新或转入人工队列；不自动验收。
4. 引入确定性工单状态机及回滚/重开轨迹。

**验收：** 同一事件重放不重复建单；规则版本可回放；规则停用立即停止新自动动作；失败/缺字段进入人工队列并可审计。

### P4 — 管理治理与运营闭环

1. 建立 `/admin/work-orders`，增强概览、调度、审计之间的工单治理关联。
2. 交付规则发布/停用/回滚、组织/上级缺失监控、规则命中率与人工覆盖报告。
3. 完成员工与管理端的 RBAC、移动端、键盘、读屏、200% 缩放、真实 PostgreSQL/Redis/Worker 故障注入验证。

**验收：** 管理端能调查和治理，但不能旁路业务审批；员工端只显示自身可执行动作；所有自动行为均有规则、事件、组织和回执证据。

## 14. 实施进展（2026-10-03）

### 已完成的 PostgreSQL 原生链路

- 追加 PostgreSQL-only 核心引导迁移；全新空库可依次建立 `tickets`、`task_events`、`execution_jobs`、`execution_outbox`、组织投影与正式工单领域表，不依赖 SQLite 快照建表。

- `POST /api/tickets` 已在单一 PostgreSQL 事务内创建工单、三级组织范围、主受理人、直属上级关注、来源引用、不可变 `task.created` 事件、审计事实和幂等回执。

- `PATCH /api/tickets/:id` 已仅允许待受理工单编辑业务字段，并在同一 PostgreSQL 事务写入版本、不可变 `task.updated` 事件、审计事实和幂等回执；Home 不再调用旧任务编辑写入。
- 正式完成/取消命令采用 PostgreSQL 行锁、版本冲突、幂等回执、验收快照与审计事实；运行成功仍不等于完成工单。
- Worker/Outbox 的 PostgreSQL 原生作业仓储、租约和终态写入已接入调度执行链路；迁移后的 PostgreSQL 集成测试覆盖建单、编辑、生命周期、回执重放及组织质量读取。
- Cron 运行时的 `cron_jobs`、`cron_runs`、`execution_worker_heartbeats` 已纳入 PostgreSQL 增量迁移；系统作业种子、人工/到期运行入队、过期接管、运行状态、执行作业与 Outbox 手递均在原生 PostgreSQL 事务中完成。
- 调度管理 API（作业/运行读取、创建、修改、手工运行、内部 tick、执行作业管理读模型与低风险失败重投）已改为 PostgreSQL 原生查询；管理读模型固定声明 `postgres_redis_bullmq_multi_worker`，不再提供 SQLite 运行模式。
- 已以全新 PostgreSQL 库验证完整迁移链，并新增原生 Cron 集成测试，覆盖系统种子、到期/人工入队幂等、Outbox 手递、调度管理读模型和人工低风险重投。
- 工单已提供主受理人的显式 `accept` 命令，以及创建人发起的 `assign` 转办命令；二者均使用 PostgreSQL 行锁、版本校验、幂等回执、不可变生命周期事件与审计事实。转办会保留原主受理人记录为 `superseded`，不覆盖责任历史。
- 已提供创建人添加/移除协同受理人的 PostgreSQL 原生命令；协同人进入“我受理”和授权详情范围，但不会获得主受理、验收或重开权限。跨组协同必须说明原因，变更与撤销均增加版本、生命周期事件、审计及幂等回执；员工详情可查看当前协同受理人并由创建人发起受控变更。
- 员工端任务中心已显示 PostgreSQL 详情中的当前责任/关注、来源依据与验收事实，并接入明确“受理工单”和“提交验收完成”入口；受理后仍需单独提交验收证据，不能把运行或受理本身视为完成。
- 创建人可通过明确原因重开已完成工单；重开会移除 `ticket_acceptances` 的当前投影，但会将每次验收永久写入 `ticket_acceptance_history`，再次验收使用新版本，历史事实不被更新或删除。
- 已提供 PostgreSQL 原生的个人授权工单原始计数报表；响应显式标识 `as_of`、时区、个人授权范围和来源，不包含 SLA、绩效、排名或生产率推断。
- 已提供 PostgreSQL 原生的组织授权工单原始计数报表：范围只能由已绑定组织负责人向下展开，或由已绑定公司管理员按其公司范围展开；不接受浏览器自报的公司/组织筛选，不暴露员工排名、SLA 或绩效指标。工单治理页展示状态与受理组织分布；员工工单中心仅在当前账号具备组织负责人或公司管理员范围时显示同源汇总，普通员工不因无权读取而看到组织数据。
- 正式工单现使用独立的 PostgreSQL `ticket_accounts` 与 `ticket_auth_sessions`，支持首个管理员 setup、登录、登出、Cookie 会话；账号与受控组织人员的绑定只能由管理员以原因发起，并写入不可变 `ticket_account_organization_bindings` 审计，绝不从显示名或历史 SQLite 用户猜测映射。
- 员工 `/tasks` 已先通过明确的“正式工单 PostgreSQL 身份”门禁再读取工单；管理端“工单治理”已使用同一管理员会话，展示未绑定账号和受控人员，并通过有原因的确认绑定表单调用审计命令。该页面不复用历史工作台会话作为工单授权。
- 新增 `KOL_RUNTIME_MODE=postgres-only` 正式启动模式：入口动态加载仅含 PostgreSQL 的 HTTP 应用，启动前校验正式 schema 并播种已发布的系统 Cron 作业；只挂载工单身份、`/tickets`、Cron 与调度运维端点，历史 `/tasks`、首页、邮件等路由不装配并返回 404。Cron 的可见性、修改权限、人工执行和风险读取也已切至正式工单身份与 PostgreSQL 工单投影。
- 已补充 [`docs/POSTGRES_ONLY_OPERATIONS.md`](../../POSTGRES_ONLY_OPERATIONS.md) 运行手册，明确环境校验、schema、HTTP/Outbox/Worker 启动顺序、tick 健康检查、账号绑定以及“绝不自动回退 SQLite”的故障边界；本次未进行任何生产切换。
- 已完成一次运行时依赖审计，详见 [`docs/POSTGRES_ONLY_RUNTIME_AUDIT.md`](../../POSTGRES_ONLY_RUNTIME_AUDIT.md)：正式工单/执行/Cron 原生子链已可在空 PostgreSQL 库验证，但 HTTP 启动、旧 `/tasks` 与首页等仍含 SQLite-shaped bridge，不能把整个历史应用宣称为 PostgreSQL-only。
- 已追加 `scheduling_rule_simulations`、`scheduling_rule_audit_events` 和规则命令回执；管理员可在 `/admin/scheduling` 创建仅限人工确认的规则草稿、对当前版本正式工单进行只读模拟、引用该模拟发布或停用版本。历史版本“回滚”只会复制为新的草稿版本，必须重新模拟后才能发布，不能重新激活旧行或复用旧模拟。发布要求版本、幂等键、审计原因和同内容指纹的成功模拟。
- 已追加独立且不可变的 PostgreSQL `ticket_business_events`：仅接收已核验的首批邮件回复/承诺、报价/合同/样品/内容期限、风险、审批或资料缺失事件。已发布规则必须显式声明 `trigger_event_types` 才会参与评估；评估写入规则版本、范围、事件、工单快照和 `matched/skipped/missing_fields` 回执。管理端可人工登记受控证据事件并查看建议；关联工单的授权员工可在详情和时间线读取安全摘要与证据引用。此链路**不**自动建单、分派、升级或改变工单状态。
- 已提供按规则版本聚合的 PostgreSQL 原始计数报表：展示评估次数、去重事件、关联工单及 `matched/skipped/missing_fields/failed`。管理员可对单条 `matched` 建议形成不可变的确认或驳回事实，报表据此显示待审/确认/驳回覆盖；**确认事实不触发执行器**，不伪造命中率、业务执行成效、SLA 或绩效结论。
- 已提供复用组织负责人/公司管理员授权范围的分类与阶段当前存量报表，管理端展示分类、阶段和状态原始数量；它不是漏斗转化、停留时长、SLA、绩效、成交或收入报表。

### 当前仍在推进的范围

- **全局 PostgreSQL-only 收敛：** 正式工单/调度已有独立的 `postgres-only` 运行模式；旧任务、发现、邮件、会话及部分管理读模型仍仅存在于历史兼容应用，必须继续迁移或正式退役，不能作为正式模式的生产回退路径。
- **工单中心完善：** PostgreSQL 详情读取已提供来源依据、受理历史、关注关系、验收证据、运行摘要和审计索引；员工端详情抽屉仍需完整呈现这些分区并补充产物链接与报表入口。
- **全应用身份切换：** 员工工单中心与工单治理页已具备原生身份入口；其余历史工作台仍由旧登录域保护。后续需将可保留的页面迁到原生身份或在 PostgreSQL-only 部署模式下明确退役，不能混用两套会话。
- **Cron 业务处理器收敛：** `overdue-scan` 与 `daily-task-snapshot` 已改为只读取 PostgreSQL 正式工单投影；Cron PostgreSQL 仓储不再导入旧 Cron store。`ownership-release`、邮件记忆与 AI 处理器因其业务仓储尚未原生化，已改为显式 `needs_takeover`，其中两个已发布系统写入作业会通过 migration 停用，防止其隐式触达 SQLite。后续需按领域完成原生仓储后重新走规则发布，而不是直接恢复旧处理器。
- **P3/P4 治理：** 已交付规则草稿、模拟、发布、停用和“历史版本恢复为新草稿”的技术闸门、首批已核验事件的无副作用评估记录、规则成效原始计数、不可变人工确认/驳回事实以及分类/阶段当前存量报表；但 Event→Ticket 自动执行器、阶段流转漏斗和停留时长口径仍未上线。个人与组织原始计数、受理/转办/协同受理/重开已上线，但仍需补更细的管理授权与协同处理语义。

> 本记录不将历史 SQLite 兼容层标记为验收通过。生产发布前，所有进入正式工单与调度路径的服务必须仅以同一 `DATABASE_URL` 运行为前提。
