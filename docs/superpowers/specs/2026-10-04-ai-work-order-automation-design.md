# AI 工单自动化设计：任务为目标，工单为标准化执行单元

**日期：** 2026-10-04  
**状态：** 阶段 A（单一工作台身份）、阶段 B（Task → Work Order 原生模型）、阶段 C 的 Jev **影子判断**、A1/A2 的受控物化器及工作台/治理端只读投影已实现并通过 PostgreSQL 集成验证；生产业务事件尚未接入异步自动建单管道，A3 自动阶段推进未启用
**适用范围：** KOL 工作台、PostgreSQL 工单/调度子系统、Jev 判断、今日任务、我的待办、管理端工作战报  

> 本设计纠正此前“将正式工单直接当作任务中心的替代品”的错误分层：**工作台账号和登录继续是唯一入口；PostgreSQL 只承载新的业务事实、工单和自动化，不再出现第二套工单登录。**

---

## 1. 业务对象的正确层级

用户确认的产品语义如下：

> **任务（Task）颗粒度更大，是一个可持续推进的业务目标；工单（Work Order）颗粒度更小，是围绕该目标生成、可标准化、可分派、可执行和可验收的一次具体动作。**

因此，不能再把“任务”“工单”“一次运行”当成同一个实体。

```text
业务对象 / Collaboration / 项目 / KOL
  └─ 任务 Task（一个业务目标，可跨多个阶段持续存在）
       ├─ AI 工单 Work Order #1（标准模板：核验 KOL 资料）
       │    ├─ 分派 / 协同受理 / 自动填充内容
       │    ├─ 运行、产物、回执
       │    └─ 验收或退回
       ├─ AI 工单 Work Order #2（标准模板：回复后跟进）
       └─ AI 工单 Work Order #3（标准模板：报价期限跟进）
```

| 对象 | 回答的问题 | 粒度与生命周期 | 是否可由 AI 自动生成 |
|---|---|---|---|
| **任务** | “这项业务目标为什么存在、整体现在卡在哪里？” | 大；可跨线索、谈判、履约、结算等多个阶段 | 可由已发布规则创建或补充，但不因一次运行成功而完成 |
| **AI 工单** | “现在应该由谁按哪个标准动作处理什么？” | 小；一个标准模板的一次实例 | 可以。由事实 + 已发布规则 + Jev 受控判断决定 |
| **执行作业** | “一次系统运行有没有执行、产出什么、是否失败？” | 更小；一次可重试的运行 | 可自动发起；成功不等于工单验收或任务完成 |
| **业务事件** | “外部世界发生了什么可验证事实？” | 不可变事实 | 不由模型伪造；来自邮件、期限、履约、人工核验等权威来源 |

### 1.1 对现有实现的影响

当前代码中有两条历史语义混在一起：

1. 工作台旧 `tickets` 投影实际承担了“任务 / 待办”的角色；`GET /api/workbench/tasks` 以 `owner_user_id`、优先级、期限、风险等生成 Today / Todo。
2. PostgreSQL 原生 `tickets`、责任、验收、运行和规则链当前被实现为“正式工单”。

这两个对象不能继续互相替代。新的落地不新建第二套“任务列表”，而是：

- 保留**任务**作为今日任务、我的待办、任务中心和工作战报的顶层业务对象；
- 新增或明确**工单是任务的子实体**，以 `task_id` 关联；
- 工单的分派、阶段、运行、验收只影响其父任务的“进度 / 阻塞 / 下一步摘要”，不直接覆盖父任务的业务目标；
- 当前 PostgreSQL `tickets` 物理表可在迁移中继续保留，但其产品语义收敛为 Task 根记录；新标准化工单使用明确的 `work_orders` 关系表，避免继续用名称和行为混淆的“第二种 ticket”。

这不违反“不新建第二套真相”的原则：`work_orders` 不是复制任务，而是任务的必需子关系，类似“订单”与“订单项”的关系。

## 2. 与工作台登录的关系

### 2.1 明确禁止第二套身份域

此前 `ticket_accounts` / `ticket_auth_sessions` / `TicketIdentityGate` 让用户在已登录工作台后仍需创建“首位工单管理员”，这是错误的产品行为，必须废弃为正式路径。

目标行为：

```text
工作台已有登录会话
  → 认证中间件取得可信 workbench_user_id / 角色 / 公司范围
  → PostgreSQL principal 映射（服务端、可审计）
  → 读取任务、工单、规则和报表
```

- **前端不出现第二个账号、密码、首次管理员设置或工单登录页。**
- 不从浏览器显示名猜测 PostgreSQL 身份；后端只接受已经验证的工作台会话主体。
- PostgreSQL 中维护 `workbench_principal_bindings`：`workbench_user_id` → `principal_ref`、组织范围、生效期、映射原因和审计。
- 该绑定是 PostgreSQL 的授权事实；旧工作台会话只作为一次请求的可信认证载体，不成为工单数据的读写库或回退库。
- 无绑定时返回工作台内的“尚未配置工单权限”提示，由管理员在原管理端完成绑定；绝不跳转至新的密码页面。

### 2.2 管理端与员工端边界

| 入口 | 处理对象 | 不做什么 |
|---|---|---|
| **今日任务 / 我的待办** | 当前用户需要推进的任务；展开显示阻塞或下一张可执行工单 | 不显示规则配置、模型 trace 或全员队列 |
| **任务中心** | 任务列表、任务详情及其 AI 工单时间线 | 不成为第二个管理员调度台 |
| **管理端工作战报** | 任务存量/流入/完成、工单负荷、自动化命中、例外和数据质量 | 不替员工批量处理任务 |
| **调度治理** | 模板、规则版本、Jev 决策、失败回放、熔断与发布治理 | 不直接改写业务事实或绕过验收 |

## 3. PostgreSQL 领域模型

### 3.1 任务与工单关系

新增下列 PostgreSQL 原生关系；所有写入均在单一事务内完成，并与 Outbox 同提交：

| 表 / 关系 | 核心字段 | 目的 |
|---|---|---|
| `tasks`（第一阶段复用现有 `tickets` 物理表） | `task_id`、目标、对象、阶段摘要、状态、负责人、任务版本 | 顶层业务任务；唯一的 Today / Todo / 战报主对象 |
| `work_order_templates` | `template_code`、版本、输入 schema、字段填充规则、验收条件、自动化等级 | 定义“标准化工单是什么”，而不是让模型临时发明工单类型 |
| `work_orders` | `work_order_id`、`task_id`、`template_code/version`、状态、阶段、优先级、期限、`automation_ref` | 一个任务下的一次具体标准动作 |
| `work_order_assignments` | 主受理人、协同受理人、路由规则、跨组原因、有效期 | 工单级责任；不覆盖任务业务责任 |
| `work_order_basis_refs` | 业务事件、邮件、期限、KOL、合同、人工输入的引用、版本、摘要哈希 | 每个自动填充和自动推进都能回放依据 |
| `work_order_decisions` | 输入哈希、规则版本、Jev 模型/版本、选择、置信度、理由、结果 | 不可变 AI 决策账本 |
| `work_order_stage_events` | 前阶段、后阶段、执行主体、规则、证据、人工覆盖原因 | 阶段轨迹；不更新或删除历史 |
| `work_order_command_receipts` | 幂等键、命令、版本、结果 | 抗重复投递与可安全重放 |

首期不迁移任何 SQLite 历史数据。新任务、工单、规则、映射、事件、运行和报表均只写 PostgreSQL。

### 3.2 工单状态与任务状态

- 工单可有：`proposed`、`assigned`、`accepted`、`in_progress`、`waiting_external`、`waiting_approval`、`ready_for_acceptance`、`completed`、`cancelled`、`needs_review`。
- 任务状态是聚合结果，而不是工单状态镜像：`open`、`blocked`、`in_progress`、`waiting`、`ready_for_review`、`completed`、`cancelled`。
- **一个工单完成不自动完成任务。** 只有任务的完成条件满足，且规则或人工验收明确提交后，任务才完成。
- **一个任务可有多个未完成工单，但必须有明确“当前阻塞工单”或“下一步工单”。**

## 4. Jev 在 AI 工单中的正确职责

Jev 适合做**受限枚举判断和概率输出**，不适合直接拥有数据库写权限、任意挑选员工、凭空填业务事实或直接完成任务。

当前代码已有三类可复用基础，但职责不同：

| 已有模块 | 现状 | 在新设计中的作用 |
|---|---|---|
| `tasks/openai-intent.ts` | Jev 在已有任务目录中做 bounded choice，并有置信度阈值 | 抽取为通用“受控选择”调用器；不能直接用它的旧 task type 当工单类型 |
| `host/kol-jev-assessment.ts` | 对公开 KOL 资料做潜力/风险建议，且仍依赖旧 SQLite 路径 | **不复用为自动建单逻辑**；它只能提供非决定性的 KOL 评分参考 |
| `stage-judgment.ts` | 基于正文、附件、履约事实的确定性证据权重，能阻止感谢、延期、跳档等错误推进 | 作为 Jev 的硬校验器；Jev 与证据规则必须一致才可自动推进阶段 |

### 4.1 Jev 判断请求：只允许选择已发布项

每次 AI 工单决策使用一个独立、可测试的 `JevWorkOrderJudge`，向 Jev 提供已脱敏、有限长度、可追溯的结构化事实，并仅提问以下有限集合：

```text
1. candidate_template_code：从当前范围已发布模板中选择，或 no_action
2. action：create | merge_open_order | update_next_step | advance_stage | needs_review | no_action
3. routing_policy_code：从当前范围已发布的路由策略中选择，或 needs_review
4. stage_action：保持当前阶段 | 允许的相邻下一阶段 | needs_review
```

Jev 返回每项的 `choice + confidence + probabilities`。它**不返回自由文本员工姓名、任意 SQL、任意状态、金额、合同事实、联系方式或未经事实支持的字段**。

### 4.2 自动填充：模板和证据优先，不让模型编造

工单字段分为三类：

| 字段类别 | 填充方式 | 是否允许 Jev 参与 |
|---|---|---|
| 事实字段 | 来自已验证业务事件、Collaboration、KOL、期限、组织和用户映射 | 只能选择 / 提取已出现的值，并保留 `source_ref` 与片段 |
| 策略字段 | 模板版本、优先级、期限计算、验收条件、受理组、路由策略 | 纯确定性规则计算 |
| 叙述字段 | 标题、背景摘要、建议下一步 | 可由 Jev 生成，但必须可标记为 AI 建议；不得作为事实、阶段或验收依据 |

例如“收到已验证报价期限”事件可自动生成：

```text
模板：quote_deadline_followup.v1
标题：报价期限跟进 · {KOL} · {截止日期}
目标：在期限前核实报价与下一步商务动作
主受理人：路由策略 quote_owner → 当前公司/对象责任人
期限：事件期限或模板 SLA（必须标明来源）
验收条件：报价事实已核验、下一步已记录、必要审批已完成
依据：event_id、邮件/附件版本、Collaboration、规则版本
```

标题、目标、期限、受理人和验收条件都不需要让模型“猜”。Jev 的作用是判断“是否适用该标准模板 / 是否应合并既有工单 / 是否需要人工复核”。

### 4.3 自动分派：Jev 选路由，规则解析具体人

“自动分配指定人”必须是自动化，但不是模型随意指定人：

```text
Jev：选择已发布 routing_policy_code = quote_owner
规则解析器：quote_owner → 对象责任人 → 受理组候选 → 负载与在岗校验 → 指定 principal_ref
PostgreSQL 事务：写主受理人、协同受理人、路由版本、解析链和原因
```

只有策略解析得出**唯一、有效、处于授权范围的具体人**时才自动分派。否则工单进入 `needs_review` 或 `pending_assignment`，并记录缺失原因；不会凭姓名相似或模型文字猜人。

### 4.4 自动阶段推进：Jev + 证据规则双重闸门

可自动推进的条件必须全部满足：

1. 工单模板的已发布规则明确允许该阶段转换；
2. Jev 对 `stage_action` 的置信度达到政策阈值（首期建议 `>= 0.92`）；
3. `stage-judgment.ts` 返回相同的建议阶段、`auto_propose=true`，且无阻断标记；
4. 只允许当前阶段到图中**相邻**下一阶段，不允许跳档；
5. 引用的是已验证业务事件或履约事实；
6. 不是外发、审批、合同/费用、取消、重开或验收等 L3 动作；
7. 规则、模板、组织/人员映射在执行时仍为已发布且有效。

任意条件失败，记录 `needs_review` 决策，不更新阶段。

## 5. 自动化级别与人工边界

用户已确认“自动分派、自动推进与人工确认并存”。因此每一条已发布规则必须声明 `automation_level`：

| 等级 | 行为 | 示例 | 是否自动执行 |
|---|---|---|---|
| A0 | 仅观察 | 记录事件、生成候选 | 否 |
| A1 | 自动生成草稿 | 生成模板、补齐可验证字段 | 是，但工单仍 `proposed` |
| A2 | 自动创建并分派 | 低风险跟进、资料核验、期限提醒 | 是；必须满足阈值、路由和去重 |
| A3 | 自动更新下一步 / 单步阶段 | 已验证回复进入“待回复跟进”、已验证资料进入“资料核验” | 是；必须通过双重闸门 |
| L3 | 高影响动作 | 外发、合同/费用、审批、取消、重开、验收 | **永远人工确认** |

这意味着“自动化”覆盖建单、分派、填内容和可逆的正常阶段推进；但不把模型判断扩展为不可逆的对外承诺、费用、合同、取消或验收。

## 6. 事件到 AI 工单的事务管道

```text
权威业务事件
  → 事件规范化 / 去重 / scope 校验
  → 查询已发布自动化规则与模板
  → Jev bounded judgement（模板、动作、路由、相邻阶段）
  → 确定性证据、组织、路由、阶段图校验
  → 生成 immutable decision（无写业务状态时也保留）
  → 单一 PostgreSQL 事务：
       task / work_order / basis refs / assignments / stage event /
       decision receipt / audit / execution outbox
  → BullMQ Worker（如规则要求后台动作）
  → 工作台任务聚合、任务中心、战报、管理审计
```

### 6.1 幂等与合并

- 业务键：`scope + source_event_id + rule_id + rule_version + task_id`。
- 若同一任务已有匹配的开放工单，规则必须显式指定 `merge_open_order`、`update_next_step` 或 `create_new_order`；默认不得重复建单。
- 同一事件重放只能重放同一决策回执，不能生成第二张工单。
- 规则停用、模型不可用、低置信度、来源缺失、人员无效或冲突时不降级为无审计直写；统一成为可追踪的 `needs_review`。

### 6.2 决策审计字段

每次自动或人工覆盖决策至少记录：

- `rule_id`、`rule_version`、`template_code/version`、`routing_policy_code/version`；
- 事件与对象引用、规范化输入哈希、使用的数据版本；
- Jev 模型名、模型版本、问题版本、各 choice/probability/confidence；
- 阈值、阶段证据判断、被拒绝的闸门及原因；
- 创建/更新/跳过/合并结果、工单 ID、Outbox ID、操作者或系统主体；
- 人工确认、覆盖、撤销或重试的原因与时间。

## 7. 今日任务、我的待办与工作战报

### 7.1 今日任务 / 我的待办

前端不切换到独立“工单登录”或独立首页。工作台继续显示**任务**：

- 一条 Task 只出现一次，不为子工单复制多条大任务；
- 卡片显示：业务目标、当前阶段、总工单数、阻塞工单、下一张建议工单、主受理人、最近自动化决定与期限；
- “我的待办”按当前用户作为任务负责人、工单主受理人、协同受理人或待人工确认人进行聚合；
- “今日任务”是“我的待办”的子集，新增原因码如 `work_order_due_today`、`work_order_blocked`、`review_required`，继续由服务端计算；
- 点击任务打开任务详情，内部显示工单列表及每张工单的来源、状态、负责人、产物和验收；点击某工单才进入该工单的标准操作抽屉。

### 7.2 管理端工作战报

工作战报必须区分任务与工单，不能把工单量伪装成业务成果：

| 战报维度 | 统计对象 | 可显示的原始指标 | 不可推断 |
|---|---|---|---|
| 业务目标进度 | Task | 新建、开放、阻塞、待确认、完成、取消、阶段分布 | 成交、ROI、个人绩效 |
| 执行负荷 | Work Order | 创建、自动分派、人工接管、等待外部、待验收、完成、超期提示 | 自动化“成功率”等同业务成功 |
| 自动化治理 | Decision / Rule | 命中、自动执行、被人工确认/驳回、跳过、去重、失败、熔断 | 模型正确率（除非另行发布标注口径） |

所有列表、汇总和报表以相同 PostgreSQL `task_id` / `work_order_id` 范围过滤，带 `as_of`、时区、规则版本和授权范围。

### 阶段 B：建立 Task → Work Order 原生模型

1. **已完成：** 追加 PostgreSQL migration：模板、工单、工单责任、依据、决策、阶段轨迹、回执、任务根回执、索引和不可变 decision / stage event trigger。

### 阶段 D：受控自动建单、填充与分派

1. **已完成模板治理：** 管理端可新建模板草稿、发布、退役旧发布版本和停用；发布时强制校验 A1/A2/A3 所需触发事件、验收条件、路由与阶段策略。已发布模板才可被 Jev 影子判断选择，且界面明确标识“自动执行未启用”。
2. **已完成受控物化器：** 已发布 A1/A2 模板仍需独立的自动化 release（状态、理由、最低置信度、路由策略和不可变启停审计）。物化器只消费不可变 decision；在同一 PostgreSQL 事务写 Work Order、依据、`task_owner` 主受理、阶段事实、物化尝试和 `work_order.materialized` Outbox。重复 decision / idempotency 不会重复建单；无 release、低置信、无效 Task 或不支持/非唯一的路由只写可审计的 `skipped`。
3. **已完成 decision → Worker 异步管道：** Jev 决策写入后以 `work_order.materialize` execution job + PostgreSQL Outbox 交给 BullMQ Worker；Worker 仅调用既有确定性物化器，返回 `skipped` 也保留终态回执。重放决策复用同一 job/outbox，不能重复建单。当前事件入口仍是管理员受控的 Jev 评估 API，尚未接入邮件/期限等生产事件生产者，因此不宣称任意生产事件已自动建单。
4. **已完成基础投影：** 工作台任务中心与工单治理页显示 Task 根、子工单数量、阻塞与责任/决策事实；当前治理页仅输出原始负荷，不将工单量或工单终态误报为任务完成或绩效。工单接管、修订、关闭和事件触发来源仍待后续命令与异步管道。

## 9. 首期验收标准

以下全部通过前，不发布任何自动化规则：

1. 已登录工作台的用户访问任务中心、定时任务和 AI 工单时，**不出现第二套账号、密码或首次管理员页面**。
2. 每张 AI 工单恰好关联一个 Task；同一业务事件重放不会创建重复工单。
3. 自动生成的标题、内容、期限、责任和验收条件可定位到模板、事件或确定性路由；模型没有生成未提供的金额、合同、联系方式或人员。
4. 自动分派只能通过已发布 routing policy 解析到唯一有效主体；无解时进入 `needs_review`。
5. 自动阶段推进必须同时通过 Jev 高置信和 `stage-judgment` 的证据闸门，且仅允许相邻阶段。
6. 运行成功、邮件发送成功、模型响应成功都不会自动验收工单或完成任务。
7. Today、Todo、任务中心、管理端战报对同一 `task_id` / `work_order_id` 的数量一致，且全部使用 PostgreSQL 权威读模型。
8. PostgreSQL 集成测试覆盖并发幂等、规则停用、模型超时、无权限、组织变化、重复事件、人工覆盖和 Outbox 重试。

## 10. 非目标与禁止项

- 不再创建、维护或展示独立工单账号体系。
- 不让 Jev 自由选择人员、创造工作流阶段、编造事实或直接写数据库。
- 不将 KOL 潜力/风险评分当作建单、分派或验收的唯一依据。
- 不把 AI 建议、运行成功、邮件发送或会话结束当作任务完成。
- 不在未发布、未模拟、未通过范围和阈值闸门的情况下启用自动建单、自动分派或自动推进。
- 不从 SQLite 读取、迁移、归档或回退任何新 AI 工单领域数据。
- 不在本设计阶段自动部署或开启生产自动化开关。
