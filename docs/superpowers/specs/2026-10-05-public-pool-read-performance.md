## 实现契约

- `GET /api/home/pool` 使用原生 PostgreSQL 异步连接池，要求配置 `DATABASE_URL`；无 SQLite 回退、远程 MCP 调用、模型调用或正式写入。
- 输入：`query`（最长 200 字符）、`filter=all/new/overdue`、`sort=score/followers/ingested-asc/desc`（另接受 `default`）、`offset`、`limit`。默认 50 条，最多 100 条；未知值返回 400。
- 输出：公开 `items`、同一 SQL 快照中的 `library` 与 `page={offset,limit,total,matched,new_count,next_offset}`。删除重复的 `kols` 数组；总数在公开主页去重后计算，筛选不只作用于当前页。
- 搜索支持员工实际看到的状态与指标文本；公开主页去重、资料完整度优先与前端原有口径一致。排序增加稳定 ID 兜底。
- PostgreSQL 一条查询统一产生页面、总数、筛选数、新建联数与同步状态。返回数据有界，但计算精确统计仍需读取授权公海集合；不是仅扫描 50 条的查询。
- 通过 `023_public_pool_read_indexes.sql` 与 schema migration 账本加入公海查询索引、最近释放历史的部分覆盖索引。
- 前端上一页/下一页、全选本页；跨页与筛选保留已经选择的分析对象，仅保留选中对象的离页快照。搜索防抖；过期请求不能覆盖当前请求。
- 领取、撤销领取、同步、头像维护、评分和清理后重读分页端点；强制刷新使用新的请求代次，避免共享写入前尚未完成的读取；末页删除导致空页时退到最后有效页。失败如实展示，不将命令成功等同于读成功。
- 公海重试不先加载整个 board。首页运行任务轮询的首次读取也按已有首屏让位延迟执行；父壳在公海懒加载时等实际读取开始再计时，避免模块尚未加载就先读侧栏。
- `Cache-Control: no-store`；`Server-Timing: pool_read` 提供读取耗时。保留动态权限检查，未新增 Redis 或浏览器结果缓存。

## 验证与限制

隔离 PostgreSQL 16，独立临时端口与克隆测试库；未对生产数据执行写入、发送、解密或采集。

性能夹具：2,000 条公海画像、6,000 条已释放历史。同一机器先移除新增释放历史索引测旧全量查询，再应用 migration 测新分页。最终实现复测：旧查询约 1,398.4ms；旧查询仅补索引后约 40.3ms；新查询五次为 55.8、38.0、36.2、37.3、46.5ms，中位数 38.0ms。旧列表重复返回的未压缩 JSON 为 2,960,950 字节，新首屏为 37,412 字节、50 条。主要数据库收益来自释放历史索引；分页降低传输、解析与渲染负担；异步访问降低该端点自身对主线程的阻塞。这是本地夹具结果，不是生产 p95 或实际用户点击耗时。

目标与证据：此夹具的新首屏仓储读取目标为 200ms 内、最多 50 条，验证达到目标。生产仍需测浏览器首字节、下载、渲染与并发负载；旧端点的同步阻塞仍可能影响同一后端进程。

续查生产（2026-10-05）：仓库脚本指定 ECS 的 `lingong` 服务运行中，环境文件配置 PostgreSQL 与 Redis。在 `BEGIN READ ONLY`、10 秒查询超时内，仅统计公司公海并测原有 SQL：115 条公海档案、2 条释放历史；尚无本次新增索引。原有 SQL 五次为 21.79、6.85、5.88、5.29、5.34ms，原始行 JSON 为 158,890 字节。这表明大数据夹具中的 1.4 秒瓶颈不能作为当前生产慢的直接证据，当前用户等待的主要环节仍需接口排队、网络与渲染测量确认；已有 PostgreSQL，并非缺少该数据库。此次检查没有改动生产代码、索引或服务。

验证资产：`backend/tests/public-pool-page.test.ts`（真实 PostgreSQL：边界、分页、跨公司排除、领取排除、最新释放、筛选、主页去重、显示指标搜索）；前端 `kolContract` / `poolView` 契约测试；`home-pool-pagination.spec.ts` 与 `home-pool-follow.spec.ts`（模拟响应的浏览器交互）。后端类型检查、前端构建、契约与 registry 校验另执行。

最终结果：新 PostgreSQL 分页测试与前端契约测试共 21 项通过；公海浏览器回归 19 项通过（关闭重试），首屏请求顺序、分页与慢响应覆盖三个场景各连续运行三次，9 项全部通过（关闭重试）。续查已将 `kol-memory` 的 DNS 与现有模拟 fetch 一起设为确定的测试夹具，并增加私网 DNS 解析不执行 fetch 的回归，`kol-memory` 24 项与分页 6 项合计 30 项全部通过。前端构建、后端类型检查、contracts 与 registry 校验通过。未宣称完整发布门禁通过。

门禁差异：此前两项头像回归因真实 DNS 失败，现已通过测试夹具修复，头像生产代码未改。TB 绑定仍缺远端字典及邮箱品牌 TB，独立校验退出非零；但当前 `.github/workflows/release-gate.yml` 明确对该项使用 `continue-on-error: true`，且配置登记为 advisory，所以它不阻止该 GitHub 发布流程。`backend/scripts/release-gate.mjs` 的 production 档仍将其计为失败，两种门禁口径有差异。没有修改 TB 规则或用其他品牌回退，也未将单项检查冒充完整发布通过。

## 发布步骤

1. 在目标 PostgreSQL 执行 `npm run db:apply:postgres-schema`，确认 `20261005_public_pool_read_indexes` 登记；使用已有部署流程执行 migration，避免在查询请求里建索引。
2. 配套部署前后端。旧客户端可读取 `items`，但旧公海客户端不能完整展示分页全集，不能仅部署后端。
3. 检查 `Server-Timing` 与浏览器请求/渲染、领取后的页数及总数；核对 PostgreSQL 执行计划和新增释放历史索引使用情况。
4. 如果数据库已更换或权限撤销，继续以现有登录与执行边界核验；此变更不承担全局登录数据层迁移。
