# AI 发现确认后的真实状态修复

需求：员工确认采集后仍显示等待确认。主责：后端专家负责作业终态与回执，前端专家负责呈现服务端确定状态。

审宪：CONST-03 要求确定状态由程序执行；CONST-05 保留 L3 确认；CONST-08 留审查证据；CONST-10 不以预测结果冒充执行能力。基本法依据：TECH-FE-03 状态与恢复、TECH-BE-02 统一提交闸门、TECH-BE-03 并发幂等与回执、TECH-BE-04 持久作业、TECH-TEST-03 发布证据；工具风险按 07-mcp-data-contract 的 MediaCrawler 异步作业契约；DESIGN §1 的真实等待不变量。

结论：符合。生产只读检查发现本次确认已入队，但因 runtime_probe_crawl_busy 被拒绝，未取得 task_id；此前作业远端返回 timeout，监控遗漏该终态，持续保留单任务锁。界面仍优先显示模型提交前的待确认描述。

实现：在匹配 remote_task_id 后将 timeout/timed_out 记为失败并释放单任务占用；服务端投影动作与执行回执状态，界面刷新并替换当前任务的旧结果展示，历史消息不改写。已知启动前忙碌拒绝可重新提出待确认请求；不自动执行，不把 uncertain 当作可重启依据。重试保留原始任务归属，并使用新的执行标识与确认卡。任务标记完成仍是独立动作。

验证：增加超时与锁释放、忙碌拒绝重新提议但未确认不调用远端、队列不再显示待确认、刷新后恢复拒绝状态等回归。生产回执与部署结果在发布完成时核验；本轮不启动新采集。
