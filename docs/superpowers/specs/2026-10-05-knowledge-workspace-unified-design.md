# 管理侧知识工作区统一设计与接口衔接审查

日期：2026-10-05。状态：详细设计；已做仓库静态核查，尚未修改运行代码、数据库或生产流程。本方案以本次用户给出的十项方案为目标，现有实现只作为事实证据。

## 1. 设计结论与审查记录

采用「全局导航不变 + 中栏筛选 + 右栏原位切换」。右栏同一时间只展示列表、详情、编辑或审批发起中的一个任务；不常驻第四栏，不再上下堆叠列表与详情。

两类知识共用宿主、基础信息、生命周期展示、操作栏、审批发起和反馈。差异收敛到内容展示、内容编辑、材料快照和加工适配器。共用交互不代表把 PDF 加工伪装成结构化保存，也不代表抹去审批与发布的独立副作用。

### 1.1 两类对象的准确划分

用户末句两次写「结构化」，不能据「未分类」「IPD」确定类型。仓库真实分支为：

| 维度 | 真实含义 | 设计使用方式 |
|---|---|---|
| `family/domain/base` | 业务族、业务域、知识库 | 中栏筛选与基础信息；分类不授予权限 |
| `base.kind` | `structured/unstructured` | 内容模型、目标库校验 |
| 在线条目的 `kind` | 模板、提示词、术语、问答、政策、方法等 | 专有字段及正文渲染 |
| `asset_type=document` | PDF 文件对象 | 文件编辑、原件、真实加工记录 |
| 类型目录的 `structured=false` | 没有专有字段，正文就是内容 | 仍可能是在线条目，不自动等同于 PDF |

所以「未分类」条目也可以是在线结构化知识，「IPD」下也可以有非结构化文件。不得以分类名、标题或文件名猜内容模型。本方案同时覆盖这两条真实链路；若截图中的两个对象都是在线条目，则都使用在线内容适配器。

## 2. 静态核查：现有前后端链路与差距

以下路径以仓库根为基准，均为实施资产证据。

| 功能 | 前端与真实接口 | 后端事实 | 对目标的影响 |
|---|---|---|---|
| 主页 | `KnowledgeHome.tsx` 并行获取 adminKnowledge、bases、domains、documents | 在线与 PDF 两个列表源 | 目前浏览器合并、筛选、算计数、分页；并非统一服务端列表契约 |
| 右栏 | `LibraryPane` 与 `DetailRail/DocumentRail` 同时渲染 | 无后端依赖 | 当前正是列表在上、详情在下，需互斥渲染 |
| 列表分页 | `PAGE_SIZE=5`，数组 slice | adminList 先查结果再切片；PDF 列表不支持统一分页 | 固定五条与目标工作区容量不匹配；合并分页和计数需同源 |
| 上下文 | filters/page/selectedId 为组件 state | 无对应持久上下文 | `revealCreated()` 清空 query/scope/brand/stage；离开宿主会丢上下文 |
| 在线新建 | `CreateKnowledgeDialog` → POST `/api/admin/knowledge` | 默认草稿；服务仍接受输入 status | 新建缺少 `StructuredFields`，专有必填字段难以完成；要限制创建接口只能生成草稿 |
| 在线编辑 | `EntryView` → PUT `/api/admin/knowledge/:id` | editKnowledge 每次 current_version+1，保留 prev.status 与 published_version；没有预期版本参数 | 文案说新版本草稿，返回状态可能仍是 published；并发与审批冻结需补齐 |
| 在线审核 | `DetailRail/EntryView` → POST `/:id/approve` | approveKnowledge 直接写 published 和 published_version | 不是通用审批发起；没有独立 approved-awaiting-publish 生命周期 |
| PDF 上传 | `UploadDialog` → POST `/api/admin/knowledge/documents`，FormData `file/base_id/draft=true` | 保存原件草稿 | 已支持批量、部分成功、余项重试；必须保留 |
| PDF 编辑 | `DocumentRail` PUT `/documents/:id/draft-file`，`file/updated_at`；POST `/:id/revision` | 替换与新版本校验已有后端服务 | revision 使用 `window.location.assign`，整个页面重载会丢列表上下文 |
| PDF 加工 | POST `/:id/start/retry/cancel`；GET `/:id` | 实际作业、进度与错误 | 可复用，依旧独立于保存和审批；不得造百分比 |
| PDF 新审批 | GET `/:id/publication-v2`；POST `/check/prepare/submit` | 原生 PostgreSQL；材料指纹、流程版本、确认、幂等与回执 | 当前关联 documentId，不能直接用于在线条目；共享类型同样限定 documentId |
| PDF 历史审批 | `LegacyPublicationPanel` → `/publication/review-check/review-prepare`、`/approvals/v2/commands` | 旧表、知识库流程绑定、allowed_actions；有 `/publication-execute` | 必须兼容已有实例、原件和回执，不能以新版空记录覆盖 |
| 审批→发布 | migration 025 的两条审批联动分支及两个处理器 | approved 进入执行作业；新服务 approved 分支更新文档 published；旧立即发布只是提前执行已排队作业 | 加一个发布按钮不能保证等待发布；后台仍会发布，必须改服务端契约 |
| 状态展示 | PDF `publication_label`；在线只读 row.status | PDF 加工 pending_review 可同时表示待提交、审批中、审批通过 | 不能再直接把 pending_review 当审批中，也不能靠标签驱动权限 |
| 组织 | PDF 审批走 reviewApi 的 `X-Review-Company`，普通 API 独立 request | documents 列表按用户可访问组织给标签；部分文档路径另核验组织 | 需统一显式当前组织，并验证列表、数量、详情、原件都是同一范围；静态检查不等于已证实越权 |
| 错误 | reviewApi 把 detail/issue 拼成普通 Error | structuredErrorList 另读结构化错误 | 审批字段失去 path/code，无法可靠定位首个字段；需保留结构化错误 |

补充证据：`frontend/src/api.ts` 的 KnowledgeRow 未声明后端已有 published_version 等关键字段；KnowledgeDocumentDetail 没有统一生命周期、版本 lineage 与允许动作。DetailRail 把版本接口失败 catch 成空数组，EntryView 同样把部分引用加载失败当空结果，应改为可恢复错误状态。

已有员工入口中，邮件模板 composer、问答模板使用 publishedSnapshot。这部分保护应保留，不能因管理页展示最新草稿而改为读取最新正文；还要回归通用查询、技能解析与文件检索，不能由某一入口的保护推断所有入口安全。

## 3. 共用工作区与页面形态

### 3.1 宿主结构

```text
现有全局导航 │ 知识筛选             │ 知识工作区：四态互斥
             │ [固定搜索]           │ [固定任务标题 / 返回入口]
             │                      │
             │ 业务族、业务域、库   │ 列表 OR 详情 OR 编辑 OR 审批发起
             │ 品牌、阶段、类型     │ 这里是唯一的右栏正文滚动区
             │ 生命周期筛选         │
             │ [筛选独立滚动]       │
             │                      │ [详情/编辑/审批固定操作栏]
             │ [上传文件][新建知识] │
```

列表不自动进入第一条详情；列表页无生命周期操作栏。点击条目后列表从右栏退出，详情占满剩余面积。中栏搜索、分组和固定底部不随四态切换卸载。底部上传、新建均用次要按钮：有当前任务主按钮时整个视口仍只有一个实底 CTA。

### 3.2 四态规格

| 形态 | 顶部 | 主体 | 底部 |
|---|---|---|---|
| 列表 | 数量与现有分页 | 平面两行记录；标题最多两行；类型、状态、日期紧凑 | 无额外统计或操作面板 |
| 详情 | 返回列表、真实标题、当前查看版本、生命周期状态 | 基础信息 → 内容 → 审批 → 来源与版本 → 辅助记录 | 按服务端允许动作组织 |
| 编辑 | 返回列表、编辑当前草稿的标题及版本 | 共用基础字段 + 对应内容编辑器 | 取消编辑、保存；未保存提示在操作附近 |
| 审批发起 | 返回当前知识、提交当前标题及版本 | 固定关联材料 + 现有流程字段 + 发布说明 + 实际预检结果 | 返回详情、提交审批 |

详情信息不重复堆叠：标题区展示状态/版本，来源区保留来源、更新时间及历史记录入口，不再重复一个「当前版本」字段。生命周期区保留「未发布版本不参与员工问答」，不是新说明模块。

列表同名条目保持可辨识状态；必要时在已有元信息中带版本，不通过标题名去重。完整标题既支持 hover，也支持键盘焦点获取；详情无截断。

### 3.3 路由与上下文

复用 `/admin/knowledge`，通过查询参数表示工作区模式与对象，例如 `mode=detail&assetType=document&assetId=...&version=...&reviewCompany=...`。URL 编码筛选及页码；长内容、文件、审批表单值不进 URL。旧 `?document=id` 和 `/entries/:id` 兼容解析进同一宿主，catalog/bases/ingest/bindings 旧入口保持可达。

宿主内状态分为：

- 列表上下文：query、family/domain/base、品牌/阶段多选、kind、lifecycle、页码及已有页容量、筛选分组折叠、选中对象复合键、列表 scrollTop、焦点条目。
- 当前知识：`assetType + assetId + version`，当前组织、服务端最新 revision。
- 阅读位置：按对象与版本保存 scrollTop、折叠区状态和内容锚点。
- 编辑缓存：初始快照、当前表单、dirty、字段错误、待上传文件、批量队列、审批发起字段。

URL 与 history.state 保存可重建导航；sessionStorage 可保存非敏感阅读上下文，必须按组织/身份分区并在切组织或退出时清理。敏感正文与 File 保持在当前宿主内存；不承诺刷新后浏览器能恢复未上传文件。

返回列表原样恢复筛选、页码、scrollTop、选中项与焦点。若新建或发布后当前记录不再匹配筛选，留在该知识详情，原筛选不变；返回列表展示实际结果，不清空条件强行定位。被删除后恢复最近有效页和相邻项；页数减少才夹取到最后有效页。

进入编辑、切知识、切组织、全局离开、浏览器返回统一走 dirty 守卫。只有内容变化才提示「保存后离开 / 放弃修改 / 继续编辑」；审批字段未提交同样保护。已保存知识不会因取消审批发起而丢失。重新加载只更新服务端快照，不覆盖 dirty 表单。提交期间锁住重复执行和冲突导航，不能发起第二个动作。

## 4. 功能与生命周期设计

### 4.1 在线知识编辑

新建和修订使用同一个编辑器，不再出现新建无专有字段、修订才有字段的差异。字段包括现有标题、类型、库分类、品牌、语言、标签、适用阶段、类型专有字段与正文；已有 subject/body_en/placeholders 等按类型映射并保留，未知 structured 扩展字段也不能因保存丢失。

知识库与 kind 兼容校验复用配置目录，服务端终审。未明确选库时沿用现有合法默认库，但编辑页必须显示实际目标库；不得显示选中 IPD 却静默保存到无关默认库。切 kind 前暂存各类型输入，只提交当前模型认可的字段；会丢失字段时说明具体影响。

已发布知识点击「创建新版本草稿」先创建明确草稿版本，再进入编辑；当前版本与 effectiveVersion 分离。保存草稿保留当前草稿身份并提高编辑 revision，审计保存变更；不能每次保存伪装为新一次审批，也不能复用旧审批。历史回滚继续表示「以历史版本生成新草稿」。

### 4.2 PDF 编辑及内容准备

保留 PDF 选文件、拖拽、批量队列、文件大小、库选择、格式/空文件校验、部分成功与余项重试。每个文件仍形成独立知识，不批量合并审批。批量保存期间逐文件展示真实结果，结束后进入最后一条成功知识详情；队列结果保持可访问，不把失败文件当成功。

现有后端支持的是 PDF，界面继续明确 PDF；不因按钮叫「上传文件」宣称支持 Word、图片等。保存只保存原件草稿，不开始解析。加工 start、cancel、retry 与草稿保存是独立动作；展示 normalize/index 真阶段、实际 done/total、尝试次数、错误及恢复入口。

文件详情集中为「文件图标 + 实际文件名 + 查看原件」，不插大段留白。解析预览、产物、原件来源、加工记录仍可展开。处理中/异常自动展开对应作业记录；自动刷新不抢阅读位置，无 total 时只显示阶段文字。替换已审批材料必须创建新版本，审批原件保持不可变。

PDF 现有上传 API 没有独立品牌、阶段等元数据写入契约。因此第一版展示实际库继承范围；若需像在线条目一样编辑这些字段，应先补后端元数据与索引范围契约，不能放一个保存无效的表单。

### 4.3 统一审批发起

从当前已保存版本点击提交审批，右栏切为审批发起，不要求用户再挑知识。服务端提供对象名称、版本、材料指纹、当前组织、可选已发布流程、现有实际表单字段及可提交原因；单一已绑定流程直接带入，多流程按现行选择规则展示。

复用 `ReviewForm` 和真实流程定义。仅剔除由材料适配器明确承担的关联字段，不能隐藏所有名字类似 knowledge 的字段。发布说明与流程 publication_note 只能有一个编辑源，后端映射，不重复填写。处理人由 check 接口解析，界面不得按组织树猜人。

提交流程：字段输入 → 只读 check → prepare 绑定材料/流程/人员版本 → L3 确认摘要 → submit 携 confirmationId 与稳定 idempotencyKey → 获取审批回执 → 回当前详情。取消确认仍留表单；失效确认重新 prepare；失败保留值，不能回空白列表。

知识页查看关联审批，通过已有集中审批入口处理；评审流程入口只负责配置。没有可用流程时显示真实原因与有权限者的配置入口，不把配置页作为正常发起步骤。没有配置权限者显示联系流程管理员，不给越权动作。

### 4.4 状态及唯一主操作

加工、审批、发布是三个状态轴；页面用服务端计算的 lifecycle 汇总显示，不把原始 status 丢掉。

| 当前条件 | 显示状态 | 唯一主操作 | 其他可用动作 |
|---|---|---|---|
| 未保存编辑 | 编辑中 · 未保存 | 保存 | 取消编辑；其他原有编辑能力 |
| PDF 草稿未加工 | 草稿 · 尚未解析 | 开始解析 | 编辑原件、刷新、按规则删除 |
| 已提交真实加工 | 待加工 / 解析中 / 建索引中 | 无 | 取消加工、刷新 |
| 加工失败或取消 | 加工失败 / 已取消 | 重试加工 | 查看错误与原件 |
| 内容准备完毕且可提交 | 草稿 · 可提交审批 | 提交审批 | 修订、按规则删除草稿 |
| 条件不满足 | 草稿 · 不可提交 | 显示禁用主动作及具体原因 | 可修复条件的已有入口 |
| 有活动审批 | 审批中 / 审批受阻 / 待补材料 | 不突出重复提交 | 关联审批、现行允许的补充/撤回/修订 |
| 审批拒绝或撤回 | 已驳回 / 已撤回 | 按后端允许动作修订或重新提交 | 原审批原因和记录 |
| 当前精确版本 approved 未发布 | 审批通过 · 等待发布 | 发布 | 查看审批回执 |
| 已确认派发发布 | 等待发布服务 / 发布中 | 无 | 实际作业及回执入口 |
| 发布失败或不确定 | 发布失败 / 结果待核对 | 允许时恢复发布 | 核对结果；版本不符时新版本重新审批 |
| 当前版本已生效 | 已发布 | 创建新版本草稿 | 刷新、既有停用等维护操作 |
| 已归档 | 已停用 | 按服务端返回，不擅自恢复 | 版本、记录、合法的新版本入口 |

审批中修订、补材料、撤回权限沿用既有流程；若内容实质变化，旧批准不得覆盖。删除只能删允许的未发布草稿：确认展示标题和版本，并说明是否有审批历史；历史生效版本和审批原件不能被知识级 DELETE 连带删除。

### 4.5 显式发布与历史兼容

新增申请按本次方案明确采用 manual 发布模式。审批终态事件只记录批准/驳回/撤回与审批回执；manual 模式 approved 不创建发布作业。用户点击发布，经 prepare、确认、submit 后，才在同一 PostgreSQL 事务内建立正式发布请求、execution_jobs 与 Outbox。

Worker 执行时复核当前发布权限、组织、批准实例、材料哈希、审批版本、当前有效版本和租约。发布成功原子切换 effectiveVersion；旧发布版在新版本准备、审批、发布失败期间继续生效。检索切换失败必须显示真实发布/索引就绪状态，不能提前展示完成。

已有申请不能静默取消或重新解释：为其保留原发布模式、审批实例、作业与回执；已排队/运行的自动作业保持原契约并如实显示「已按原流程进入发布」。仅新申请切 manual；如需转换历史尚未派发申请，应有单独迁移清单、审计与原子防竞态方案。新版页面同时读取两套历史，但写入统一新契约。

迁移必须检查 024/025 既有触发器、新旧两个 worker 及立即发布入口。不能只改 025 主触发器，留下 legacy approved 分支自动发布。已有迁移不改校验和，使用新的增量 migration；确切编号实施时按迁移账本确定。

## 5. 前后端目标契约（以下均为待实现设计）

### 5.1 统一查询投影

建议增加版本化管理工作区查询层，不合并底层内容文件与在线正文存储。列表、详情、允许动作由服务端适配器聚合；前端组件只消费共享 schema。

| 目标接口，前缀 `/api/admin/knowledge/workspace-v1` | 输入与输出 | 要点 |
|---|---|---|
| GET `/assets` | q、family/domain/base、brand[]、stage[]、kind、lifecycle、page、pageSize；返回 items、total、page、pageSize、facets、queryRevision | SQL 权限过滤先于计数/分页；不是取全量到浏览器再授权 |
| GET `/assets/:assetType/:id` | 明确组织、可选查看 version；返回 metadata、content、lifecycle、approval、publication、versions、actions | assetType 为 entry/document；统一来源字段 |
| GET `/assets/:assetType/:id/review-options` | 当前 version；返回已发布流程、字段、带入关联和 blockedReason | 对接现有流程规则和组织，不发明流程 |

列表每行至少返回复合对象键、title、assetType、kind、分类、范围、updatedAt、viewVersion、effectiveVersion、lifecycle.code/label、实际 sourceStatus。facet 的数字与 total 来自同一查询口径；同组候选计数排除本组，跨组同时满足，保留现有语义。排序使用稳定 tie-breaker（对象键），不得把两个不同对象的同名条目合并。

当前品牌/阶段的「全品牌/全阶段」匹配语义保留；未知字段不能在浏览器擅自解释成全范围。分类未归类由服务端明确表示，避免空值与不存在混用。更改上级分类清理失效下级，其他筛选保持。

组织一致性：所有查询/写入显式携带当前组织；缺失、非法组织由服务端明确处理。列表、facet、详情、文件访问、材料读取、命令、后台执行校验同一身份范围。文件链接通过已有受控 company 查询参数或受鉴权读取方式提供，不依赖浏览器普通 a 标签发送自定义 header。

### 5.2 版本与允许动作模型

```ts
type KnowledgeRef = {
  assetType: 'entry' | 'document';
  assetId: string;
  version: number;
  revision: string;
};
type ActionAvailability = {
  id: string;
  visible: boolean;
  enabled: boolean;
  reasonCode?: string;
  reason?: string;
  risk: 'L1' | 'L2' | 'L3';
  requiresConfirmation: boolean;
};
// 详情同时包含 viewVersion、draftVersion、effectiveVersion；
// lifecycle 是服务端投影，原加工/审批/发布状态各自保留。
```

权限不可用的动作是否隐藏，状态暂不可用的动作如何说明，由后端 action 返回；前端只叠加本地 busy/loading/dirty 限制，不据 status 推导业务资格。新模型中的 version 是可审批材料版本，revision 是编辑并发标记，不能混用。

### 5.3 写入与审批命令

新接口名称只是设计建议，落地需统一到共享 schema 与既有网关，不让前端拼任意动作 URL。

| 操作 | 现有复用资产 | 待补契约 |
|---|---|---|
| 在线创建/保存 | create/edit 字段校验、kind 配置、版本快照 | 保存接口强制 draft；expectedRevision；当前草稿更新与新版本创建分离；原生 pg 事务 |
| PDF 上传/替换 | multipart file/base_id/draft；draft-file updated_at | 明确 expectedRevision、目标版本、组织与回执；返回统一对象投影 |
| 创建新版本 | PDF revision、在线历史快照 | 共用 revision-create 语义；expectedEffectiveVersion；同一知识活动草稿约束按现有业务允许口径确定 |
| 加工 | start/retry/cancel | 原作业契约保留，返回作业键与允许恢复原因 |
| 审批预检 | publication-v2/check、review-check | 两类材料适配为 KnowledgeRef；返回字段 issues，不只拼 reason |
| 审批 prepare/submit | 两套确认、review engine、材料指纹及幂等资产 | 共用 command；confirmation 绑定 org/actor/ref/materialHash/templateVersion/values/评审人解析版本 |
| 发布 prepare/submit | 两套执行服务、租约、Outbox、回执 | manual approved 的独立发布确认，发布请求才派发；有效版本 CAS |
| 删除/归档/回滚/复制 | 原有对应业务服务 | expectedRevision、服务端 allowed actions、L3 确认、幂等与审计；不能删历史快照 |

审批 submit 和 publish submit 返回 `receiptId/ref/lifecycle/revision/instanceId/jobId` 等实际产生字段。新接口用共享命名；现有 snake_case/camelCase 在适配层转换，不在页面各自猜字段。

统一 ApiError 保留 `httpStatus/code/message/issues[{path,message}]/requestId/retryable/currentRevision`。字段失败定位首项、保留所有输入；409 显示服务端新版本与刷新/重新确认入口，不自动覆盖；403 撤去已失效动作，防止旧缓存继续读内容；超时且可能已提交时按幂等键查真实回执，不能换键盲重试。

### 5.4 原生 PostgreSQL 变更边界

将本方案涉及的管理查询、在线草稿、版本、审批材料、发布、范围读取及动作校验改用异步 pg 数据访问。新增统一审批关联支持 entry/document，包含材料 ref、业务版本、编辑 revision、原件/结构化内容摘要、审批实例、发布模式、回执。已有文档审批表不强行改为「把正文转 PDF」；适配器生成在线内容快照或固定 PDF 原件快照。

活动申请防重、版本 CAS、批准版本不可变、发布唯一生效版、confirm 单次消耗与 command 幂等均由数据库约束/事务保证。新版本字段扩展需同步共享类型、对象/事件目录、迁移登记及契约测试。未迁移服务不得被声明为已经符合 PostgreSQL-only。

## 7. 视觉规格与适配

### 7.1 数值与配色落地口径

本次用户明确给出正文 14、标题 18、蓝色主操作等建议，现行 DESIGN §5 却要求所有文字 `--ds-font-sm`，§3 规定主行动品牌粉。两者不能同时当成已经生效的同一规格。

本详细设计采用用户本次方案的层级与蓝色主操作作为知识页目标，实施时先在 DESIGN 登记知识管理工作区的限定映射并在 styles.css 维护语义 token；全局导航仍保持原样。不得直接覆盖全局 `--primary`，不得在知识页面硬写色值/字号，更不能把历史 spec 的标题字号覆盖当现行法。

若先交付纯布局步骤，则沿用现行 DESIGN token；交付视觉步骤后才切换限定映射。这是实施顺序，不增加用户审批流程。

| 部位 | 设计目标 | 实施映射 |
|---|---|---|
| 中栏 | 建议区间 220–260，选择已有 260 轨道规格 | 复用 DESIGN §6 的既有宽度规格，新增页面语义 alias 时登记来源 |
| 正文 | 用户建议 14，深灰可读 | 知识正文 token 映射既有 body 字阶；在 DESIGN 登记局部角色 |
| 辅助文字 | 用户建议 12–13 | 知识 metadata 映射既有 helper/sm，日期不弱到不可读 |
| 详情标题 | 用户建议 18，中等字重 | 映射既有标题档并核对实际定义；DESIGN 局部允许后使用 |
| 分区标题 | 用户建议 14，中等字重 | 与正文同档，靠字重/间距区分 |
| 控件/筛选行 | 使用现行 32 高度档 | `--control-h-lg/form`；筛选选项紧凑列表 |
| 圆角 | 控件 6，必要容器 8 | `--radius-control/card`；详情分区不用圆角框 |
| 右栏内边距 | 使用已有 space-5 | 工作区统一对齐线，不层层累计 padding |
| 字段/分区间距 | 字段 space-2/3，分区 space-4 | 不硬编码用户建议区间内的任意数字 |
| 工作区背景 | 浅色白底，深色随偏好 | `--bg`，不硬写白色；细线 `--border` |
| 选中/hover | 蓝色选中，轻灰 hover | 选中复用 accent 及非颜色标记；hover 复用中性背景 token |
| 主按钮 | 知识页蓝色主行动 | 局部 knowledge-action 职责映射，仍遵循唯一 CTA |
| 状态/危险 | 小浅底标签与文字、危险文字/描边 | success/warning/danger；不靠颜色区分 |

不新增外框、阴影与卡片套卡片。右栏只有任务容器，各 section 使用语义标题、细线和间距。全文与字段网格共用起点，长文件名/长 ID 强制换行，不整栏 overflow-x:hidden 掩盖溢出。

### 7.2 字段、页脚和三轴

内容容器达到 DESIGN 允许的 720 宽度时才启用两列字段，每个字段标签和值同行；长正文、分类路径、适用范围可跨列。480–719 采用单列字段，窄于 480 标签在上值在下。阈值看右栏容器宽度，不能仅看浏览器宽度。

固定操作栏用 flex 最后一段占据实际高度，正文 `flex:1;min-height:0;overflow:auto`，不绝对定位覆盖正文。次要动作靠近主操作，危险动作在另一侧；窄宽度允许次要动作入更多，不藏唯一主操作。编辑页顶部不再另放保存按钮。

宽度轴：桌面三栏；按现行 1100 堆叠断点可将中栏放上方压缩显示，继续保留展开筛选入口；触摸窄宽采用现有导航抽屉和可展开筛选，右栏任务全宽。均不增加常驻列，不重做全局导航。

高度轴：低高度减少装饰性间距、折叠辅助记录；正文继续滚动，页脚完整可点。输入轴：键盘 Tab 顺序与页面一致、返回后焦点回原条目；触摸命中区按既有 44 最小命中规格扩大，不增大视觉控件；关键标题与理由不能只通过 hover 获取。

所有折叠采用可键盘操作 summary/button；失败用 alert，成功/执行用 status。浅/深色对比度按 DESIGN §1/3；减弱动效偏好停用动画而保留状态文字。

## 8. 前端组件分工及反馈

建议保留 KnowledgeHome 作为兼容入口，内部改为 KnowledgeWorkspaceShell。拆出 KnowledgeListView、KnowledgeDetailView、KnowledgeEditor、KnowledgeReviewInitiation、KnowledgeActionBar、useKnowledgeWorkspaceContext。内容层提供 EntryContent/EntryEditor 与 DocumentContent/DocumentEditor；PublicationPanel/LegacyPublicationPanel 的读投影进入同一审批摘要，历史差异藏在 API adapter。

复用 StructuredFields、ReviewForm、VersionDiff、既有 ConfirmDialog；将 CreateKnowledgeDialog/UploadDialog 的内容和队列抽出放右栏编辑，不保留第二套表单。EntryView 的版本/范围/引用/复制/回滚迁到共用详情，旧 route 进入兼容宿主。

保存、提交、发布与恢复操作均有同步锁及 busy 文案，确认打开时底层主按钮降级，失败提示位于当前操作附近。成功按返回 ref/revision 更新详情并使同组织列表/计数缓存失效，不用全页面跳转。审批/加工刷新只刷新对应对象；轮询是观察持久作业，不承担执行时钟。

详情与列表读取失败不展示「无知识」；版本加载失败显示「版本记录读取失败」和重试，保留当前正文。403/404 分别按服务端脱敏信息呈现；不继续显示已撤权的缓存内容。审批轮询应观察 reviewStatus、publicationStatus、jobStatus 和 revision，不能只比较 waiting/published 粗状态。

## 9. 实施顺序与验收

1. 收口共享模型、字段保留清单、当前组织和 action 投影；制定增量迁移及历史发布模式策略。
2. 完成原生 PostgreSQL 工作区查询和在线草稿/材料/版本契约，统一错误；接通两类对象通用审批，移除直接发布旁路。
3. 完成 manual 批准→等待发布→确认派发链路及新旧 worker 闸门，验证并发、历史回执与有效版保护。
4. 完成四态宿主、URL/列表上下文、dirty 保护，迁移编辑器与审批表单；保留既有子页直达。
5. 收口知识页 DESIGN 映射并实施平面列表、字段网格、固定操作栏和三轴适配。
6. 按实际修改运行后端契约/注册校验、typecheck、相关真实 PostgreSQL 测试、前端 typecheck/build 与知识/审批 E2E。设计文档本身不以这些测试冒充已实现。

| 验收场景 | 必须观察到的结果 |
|---|---|
| IPD 与未分类分别含两种对象 | 筛选不决定内容类型；选择适配器正确 |
| 列表→详情→编辑/审批→返回 | 右栏四态互斥；没有上下列表详情、常驻第四列；筛选页码滚动选中恢复 |
| 新建保存不匹配原筛选 | 留当前知识详情，返回仍是原条件；不清空筛选 |
| 在线所有 kind 新建/修订 | 专有字段可填写，后端校验；旧未知字段、原稿、语言/范围保留 |
| 已发布知识生成草稿 | 当前草稿状态与版本明确；旧 effectiveVersion 问答/技能调用继续生效 |
| 同版本并发保存 | 后写明确 409，保留本地输入，不覆盖第一份结果 |
| 两类知识审批发起 | 自动携带当前对象及版本；表单不重复选知识；处理人来自真实预检 |
| manual 申请审批通过，关闭浏览器 | 仍未发布，没有发布作业；只读刷新不产生作业 |
| 明确发布并双击/并发 | 一份正式发布请求、一个作业和回执；材料/授权变化不发布 |
| 旧自动申请、已在队列或运行 | 原实例、作业、原件、回执不丢；不重复发布，不强行变 manual |
| 审批拒绝/撤回/补充/受阻 | 原因和关联入口存在；不当成 approved，不提前生效 |
| PDF 部分上传失败/加工失败/取消 | 成功对象真实存在，余项可重试；真实阶段与恢复动作保留 |
| 失败与确认过期 | 输入保留、首错误定位、重新 prepare；重试复用命令幂等范围 |
