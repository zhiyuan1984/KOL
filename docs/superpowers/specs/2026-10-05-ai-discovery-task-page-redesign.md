# AI发现任务页详细设计（已确认）

日期：2026-10-05。状态：用户已确认；本地实现已验证，未部署或启动真实采集。

## 1. 目标与需求解释

提交后进入可刷新、可恢复、可离开的发现任务页。中栏回答“正在做什么、需要我确认什么”；右栏回答“发现了谁、我如何处理”。

第16、17项合并解释：取消中栏的“返回AI发现”，在右栏顶栏左侧保留唯一的“返回 AI发现”；与下载、复制、打开、分享、切换控件垂直居中对齐。第18项删除“本轮结果”标题及其占位行，不删除结果内容。

本设计只规定平台容器、结构化过程事件和受控操作的展示，不固定模型每次回答的段落、结论或措辞。

## 2. 当前代码证据与待核实问题

- 路由采用 BrowserRouter，已登记 `/s/:id`，Home 提交成功后调用该路径的导航。生产地址仍为 `/` 且全部导航无响应的根因尚未验证；不能仅凭该现象认定为某一种路由故障。
- ChatBlocks 分开渲染 process_trace、operation_trace、结果指针；泛化标签回退为“正在处理这项工作”。分组消息顺序无法保证组内事件的整体时间顺序。
- 过程步骤使用 observed_at，缺值显示“时间未记录”；初始准备条目存在没有步骤时间的构造路径。新的记录需从事件源修复，不能用浏览器当前时间补造历史。
- RuntimeActions 不区分动作是否已执行，固定显示“需确认执行（L3）”，并直接展示进度和回执 JSON。
- 任务页的 DiscoveryRuntimeResults 使用独立简单结果卡；公海 PoolRow 已有可复用的对象卡信息层次。
- 粉丝下限10000、上限2000000在前后端默认模板中同时存在；已读取的现行法规未提供200万上限的业务理由。
- Home discovery 的 follow 接口明确返回禁止创建 Collaboration；忽略有服务端候选状态接口，但前端当前只维护本地 ignoredIds。

上述是本地代码证据，不是对生产根因或能力完成状态的声明。

## 3. 页面结构与导航

### 3.1 页面骨架

```text
左栏导航                 中栏                         右栏
可随时切换               AI发现 · 任务名称             返回 AI发现   ↓ MD  ↓ JSON  复制  打开  分享  切换
                         本次发现条件（可展开）        [红人对象卡]
                         用户提交的要求                [红人对象卡]
                         按时间追加的业务过程流        [红人对象卡]
                         范围确认 / 补充信息卡
                         后续输入区
```

右栏不再增加“本轮结果”及重复的“发现候选”标题行；列表确有需要时用紧凑筛选控件表达筛选，不用标题占空间。状态分别属于过程事件、确认动作与对象卡，不把同一状态重复显示在页头和各栏。

### 3.2 路由与恢复

1. 成功提交后地址明确为 `/s/{sessionId}`；服务端绑定 taskId、sessionId 与发现条件版本。
2. 刷新、直接打开链接、新标签页“打开”都恢复同一个任务，不再创建采集或重复提交。
3. “返回 AI发现”进入 `/?tab=discovery&resume={taskId}`，恢复提交条件并提供继续原任务入口；用户选择重新提交时才新建任务。
4. 左栏所有导航在排队、分析、待确认、采集中都可用；离开页面不自动取消持久作业。
5. 浏览器前进/后退正常工作；路由加载失败显示原因与重试入口，不留不可点击的透明遮罩。
6. 实施前检查生产导航事件、运行错误、加载资源、遮罩命中、地址与组件状态是否一致；部署检查深链是否返回应用入口。

### 3.3 工具条

- 返回入口使用正文语义色 `--text`，浅色下为深色字，深色下随主题适配；文字按钮，无实底。
- 桌面宽度足够时所有控件同一行，垂直居中：返回靠左，其他动作靠右；不把整组水平居中挤在一起。
- 窄右栏保留返回与切换，其余收进“更多”，不缩小字体，不横向溢出。
- `↓ JSON` 属技术导出，沿用显式调试权限可见规则，不新增普通员工默认技术入口。
- 复制、导出与分享需要明确当前对象和范围；无内容时禁用并说明原因。分享继续校验范围与权限。
- 右栏折叠时返回入口仍可达；窄屏堆叠时出现在结果区上方。切换控件沿用当前含义，不更改其业务功能。

## 4. 中栏布局与间距

- 所有任务、过程、确认、分析内容占满中栏可用宽度，仅保留中栏既有内边距；去掉消息容器的独立窄宽度与居中限制。
- 卡片宽度不扩展到右栏；中栏 min-width:0，长文本换行。
- 所有文字用 `--ds-font-sm`；标题靠字重区分。卡片内边距 `--space-3`，标题至正文 `--space-1`，同段字段与连续文字 `--space-1`，不同语义段 `--space-3`，相邻独立卡片 `--space-4`。
- 清除叠加的 Markdown 段落默认 margin、卡片最低高度和空白占位；不通过强行裁切文字压缩卡片。
- 取消“只读分析”作为独立大卡片标题；用风险标签“只读（L1）”标明实际读取性质。结果指针压成一句具体说明。
- 中栏固定头部、单一 feed 滚动区、固定输入区；底部跟随新增内容，用户上滚后停止跟随并出现“有新内容”入口。
- 范围确认卡出现后确保可达；决策后收为真实决策事件，原范围可展开，历史不删除。

依据：DESIGN §1/4/5/6/8/10/11。布局不新增平行字号、色盘或间距档。

## 5. 合并为一条业务过程流

### 5.1 合并与排序规则

准备事件、业务能力调用、模型可公开的分析摘要、确认、采集、筛选、结果发布使用同一任务过程流。取消独立“处理过程”和“正在调用系统能力”两个总容器。

事件至少包含稳定 eventId、taskId、runId、actionId（适用时）、业务标题、状态、发生时间、服务端记录时间、单调序号和必要摘要；原始工具名只在管理员授权的诊断层保留。

- 实时过程按服务端记录序号追加，事件主时间展示真实的服务端记录时间，含秒；跨日加日期，统一 Asia/Shanghai。
- 主时间是事件被记录的时间，不能冒充远端发生时间。正常事件两者接近；迟到事件在流末追加“补充记录”，注明实际发生时间，不插入过去位置打断阅读。
- 同一动作进行中的进度原位更新，保留首次记录时间；完成、失败、取消、重新执行各追加独立事件。不会把早期条目时间改成后续时间而打乱顺序。
- 轮询快照不生成重复事件；重放按 eventId 去重。多个运行以 runId 区分，重试不覆盖上次失败。
- 新任务从“需求已提交”与“正在核对发现条件”开始记录真实时间。历史缺时间只标“历史步骤未记录时间”，不造时间；有序号时依序号恢复，完全没有排序依据的历史归入可展开的“旧任务记录”。
- 不渲染只有时间、没有内容的空行。未知能力用“正在读取发现任务所需资料 · 未提供步骤说明”，保留真实状态并记录展示契约缺口；不能猜成具体的检索动作。

### 5.2 业务标题

| 当前表达 | 新表达原则与示例 |
|---|---|
| 准备任务 | 正在核对发现条件 |
| 正在调用系统能力 | 根据真实动作显示：正在读取公开红人资料 / 正在检查采集状态 |
| 正在处理这项工作 | 根据真实动作说明对象与目的；缺说明时如实说明，不兜底猜测 |
| 正在核对采集范围 | 正在核对本次搜索的平台和关键词 |
| 采集范围待确认 | 请确认本次采集范围 |
| 筛选说明、数据边界 | 合并成“结果如何筛选”，只出现一次 |
| 任务结果已放入结果工作台 | 已取得候选资料，请在右侧查看（有可靠数量时才写数量） |

风险、缺失授权、失败和冲突信息不能因压缩而隐藏。模型正文保留其任务相关内容；以上规则用于结构化标签和重复系统包装，不用前端删改模型结论。

### 5.3 示例

以下仅为结构示意，时间与数量不作为真实运行事实：

```text
10:20:01  需求已提交
10:20:02  正在核对发现条件
10:20:05  请确认本次采集范围
          平台：YouTube

          需要确认（L3）· 确认后启动外部采集
          [确认开始采集] [修改条件] [暂不采集]

10:20:13  采集请求已提交，等待开始
10:20:20  正在搜索相关内容
```

## 6. 确认、采集进度与操作记录

### 6.1 风险语言与状态

风险等级保持可见，业务解释在前：只读（L1）、草稿（L2）、需要确认（L3）。L3 旁显示该动作具体影响，例如“确认后启动外部采集”或“确认后导入正式红人库”。不要求员工从编号理解后果。

| 服务端事实 | 展示 |
|---|---|
| 待确认且未执行 | 请确认采集范围 · 需要确认（L3） |
| 已确认、已入队 | 已确认，等待开始 |
| 外部提交成功 | 采集请求已提交 |
| 采集中 | 正在采集公开资料 |
| 成功终态 | 采集已结束；另行展示结果读取与核验状态 |
| 部分结果 | 已取得部分资料，剩余资料尚未取得 |
| 失败 | 未完成采集 · 具体可读原因与适用恢复动作 |
| 外部结果不确定 | 正在核对是否已提交 · 提供核对入口，不重复发起 |
| 取消/停止 | 分清停止请求已提交与实际已停止，保留已发生动作 |

已经执行的卡片不再显示“需确认执行”。历史风险等级可在操作记录保留。动作失败不能由模型旧文案覆盖真实状态。

### 6.2 业务进度

取消默认 JSON 进度；展示真实可知阶段，例如等待开始、搜索相关内容、读取红人资料、整理候选、读取结果、核对筛选条件。

只有远端确有对应阶段证据才显示；未知阶段写“采集中，采集服务尚未提供详细进度”。不制作虚假百分比或预计剩余时间。

数量点明单位与口径：搜索到的内容条数、取得的红人数、已核验的红人数分别列示；请求的检索数量不当作红人总量或完成分母。无数量时不造0或进度条。

停止、重试遵守现行风险目录；需要确认的操作仍确认。忙碌提示“另一项采集正在进行，本任务尚未开始”，提供刷新状态/稍后重试；不能暗中并发第二项采集。

### 6.3 操作记录

“查看回执”改为“查看操作记录”，默认摘要包含：操作、平台/对象范围、确认人、确认时间、提交时间、实际结果、成功失败明细与下一步。编号可在展开层用于客服核对，不成为主要进度文案。

提交成功、采集完成、导入正式库的记录分别对应不同动作。原始 JSON、堆栈、内部工具名仅在具备权限的显式诊断层可见；业务层不展示技术原文。

## 7. 粉丝门槛

用户已确认：默认粉丝至少10,000，**上限默认值为不限**。条件卡显示“粉丝至少1万”，高级条件提供可选上限；未填写上限必须在数据契约中表达为无上限，不能背后恢复200万或换一个更大的有限值。

“至少1万”定义为 ≥10,000；如果用户明确指定“大于1万”，则是 >10,000，提交与核验要保持同一口径。本方案默认采用“至少”。

取消200万默认上限的理由是当前需求不要求该上限且没有已读取的业务依据。提高下限会缩小可选集合；粉丝更多本身不能证明内容方向、受众地区、近10条播放或合作条件符合本次需求，因此不把粉丝门槛自动越调越高。

必须同步条件模板、输入校验、序列化、摘要、后端核验与导入预览。旧任务保留当时的上下限快照，不静默改写；用户改条件后才形成新版本并使旧确认失效。采集工具不支持粉丝过滤的物理边界继续在确认中说明一次。

## 8. 右栏红人对象卡与三个文字按钮

### 8.1 复用公海卡的呈现

提取公海对象卡公共展示层，发现和公海分别传入字段与动作。复用头像、身份、元信息、公开指标、内容简介、操作区的视觉层次；不把发现候选误标为“在库”“已建联”。

卡片依次显示：

1. 头像与名称、候选/已在公海/我已跟进等真实对象状态。
2. 平台、主页、评分与依据入口；未评分给出真实缺项，不造推荐分。
3. 粉丝、近10条均播、互动率（有可靠数据才显示）、资料取得时间。
4. 内容方向/地区、简短匹配说明；粉丝和均播无法核验时明确标注。
5. 操作：`跟进` `忽略` `加入公海`，均为文字按钮，无实底。

窄栏字段单列；超过一行自然换行。次要评分细项、来源证据、采样情况、缺失资料进展开详情。没有数据的字段不造零值；关键筛选缺失必须明确写无法核验。近10均播不能用任意采样均值替代。

### 8.2 加入公海

打开确认摘要，说明当前红人、平台稳定ID、来源批次、实际将导入的字段及缺失项，风险标“需要确认（L3）”。确认后经正式导入网关执行并保存真实回执。

只导入正式库，不取得个人跟进关系，不发信、不解密、不改变阶段。成功后显示“已加入公海”；已在库时显示真实在库状态，避免重复导入。缺邮箱不自动拒绝导入、不编造邮箱；其他必需条件不满足时由服务端返回原因。

### 8.3 跟进

用户补充（2026-10-05）：**跟进不需走受控领取流程**。撤回先导入公海、再领取的提案。

- 点击“跟进”直接提交独立的跟进动作，不进入公海领取流程、不要求先加入公海；成功后进入“我的红人”。加入公海成功后进入“公海”；失败保留当前任务并说明原因。
- 按钮反馈为“跟进中…”→服务端成功后“已跟进”；失败展示原因并恢复可操作状态，重复点击不得建立重复关系。
- “跟进”和“加入公海”分别记录自己的结果；跟进不暗中导入公海，不发信、不解密、不自动改变正式合作阶段或完成任务。
- 服务端继续校验当前员工、对象范围、允许动作并记录结果。这里的校验是后台执行职责，不是给用户增加领取步骤。
- **用户已确认的业务语义**：归属当前员工，其他员工受排他跟进规则限制。这是有效跟进关系，不是收藏或非排他关注。
- 点击即提交，不再增加领取弹窗。服务端以当前用户和对象稳定ID原子取得允许范围内的排他归属；已归属本人时幂等返回已跟进，已归属他人时拒绝覆盖并返回权限允许披露的原因。授权管理人员的例外访问仍遵守BIZ-03。
- 对未入库候选，跟进关系引用候选稳定身份；不为了跟进偷偷执行正式公海导入。后续显式加入公海需要按真实归属状态处理，不能把已排他跟进对象误报为可供其他员工领取的公海对象。建议跟进成功后将“加入公海”置为不可用并说明“已归你跟进”；回公海属于另一独立动作。

当前Home follow禁止创建Collaboration，不能直接移用为这个新动作。实现需按用户确认的语义定义独立跟进关系及动作契约；不用合作关系冒充跟进。BIZ-05现有“业务认定的建联事件成功后”触发与本次直接点击取得归属存在差距：实施前由KOL业务角色显式记录本次用户决定，发布“发现候选直接跟进”动作的触发、风险及授权规则，并同步受影响契约；不偷偷改法，不再要求用户重复确认已经明确的选择。14天规则的初始计时与无邮箱对象证据口径依现行有效规则核对，缺项由业务角色补齐，不能把点击伪造为有效邮件往来。

### 8.4 忽略

提案语义：这次发现中不考虑该候选，不删除红人档案、不影响公海和其他员工、不等于永久拉黑。

建议按当前员工和当前发现任务持久保存排除状态；本任务刷新和重开保持忽略，新发现任务仍可出现。卡片退出默认列表并取消勾选；提供“已忽略”筛选及“恢复考虑”文字动作。乐观更新失败恢复卡片并显示失败原因。

目前接口没有已核实的恢复能力；需补齐受控候选状态契约和授权校验，不能用前端隐藏冒充持久成功。该动作是任务候选状态变更，风险按发布目录判定，不能以“忽略”文案推断为破坏性删除或擅自降风险。

以上为设计时差距记录；本轮已新增按员工及发现会话限定的服务端 ignore/restore 契约，验证证据见§12。

## 11. 实施与验收

实施顺序：导航故障核查与修复 → 页面容器及工具条 → 统一事件投影与时间 → 确认/进度/记录 → 无上限契约 → 共享对象卡及业务动作。

验收至少覆盖：

1. 提交、直接打开、刷新、返回、左栏切换、浏览器前后退；等待期间可离开且任务可恢复，无重复执行。
2. 正常事件、同秒事件、乱序/迟到、历史缺时间、重复轮询、重连、多个运行；无时间倒置、空行、重复过程块。
3. 待确认、排队、已提交、执行中、完成、失败、部分成功、不确定、取消与停止真实终态；正确区分采集、结果读取与核验。
4. 普通员工无原始JSON或内部工具名；管理员诊断仍脱敏且授权；风险分档、确认与操作记录可达。
5. 无上限、可选上限、10000边界、旧条件快照、资料缺失与近10条样本不足；前后端筛选一致。
6. 单条加入公海、重复导入、缺邮箱、已在公海；跟进独立提交、不经过领取、不自动导入、重复点击与失败恢复；忽略持久化与恢复。需要确认的正式导入未确认零写入。
7. DESIGN多视口矩阵、键盘与触摸、浅深色、200%缩放、减少动效；右栏单列、不溢出、中栏满宽、一视口最多一个实底CTA。

前端夹具验证、真实harness验证、授权外部集成验证分别报告。设计确认不等于启动真实采集或给生产外部写入授权。
