# 本体管理端：目的、现状、产品设计与实施计划

日期：2026-10-17。状态：设计提案，未接生产服务，未创建数据库表。

## 1. 输入、目的与边界

原对话《华为业务对象分层与清单》的可访问用户消息要求：业务族→业务域→业务主题→业务对象；对象下含属性、关系、事件、规则、动作；核实 KOL 项目的真实载体；设计管理端及编辑卡片；视觉与员工端一致，五个维度保留相同左栏与中栏。

原助手正文目前仅返回内容引用，附件未返回。因此本文不宣称恢复原方案，也不宣称拥有华为官方完整分类。业务分类是待业务专家确认的 KOL 提案，不能将“参考华为分层方法”解释为复制华为事实。

目的：让管理者回答“企业有哪些业务对象、它们如何关联、发生什么、受什么约束、允许做什么，以及修改会影响谁”。员工端消费已发布定义与授权动作；管理端维护定义、来源、依赖和版本。管理对象定义与编辑某个真实 KOL 的业务数据分别进入不同流程。

本轮交付：现状证据、产品与交互方案、五维可切换 HTML 视觉原型（含编辑卡片）、实施计划。原型明确为演示，不发送、导入、解密、删除或发布真实数据。用户已补充七张参考图并明确“视觉以这个为唯一标准”；本任务视觉以这些图片为唯一基准，替代此前对齐 DESIGN.md 和 styles.css 的原型方案。

### 优先处理的具体差距

1. objects-registry 中 task/work_item/follow_task 仍引用 work_items；db.ts 已使用 tickets，三表设计文档 §10 也已取代早期镜像方案。读取投影应显式标记过时映射，业务复核后修订目录，不能静默把历史引用当现行表。
2. objects-registry 的 skill_grant 与 user_skill_grants 是历史授权口径；CONST-02/05 及 PROD-PLAT-04/05 已规定 Agent 是人员使用权限锚点。登记为迁移差距，禁止在新管理端恢复独立技能授权。
3. business-events.ts 在目录不存在/损坏时返回 null，未知事件默认警告，strict 才抛错。治理发布及正式写入需明确失败策略，不能把现状宣传为严格白名单。
4. routers/events.ts 传入的过滤器以及 listBusinessEvents SQL 未携带租户/主体/授权范围，business_events 也未见独立 tenant 列。应用存在登录中间件，但登录不等于对象数据授权。完整调用上下文和部署隔离仍需进一步核实；新本体实例预览上线前必须服务端收敛范围，不能依赖前端过滤。
5. KOL 画像目录将 contact_decryption 列在属性中，语义上涉及敏感动作。先显示“待业务复核”，不自行删改定义。
6. 对象的 layer/group 是平台/业务/组织治理分层，不能直接当作业务族/域/主题。关系、规则、动作清单存在，也不代表可编辑注册表和生产执行已经齐全。

## 4. 管理端心智模型与信息架构

心智模型：业务地图定位对象 → 对象工作台管理五维定义 → 变更单审查影响 → 发布版本供员工和 Agent 使用 → 证据追踪。

建议主入口：管理端现有“数据”治理入口下的“本体”，候选路径 /admin/data/ontology。路径为提案，实施时核对当前路由，不随意增加一级导航。

业务族/业务域/业务主题是分类节点；业务对象是可复用定义。建议一个对象一个主分类，其他主题通过引用展示，避免复制定义。组织层级、数据权限和业务分类是三个独立概念。

## 5. 五维内容及编辑卡片

共用：名称、稳定 code、所属对象、说明、来源引用、责任角色、当前版本、状态、变更原因。code 发布后不直接修改；更名显示名与新建类型分开。删除优先停用，保留历史解释能力。表格行操作使用文字按钮；空数据说明“未登记/未接入/无权限/加载失败”的真实区别。

| 维度 | 列表信息 | 编辑卡片专属字段 | 必须校验 |
|---|---|---|---|
| 属性 | 名称/code、业务类型、基础/派生、来源、映射差距 | 类型、枚举/字典引用、空值策略、派生依据、敏感/脱敏声明、物理映射 | 对象内 code 唯一；字典有效；不得直接修改真实档案；敏感读取仍受闸门约束 |
| 关系 | 名称、起点→终点、基数、方向、作用域、事实来源 | 起终对象、基数、反向名称、有效期、关系载体、授权范围依据 | 引用对象存在；不把合作关系和排他跟进混为一体；不自动生成授权 |
| 事件 | 过去式名称、code、对象、生产者、目录实施状态 | payload schema 引用、来源、时间语义、证据/回执要求、幂等策略 | 区分事件定义与历史事实；不能手改历史事件；目录登记不等于已接线 |
| 规则 | 规则摘要、条款、作用域、执行点、版本 | 条款原文/引用、条件和结果描述、冲突策略引用、后端执行点、验证用例 | 沿用正式规则与执行器；不得让浏览器表达式成为权限或审批依据 |
| 动作 | 动作名、R1/R2/R3、副作用、技能绑定、确认/审批 | 输入/输出 schema、Agent→技能→工具依赖、异步契约、幂等、回执/补偿引用 | 风险不得低于工具下限；R3 确认与回执；发送/导入/解密/删除/阶段变更独立 |

动作卡片中采集显示“异步作业”，具备任务 ID、真实进度、取消和重试入口；单任务约束仍由后端执行。原型不触发采集。事件编辑卡片编辑的是事件类型，不是将某次事件改成“已成功”。

编辑卡片按参考图 1 的紧凑独立表单呈现：白色卡片、浅蓝边框、头部标题与关闭、底部取消与蓝色保存；短字段并排、长字段整行。实际操作一次打开一张卡片，保持背景可辨认但不可操作；长内容内部滚动、操作区固定；窄屏单列。ESC/遮罩关闭有脏数据时确认丢弃，关闭后恢复焦点。

## 6. 变更生效流程

拟定定义版本状态：草稿 → 校验通过 → 按适用规则审核 → 待正式确认 → 已发布 → 已停用。校验失败保留草稿和错误，不伪造后续状态。是否需要业务审批由现行适用规则确定；规则空白仅暂停正式生效部分。

保存草稿为 R2，显示“未生效”；正式发布/停用/回滚属于正式写入，按 R3 显示影响范围并确认，保留回执。回滚创建新发布版本引用旧内容，不抹除事件和审计。不自动回滚已发生的业务副作用。

发布前校验：结构与引用完整；code/枚举稳定；数据与执行依赖存在且版本兼容；权限和风险不降级；业务条款有依据；影响的 Agent/技能/流程/视图可列举。影响数必须来自实际依赖图，无法计算时明确未知，不显示虚构数量。

发布时锁定 base_version 与内容哈希；并发冲突返回最新版本和差异，不能覆盖。发布快照、审计、依赖版本同事务或可靠 outbox 提交；运行中任务绑定定义版本，新的任务使用新版本。具体版本兼容策略进入实施规格，由后端评估，不暗改运行中任务语义。

## 7. 数据承载建议（全部为待实施提案）

不把对象实例迁入通用 EAV，不为了管理定义改写业务权威事实源。先对配置和业务载体建立只读投影，再选定唯一的可写定义来源，禁止数据库和 YAML 双向抢写。

建议：现有 YAML 作为首个版本的导入输入；有管理编辑能力后，以版本化定义仓库为唯一编辑来源，配置文件变为受控导出/兼容产物；运行消费者逐批切换，切换前仍以现有配置为现行来源。切换步骤需要明确版本和回退开关，不能在原型中假装完成。

候选逻辑表（最终 DDL 由架构与后端设计）：

- ontology_taxonomy_nodes：分类节点、父节点、层级、业务包、责任与来源；对象分类引用独立保存。
- ontology_object_definitions：对象稳定 ID/code 与主分类，不保存 KOL 实例。
- ontology_definition_versions：租户/业务包、对象、不可变版本快照，内含五维定义和来源、schema_version、base_version、hash。
- ontology_change_sets：草稿、差异、验证结果和适用审核引用。
- ontology_dependencies：版本间依赖和运行消费者引用，支持影响分析。
- ontology_releases：发布快照、确认与审核/审计引用、生效与停用记录。

是否将属性/关系/事件/规则/动作拆成独立物理表，按查询和约束需求决定；不能将上述候选名描述为仓库已有数据表。全局平台定义与租户扩展分层，租户不能降低平台风险下限或改写其他租户定义。

拟定接口：GET taxonomy/objects/object definitions；POST changesets；PATCH 草稿（base_version）；POST validate；GET impact；POST publish/disable/rollback。均属于待建 API；不虚构现有 /api/ontology 接口。实例预览经已有领域读取服务及 PEP 取数，模型不能绕过授权。
