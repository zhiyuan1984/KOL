## 4. 核心实现发现与改造

本节路径和行号均针对附件解包目录；相同路径的工作区代码不一定相同。

### F1 · P0：两套费用规则和硬编码事实参与正式执行

证据：`backend/src/approval/policy.ts` 定义固定汇率与 5000/20000/100000 档；`flow-engine.ts:274` 默认图采用 5000/50000 档；`plan.ts:calculateApprovalPlan` 的默认参数直接使用 EXPENSE_POLICY，正式路由和 flow 解释器实际调用它。policy 的“Stub/offline”注释未构成运行隔离。`snapshot.ts:8` 返回代码内组织人员清单，`inbox.ts:employeeForUser` 按姓名/邮箱匹配身份。

运行复现：同一申请人、CNY 30000，旧计划为品牌负责人 → 部门负责人 → 财务 → 总经理，新默认图缺财务。这里不裁定哪个金额档正确；问题是同一事项存在两个权威口径且都可执行。

改造：统一使用业务发布的 policy_version、organization_version、人员外部 ID 绑定、汇率来源/日期/版本。通用引擎只解释配置；费用模板属于业务包。默认品牌 LT、固定兜底 emp_wang 和“全部 CEO 终审”从内核迁出；缺正式配置明确阻断。旧路径迁为同一服务的适配层。

### F2 · P0：未知身份、未知币种与用户字段能改变审批链

证据：`flow-engine.ts:151` 未匹配申请人时取 org.employees[0]（当前为总经理）；`:165` 任何 plan.blocked 都归为 amountCny=0；`:180` 用户 fields 最后展开，覆盖 amount_cny、brand、region。`org.ts:roleHolder` 对未知 role 落入部门负责人分支，而非报错。

运行复现：30000 元加入 fields.amount_cny=0 后少经过部门负责人；币种 ZZZ 同样进入最低金额分支；不存在的申请人仍可成功解析指定人流程；不存在的 role 被解析成部门负责人。

改造：requester 由服务端登录身份及已授权代申请关系确定，不允许姓名字符串替代身份；计算字段放 system 命名空间，用户字段放 form 命名空间；禁止保留字；费用类型必须有合法金额/币种/汇率。非金额类型不调用费用引擎。未知身份、角色、表达式、币种返回具名错误。

### F3 · P0：列表与通知绕过单据可见范围

证据：`routers/approvals.ts:196` 无参数调用 listTimeoutsFor；`timeout.ts:listTimeoutsFor` 的 userId 未使用，查询所有 pending；`gateway/wecom.ts:249` 全量读取 wecom_cards，路由直接返回。`routers/approval-types.ts:43` 只按 published 筛选，忽略 visibility。app 的全局中间件验证登录，并未替这些查询添加单据范围。

后果：登录不等于有权读取他人审批标题、审批链、卡片正文与 payload。当前代码即可确认对象范围缺失；不把这一发现夸大为已在生产发生泄漏。

改造：查询层共用当前 company/object/participant 可见范围，通知必须经关联审批 JOIN 过滤；超时列表只给允许查看的实例；类型的可见与发起范围结构化，列表、预览、提交都校验。未来抄送权限独立声明，不能直接等同审批权。

### F4 · P0：多类型提交未绑定确认版本，也未实现幂等重放

证据：`routers/approvals.ts:241–300` 仅要求 idempotency_key，创建后 saveCreateReceipt，没有 createReceipt 读取；没有 expected_version、内容指纹比对或 form_schema 验证。旧费用路径有相应版本与重放逻辑。`Approvals.tsx:338` 新路径直接 POST；已成功的 typePreview 在字段变更后未失效。

后果：同键重试仍生成新单；预览甲、编辑乙后可按乙提交而用户仍看到甲链；绕过 HTML 表单即可提交缺必填/非法选项。初次点击提交时才算出审批人，紧接着创建，用户没有机会审阅算出的路径。

改造：共用 prepare → 确认 → commit。prepare 返回规范化表单、审批人、风险、规则/组织/类型版本与不可变确认摘要；commit 绑定身份、范围、摘要和幂等键并在事务中创建回执。相同 key+payload 返回同一实例，不同 payload 返回冲突；不因重试生成新 key。前端每次影响路径的编辑使预览失效，异步预览取消旧请求或按请求版本丢弃迟到响应。

### F5 · P0：转交/加签把“指定人员”当成审批资格

证据：`gateway/wecom.ts:388` transfer 只检查非空和不同人，未知员工也能写入 chain；`:440` countersign 只检查存在、不重复，默认允许；没有模板开关、业务范围和资格校验。`inbox.ts:canDecideCurrent` 人员 ID 等于当前 chain 节点即可决定。UI“加签人仅查看”与插入真实审批链后的行为矛盾。两个路由虽然接收 idempotency_key，却未传递或消费。

改造：服务端提供 allowed_actions、eligible_assignees 与资格解释；必须区分“追加有决定权的审批节点”和“征询意见/抄送”。目标范围、在职状态、利益冲突与代理关系按发布规则复核；转交同步更新通知、计时和责任记录，命令共用版本与幂等契约。

### F6 · P1：多类型和节点语义只完成了部分解释

证据：`routers/approvals.ts:292` 所有类型 kind 固定 expense；`Approvals.tsx:runTypePreview/submit` 只送 fields，不映射顶层 amount/currency；`queue.ts:objectLabelOf` 因 expense 将普通审批渲染为人民币金额。`flow-engine.ts` 每个 approval 只解析一个人，mode 只是结果标签；create-by-type 存 steps 时丢弃 mode，cc 也未存；handler 被塞入相同审批链。`host/approval-fulfill.ts` 的 expense 分支仅返回本地完成信息，不执行请假、付款等独立业务动作。

改造：发布前明确支持矩阵。未实现模式不可配置为可发布能力。建立 node_instance、assignee_task、decision、cc_delivery、handler_execution 等运行实体；类型声明独立业务 kind/action 与 form 字段绑定。批准与后续执行分开存状态，只有真实回执才能显示对应执行成功。费用批准本身不必付款，也不得承诺付款已完成。

### F7 · P1：图验证允许空图和循环“成功”，版本发布不能持续维护

证据：`flow-engine.ts:190` guard 到 50 后跳出，仍追加终审并返回 ok；start 为空直接返回成功。运行复现已确认两者。`approval-types.ts:publish` 只用一组输入 testFlow，不能覆盖所有分支。已发布 PUT 被拒绝（:99）；再次 publish 仅增加同一行 version（:136），没有 fork draft 或版本内容表。

改造：服务端结构校验必须覆盖起终点、节点 ID 一致性、引用存在、可达性、循环、出口完整性、条件语法/字段类型和已实现节点能力。单样本试运行不能代替图校验。发布版本不可变；修改已发布类型时创建下一版草稿，包含基础版本与草稿 revision；发布凭 content_hash+验证报告，重复发布同一内容不产生伪版本。旧实例冻结所引用的定义与政策，当前人员资格仍须实时复核。

### F8 · P0/P1：超时 handler 存在，但自动化闭环不完整

证据：`cron/handlers.ts:113` 不使用 ctx 的身份/范围；`:123` 提醒只 markReminded，注释明确通知后续接；`:160` transfer 无预期版本；`:163` trackTimeout 删除旧记录并以默认参数重建，丢失 escalated、auto_action、auto_at 与自定义期限。扫描没有比对记录的 node_index 与当前节点；`:191` 未实现的 approve/reject 也清除计时记录。`handlerContract:389` 没有该 handler 条目。全局搜索仅出现类型联合、回执名称、handler 映射三处，不足以证明已注册每五分钟持久调度。

改造：先支持已发布授权范围内的提醒、升级、人工接管；不擅自启用自动批准。计时绑定 instance/node/assignment revision/policy_version，过期任务明确 skipped；扫描只处理服务身份授权范围，原子领取与幂等。升级保留策略与历史，新增下一计时事件，不覆盖历史证据。通知采用持久 outbox+真实投递回执，失败可重试；暂不支持的策略发布时报错。补 seed/启停/取消/失败恢复/运行审计与监控入口。

### F9 · P1：设计器与发布测试不能保证“所见即所发”

证据：`ApprovalTypes.tsx:184` NodeEditor 更新父 editing；`FlowCanvas.tsx:106` 仅节点 ID 集合变化才重置内部 hist。属性修改不改变 ID，下一次拖拽会把旧 state 回传覆盖父节点属性；切换同 ID 节点集合的类型也有风险。`ApprovalTypes.tsx:122` 试运行只传类型 ID 和测试值，后端读取数据库旧 flow；修改后未清 testResult。publish 也只读取已保存内容，且 UI 发布传参遗漏测试的品牌/区域。

改造：以单一 FlowDocument reducer/store 为源，画布、属性面板、列表、历史记录都发语义命令。保存、试运行、发布绑定同一个 revision/hash；编辑后测试标为过期。切换类型未保存时提供保存/放弃/取消。一次拖动只记一条撤销操作；深复制被修改节点，避免删除操作变异历史快照。

## 5. 用户体验评审及目标交互

这里是基于组件和 CSS 的专家评审，不是已完成浏览器实测。无障碍参考 W3C 的 [WCAG 2.2 拖拽替代说明](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)：可点击/点按的不拖拽替代与键盘操作应分别验证，已有列表视图可复用为替代，但须语义等价。

### 员工端：围绕“哪些单需要我决定”

入口仍为 `/approvals`。默认展示待我决定 / 我发起的 / 已处理，筛选使用辅助态。列表行保留类型、业务摘要、申请人、当前责任人、状态/期限；不在每行展开完整流程与全部回执。选择一行后展开详情。

详情顺序：审批对象及版本 → 与上次相比的实质变化 → 申请资料/附件 → 当前节点、审批依据与完整路径（可展开）→ 决策区 → 历史与回执。风险分档与授权缺口由后端返回。费用审批显示制度、币种、汇率来源/日期；非金额审批不显示“人民币 0”。

发起流程：选择有资格使用的类型 → 填字段 → 检查申请（L2，服务器预览）→ 展示审批链、对象范围与实际后果 → 确认提交 → 实例回执。编辑后旧预览失效；网络不确定时用原幂等键查状态。失败保留表单与附件引用。

同意、驳回、撤回、转交、加签独立命令。确认详情与最终后果来自服务端；不通过 kind != expense 在前端推断“都会写阶段”。“已批准”“待执行”“执行失败”“已完成”分开，纯审批事项明确“不包含付款/发送/阶段写入”。

### 管理端：围绕“这版流程能否安全发布”

类型列表只保留名称、分组、负责人、当前发布版/草稿状态和异常提示。选择类型后进入版本详情，避免把新建表单、所有节点、试运行结果无限堆在一页。

版本详情用基本信息 / 申请表单 / 审批流程 / 验证与发布四个页内面板，共享同一草稿。页面顶部持续显示保存状态和版本。编辑阶段主 CTA 为保存草稿；已保存且验证通过时主 CTA 为发布，保存降为辅助。发布确认展示版本差异、范围、策略与验证摘要。

流程画布采用节点库 → 画布 → 属性面板；可用宽度不足时属性面板收为抽屉，窄屏提供等价列表编辑。节点使用业务名称，内部 node ID 收在高级详情。角色/指定人使用可搜索选择器，展示“解析到谁、为什么、来源版本”；不要求管理员手输 emp_ ID 或任意 role 字符串。

角色任职在现有组织治理中维护，节点只引用并提供跳转入口。没有独立角色授权页不需要补“形式上的页面”，需要补的是可管理、可解释、可审计的授权事实。

## 6. 技术改造边界

建议在当前 Hono/React/TypeScript 与现有持久化体系内演进，不因本轮评审更换框架或引入第二套队列。

```text
权威组织/角色任职 + 业务发布制度/类型版本
                    ↓
           ApprovalDefinitionValidator
                    ↓
登录身份/范围 → ApprovalPrepare → 确认摘要
                    ↓
              ApprovalCommandService
          身份 / 权利 / 版本 / 幂等 / 事务
                    ↓
       实例 + 节点任务 + 决定 + outbox + 计时
                    ↓
        受控后续执行 / 通知投递 / 超时调度
                    ↓
       队列投影、允许动作、审计与真实回执
```

候选数据契约：类型与版本分离；实例引用 type_version、policy_version、form_hash、organization_version 和确认摘要；节点任务使用稳定 node_instance_id/assignment_revision；命令具有 actor、scope、expected_version、idempotency_key。此处是实现建议，不新增业务规则。

关键规则：服务端返回 allowed_actions、eligible_assignees、consequence、risk、blocked_reason；UI 不推导审批资格。运行中旧实例保留历史审批依据，但组织撤权或任职失效必须阻止旧审批权继续使用，并进入规则定义的重派/接管流程。

## 7. 实施顺序、责任与验收

| 阶段 | 主责 | 交付 | 放行条件 |
|---|---|---|---|
| M0 规则与范围收口 | 业务专家、平台产品经理 | 权威制度/组织来源、角色权限、支持矩阵、CEO/自批/代理/超时口径、附件与业务后果契约 | 相关决策有出处、责任人、范围和生效版本；已发现 P0 的受影响新提交不放行 |
| M1 权限与命令契约 | 后端、测试经理 | F1–F5、发布结构校验、共享 prepare/commit、服务端 schema/范围校验 | 未授权读取/提交/转交拒绝；保留字段不可覆盖；同键不重复；旧确认失效 |
| M2 运行语义与超时 | 后端、架构师 | 支持的节点运行语义、不可变类型版本、调度契约/outbox/接管 | 节点状态正确；重启/重试可恢复；陈旧任务不改新节点；通知有真实投递状态 |
| M3 编辑与员工体验 | 前端、UI/UX | 单状态设计器、同版本测试发布、动态表单、独立确认、列表详情结构 | 所见/所测/所发同 hash；新旧版本可维护；失败不丢输入；单主 CTA |
| M4 验收与迁移 | 测试经理、项目经理 | 定向回归、视口/输入矩阵、数据迁移清单、灰度与回退记录 | 按 TECH-TEST-03 分开保存模拟、真实 harness、授权集成证据；无越权或错误副作用 |

可以先并行准备 M3 的纯呈现调整，但涉及人员权限、会签条件、自动决策等交互必须消费 M0/M1 定义的契约。这里的并行是实施安排建议，本次未启动代理或实施代码。

迁移时逐文件合并附件增量。已运行审批的原始 chain/payload、规则出处和决定必须保留；不能按新定义静默重算历史批准。对缺少权威版本的待审批单标记待核验，由有权角色处理。切换后保留旧 API 适配层直至消费方迁移；回退只停止新模板发布/新提交并恢复兼容入口，不抹除已发生决定或外部回执。

### 必须新增的验收案例

1. 普通员工不能获取其他人的通知、超时单据、非授权类型；直接详情/统计同样受限。
2. 未知申请人、无有效人员绑定、未知角色、跨范围转交/加签拒绝；组织撤权立即生效。
3. 金额分界由同一发布制度驱动；未知币种/缺汇率阻断；fields.amount_cny/brand/region 不得覆盖系统上下文。
4. 同一幂等键重复与并发提交只生成一个实例；断线后取回原回执；相同键不同内容冲突。
5. 必填、条件必填、下拉选项、数字精度、附件所有权在服务端拒绝非法输入；动态金额正确进入条件表达式。
6. 空图、死循环、断引用、缺默认出口、非法表达式、不支持模式发布失败；有效图的边界分支逐一可验证。
7. 会签全部通过、或签单人通过、拒绝处理、办理完成与抄送只读按业务发布口径验证；未发布规则不由测试自行创造。
8. 改节点属性后拖拽/撤销/重做不覆盖；同节点 ID 的两个类型不串数据；编辑未保存时不能把旧测试标作当前通过。
9. 发布 v2 后 v1 实例仍可解释；重复发布幂等；两名管理员同时修改返回冲突。
10. 超时前后、双扫描器、已完成后迟到、节点已流转、人工转交、重启、通知失败、无合法升级人、连续升级均有确定结果与接管入口。
11. 撤回确认不能称驳回；转交确认不能称同意；不存在目标不能写进 chain；状态/回执不重复展示。
12. 按 DESIGN §13 的宽度×高度×输入模态矩阵验证；含 1260/1024×630/589、≤860 触摸、200%缩放、深浅色、键盘读屏与减弱动效。未实测不得标记通过。

现有 `e2e-approval-timeout.mjs` 只检查创建后有 deadline/remind_at，未推进时间执行 handler，不能证明升级、提醒投递或恢复已完成。三个脚本默认访问固定 localhost，不能不分环境直接运行。后续应纳入受控测试环境和发布门禁，保留明确的测试身份与隔离数据库。
