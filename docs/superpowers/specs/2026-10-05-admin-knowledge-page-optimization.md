## 审查链（CONST-08）

需求 → 主责角色 → 宪法条款 → 基本法条款 → 结论与证据 → 下一步

- 需求：依用户截图优化管理侧知识页面的视觉、筛选、原件、审批交互及事件反馈。用户进一步明确授权「补齐独立知识发布审批流程及后端事件联动」。
- 主责角色：UI/UX 决定布局与无障碍；前端实施服务端状态、表单及确认；后端实施审批绑定、原生 PostgreSQL 提交闸门、事件和执行；测试经理验证交互、权限、版本和恢复。组织成员关系与评审人规则复用现行权威配置，不由页面推断。
- 宪法条款：CONST-04（职责与权限）、CONST-05（正式动作确认）、CONST-06（原件来源）、CONST-08（先审宪再审法）、CONST-10（诚实交付）。
- 基本法条款：PROD-PLAT-04/05；BIZ-14/15；TECH-FE-01/03、TECH-BE-01/02/03/04、TECH-TEST-01/02/03；组织权限与工具风险目录的 L1/L2/L3 契约。
- 结论：符合。新增知识发布申请是独立副作用：选择实际已发布流程 → 服务端预检 → 展示对象/流程版本/处理人/发布后果并确认 → 冻结资料版本及发布说明 → 进入现有评审待办 → 审批通过事件 → 后台再次核验授权与材料 → 发布并留回执。拒绝/撤回不发布；直接管理员 publish 入口拒绝绕过审批。
- 证据：页面不自行解析评审人；普通与知识流程共用 reviewResolver 和组织上下文构造函数。确认绑定命令、资料指纹、流程定义和处理人；材料/权限/流程变化要求重新确认；行锁、唯一活动申请约束与确认幂等回执防止重复提交。
- 下一步：执行版本化迁移、配置实际组织评审流程并启动现有 Outbox/执行服务后，在授权部署环境验证真实业务资料。

## 界面与交互

截图作为结构参考；DESIGN.md 是 token 数值来源。统一小字号，通过字重、间距、边框与分隔表达层级；使用规范要求的品牌主行动颜色。筛选区采用图标标题与可键盘折叠的分组，折叠不清空选中；长列表渐进展开；分页、搜索与分类计数同源；新建/上传后定位实际记录与页码。

结果行只出现一次知识标题和状态。资料详情包含分类、原件、加工记录、发布流程及其实际字段、发布说明、服务端预检与重新检查。唯一主行动位于对应材料表单之后，确认期间降低底层强调；按宽度、高度、输入模态分别适配，触控命中区扩大而不扩大视觉控件。

解析作业和审批申请只跟随实际服务端状态刷新。接口失败不冒充空结果。审批提交不显示“已发布”；审批通过但发布服务未完成时展示真实等待、作业编号与处理入口。不确定/失败执行必须重新确认恢复；权限或材料变化造成的发布失败要求按当前版本重新提交。审批页面向参与人展示本次资料原件、发布说明、版本、发布状态与回执。

## 后端实施契约

- 增量 migration：`backend/migrations/025_knowledge_publication_applications.sql`，登记到 PostgreSQL 迁移清单；请求路径不建表。
- 持久绑定：`knowledge_publication_applications` 关联通用评审实例、原件哈希、加工版本/任务、资料更新时间、流程版本、发布说明及终态回执。一个资料最多一个活动申请。
- 提交确认：`knowledge_publication_confirmations`，操作与命令摘要、组织、身份、材料摘要及有效期绑定；重复同一请求返回原回执，变更内容不得复用确认。
- 审批终态更新与 `execution_jobs` / `execution_outbox` 在同一 PostgreSQL 事务内提交（数据库触发器）。后台 `knowledge.publication` 处理器不依赖页面/进程内定时器。
- 发布执行锁定申请与资料；审批通过且身份/组织授权仍有效、资料和加工版本完全匹配才更新 `knowledge_documents`。发布成功、失败、拒绝、撤回及恢复分别记录 review_events。处理重放返回原回执，不重复发布。
- 原件接口只对当前组织的流程参与人或流程管理员开放，读取时核对原件哈希；权限撤销即时生效。已有审批留痕的资料禁止删除原件，保留历史并使用归档。
- 事件登记：`config/event-catalog.yaml`、事件清单 §8 的知识发布实施事件。
