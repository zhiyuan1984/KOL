# 阶段7：双Agent交接与正式合作上下文

基线为 GitHub main `3b26e7d8`。本阶段复用现有任务中心、Agent治理、原生合作、协作会话、工单与审批闸门，不扩大技能批次，不建设另一套业务执行引擎。

## 已实现范围

- 业务配置提供 `agent:lead` 和 `agent:collab` 首批装配，复用已实现的五个技能正文与共同Codex harness。安装走现有草稿、预检、明确确认发布流程；不在运行时自动创建Agent。原 `agent:kol`、旧任务、会话和深链保持可用。
- 新Agent复用原Agent当前有效绑定的同一覆盖范围，不从邮件或交接包授予资格。有到期绑定时拒绝自动安装。治理归属优先采用原Agent已确认组织；原Agent缺失组织时，仅采用当前发布管理员在原绑定公司中的唯一有效主组织。该归属不修改原Agent，也不替代人员绑定、组织继承或业务范围。
- 原任务详情内准备R2交接候选，记录任务版本、目标Agent/技能、原因、已知对象与来源引用、评估/草稿版本、已确认选择和待办引用。缺项明确显示；不复制邮件正文、工具输出或凭据，不补造对象与事实。
- 明确确认后用原任务创建器原子创建一个关联的待处理任务；重复确认只返回同一回执。交接本身不运行模型、不转移负责人、不创建合作、不发送、不解密、不推进阶段。
- 接收和实际运行均重验当前任务访问权、目标Agent资格和技能依赖。来源任务版本改变时阻止继续使用旧依据。交接依据与已采纳回执在数据库内不可覆盖或删除；前后任务可沿原地址互相追溯，失去来源访问权时不展示来源标题。
- 正式协作上下文只按 `kol_cooperations.project_task_id` 读取已有关系，并复用原 `requireCoop` / `requireLead` 范围检查。合作负责人、跟进负责人、档案负责人分别表达；来源未提供档案负责人时明确未知。线索、合作和工单状态不互相替代。
- 现有协作会话继续提供工单、审批门槛、复核和事件事实。未清理旧 `collaborations`，未按同名或旧ID猜测正式合作，未更改审批链、合法阶段转移或业务归属规则。

## 邮件与历史兼容

交接传递邮箱、选中会话/消息与对象的选择器；执行时继续由原实时上下文解析器核验当前邮箱绑定和来源版本，通过目标Agent已挂载技能读取最新授权证据。本体只补充业务语义与稳定引用，不能替代实时邮件正文和互动历史。

未带交接记录的历史任务不会被强行迁移；缺Agent字段时保持原有 `agent:kol` 解释。伪造 `input._handoff` 不能生成可信交接上下文，运行器仅采纳服务器持久回执。原任务和来源地址不会自动导回首页或被目标任务替换。
