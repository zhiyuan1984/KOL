## 实施边界

六类起点：单人、会签、条件、审批后办理、通用事项、知识发布。需要实名配置的起点保留待配置状态，不能直接发布。普通审批支持员工在管理员发布范围内选人；知识发布沿用既有管理侧固定人员规则。后续办理是实际人工任务和证据登记，不承诺付款、外发、导入或阶段自动推进。

旧费用技能接口仍兼容既有调用；新员工 AI 入口要求仅生成 v2 草稿，没有匹配的公司流程时给出缺口并返回审批中心。协议与受控保存验证不代表真实 Codex 生成质量或外部系统写入已验证。

## 验证与部署证据

相关后端验证共 85 个独立用例通过：审批 API 29 个（真实 session 与独立 PostgreSQL 模板测试库），审批引擎、图、条件、数值与新增规则 54 个，业务审批严格输出协议 2 个。修改后只重跑受影响的边界；未运行无关功能的全量回归。

审批浏览器共 24 个独立用例通过，覆盖管理侧创建/复制/保存恢复/发布/知识流程、员工草稿/路径与候选/提交确认/版本升级/附件/金额，以及来源、AI 草稿恢复、窄屏、短屏和触控。处理回执与本轮材料差异用例通过；最后仅重跑受影响用例。

前后端类型检查、前端构建通过。真实 Codex app-server 使用本次严格 schema 完成一次合成草稿生成（review_draft），未挂载业务工具、未写入正式申请；这是输出协议验证，不表示生产公司配置或外部履约已验收。

发布执行：以相关验收通过后的 main 提交为固定版本，使用现行 deploy.sh 构建并重启 API、Outbox 与两个执行 Worker，检查 /api/version、/api/health、静态资源和服务状态。按用户限定范围，本次 main 提交跳过自动全量 CI，由上述限定验证及手工固定版本部署完成发布；工作流和现行法均未修改。发布前无冲突合入 main 的 be7da7e9（已有采集超时修复），不重测该无关功能。本机主 checkout 存在其他任务的未提交修改，保持原样，通过当前隔离工作区快进远端 main。

没有数据库迁移或预先创建公司流程。既有申请保持原定义与材料版本。若已发布 requester_choice 规则，回退到不识别该规则的旧后端会阻断对应申请；应保留实例与回执，优先修复当前后端或仅恢复上一版界面。最终部署回执保存在本次工作区 artifacts/approval-deployment.md。
