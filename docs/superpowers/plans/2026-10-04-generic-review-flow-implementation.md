# 通用评审流程：实施任务与验收计划

日期：2026-10-04。状态：核心人工评审链路已开始落地；各任务实现范围、验证与剩余差距见[实现记录](2026-10-04-generic-review-flow-implementation-status.md)。依据[详细设计](../specs/2026-10-04-generic-review-flow-detail.md)、[概要设计](../specs/2026-10-04-generic-review-flow-overview.md)及[现状评审](../specs/2026-10-04-approval-v2-review.md)。文档完成不等于生产功能完成。

## 1. 实施原则与依赖

先完成共享契约、隔离与命令事务，再完成运行语义和设计器，最后完成业务集成与迁移。受影响接口已有 P0 问题先修，不能等整个重构结束才补权限。保持现有分支变更，附件按文件差异取用，不覆盖全仓库。

角色分工是职责分工，不表示已创建子代理或自动分派任务。技术规则由对应专家角色决定；业务规则缺口只阻断依赖模板发布，不阻断组件和契约实现。

## 4. 重点故障注入

1. 在 command 插入后、状态更新后、事件写入后、outbox 写入后分别抛错；每个注入点验证整笔事务回滚。
2. 在数据库 commit 后、HTTP 返回前模拟断线；相同 key 返回原实例/决定引用。
3. 在远端接受后、本地保存回执前模拟退出；按外部幂等/查询能力恢复，否则 uncertain，不重复外发。
4. timer 被领取后人工转交或补充材料，再执行旧 job；预期 skipped 且当前新任务不变。
5. 两个发布者读取同草稿，分别保存/发布；竞争失败方显示版本差异，不后写覆盖。
6. 准备确认后撤销角色任职、停用 Agent 或撤销业务对象范围；确认不得继续执行，回执查询不泄露旧材料。

模拟故障仅在隔离测试数据库与明确夹具中运行。业务写入集成测试使用显式授权的对象/范围，不为证明只读能力而发信。

## 5. 测试和发布执行顺序

实施时先定向运行本次新增契约、服务单元/事务集成、组件与 E2E；通过后执行仓库要求的门禁，不因文档阶段预先声明通过。

| 检查 | 现有入口 / 应接入方式 | 证据 |
|---|---|---|
| 规范与契约 | backend `validate:contracts`，扩展 review schema 与模板夹具验证 | schema 版本与验证报告 |
| 后端静态检查 | backend `typecheck` | 编译记录 |
| 后端行为 | backend `test`，接入 review suites；生产门禁 PostgreSQL 模板库 | 用例结果、故障注入与并发记录 |
| SQLite 兼容 | 使用明确隔离 DB 的同一 repository 测试集 | 兼容结果，不替代 PostgreSQL 验证 |
| 前端静态/构建 | frontend `typecheck`、`build` | 构建记录 |
| 前端交互 | frontend `test:e2e` 定向 review specs | 页面截图、trace、视口与输入模态记录 |
| 发布门禁 | backend `release:gate` 与 `.github/workflows/release-gate.yml` | 平台/模板/Policy/schema/技能依赖版本、回退记录 |

当前 frontend `test:e2e:release` 与 workflow 中列出的集合不含新增评审套件，D17 必须同时更新实际执行集合与记录，不能只新增测试文件。数据库迁移同时接入 PostgreSQL schema apply，不能只让本地 SQLite 自初始化测试通过。

## 6. 上线分批与回退

第一批：仅治理草稿、定义校验、预览和受限测试模板；不开放未验证节点。

第二批：对已明确范围的员工开放“费用+一个非费用”真实申请和人工评审。观察访问拒绝、命令冲突、重复实例、积压与阻断原因，不自动扩大范围。

第三批：开放已验证的多人评审、通知、超时与办理能力；有独立授权和回执的后续动作最后启用。

发生越权、重复副作用、错误批准时停止受影响的新提交/动作，保留读历史与接管。恢复需修复根因、补偿已发生副作用并取得定向验证证据。关闭开关不等于撤销已发生的决定、通知或外部执行。

回退包必须兼容已建新表并可读取/处理 v2 实例。完全旧二进制不能直接接管有 v2 活跃单据的数据库。未使用表可以留存，运行数据不通过破坏性降级迁移删除。

## 7. 完成记录格式

每个任务实施后记录：requirement_refs、implementation_assets、owner、status、commit/version、evidence、known_gaps。状态只能依证据从 not_started → in_progress → verified → released；真实授权集成未完成时明确列缺口，不把 stub E2E 标成 production verified。
