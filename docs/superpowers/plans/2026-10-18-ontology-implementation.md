# 员工端与管理端本体实现记录

日期：2026-10-18。范围：本体定义工作台与治理服务；不重写员工端其他业务功能。

## 审宪与适用边界

需求 → 员工端浏览业务定义；管理端维护对象、属性、关系、事件、规则、动作，保存草稿、确认发布、停用、回滚 → 主责角色：平台产品经理 / UI/UX 专家（界面与定义治理）、KOL 业务专家（沿用 BUSINESS 语义）、架构及后端专家（原生 PostgreSQL、版本与确认）→ CONST-02/03/04/05/06/08/10 → PROD-PLAT-01/03/04/05、PROD-AGENT-01、BIZ-01/02/10/11/12/14/19、TECH-FE-01/02/03、TECH-BE-01/02/03/04 → 符合：新接口复用工作台身份，当前组织成员关系决定公司范围；管理员资格不越过公司范围；员工仅获得业务定义投影，不能获得草稿、内部依赖或治理写入口 → 下一步：定向测试、部署时初始化本体 schema。

规则和动作在本实现中是描述性元数据，不是可执行 Policy、业务审批决定或人员授权。元数据发布由本公司管理员在完整内容预览后 R3 确认；发布不修改既有规则执行器、审批链、技能/工具绑定、Agent 使用资格或业务实例。需要改变执行规则与正式业务数据时，仍走原有领域发布与 Host 闸门。本次没有实现从自由文本规则生成执行代码，也没有将动作编码变成任意工具调用 URL。

视觉：用户明确指定的七张图为本任务唯一视觉依据，采用蓝白三栏、三层横向筛选、对象表与五维页签、紧凑独立编辑卡片。仅对本体路由作用；已有壳层的字号强制收敛和通用页面留白对本体面做显式排除。共享其他页面的视觉与已有改动保留。

## 实施资产

- 员工入口：`/ontology`；仅浏览业务对象登记及发布定义，支持分类、搜索、分页、五维查看；不调用模型或外部工具。
- 管理入口：`/admin/ontology`；`/admin/data/ontology` 跳转至同一页面；增加本体导航。
- 共享类型：`shared/ontology.ts`；前端：`frontend/src/ontology/`；原生 PostgreSQL 服务：`backend/src/ontology/`；接口：`backend/src/routers/ontology.ts`。
- 注册基线：已有 objects-registry 与 event-catalog；关系、规则、动作的结构化语义放入 `config/ontology-semantics.json`，逐项引用现行条款。平台内核不硬编码 KOL 语义。不导入原型的 example_* 示例为生产定义。
- 四张新增表：`ontology_documents`、`ontology_versions`、`ontology_confirmations`、`ontology_receipts`。历史和回执禁止更新或删除；文档写入使用公司粒度事务锁及预期版本；确认绑定主体、公司、动作、对象版本、目录版本和有效期；幂等键重放返回原回执，不同内容拒绝复用。
- 草稿保留于 PostgreSQL，保存不影响员工读面；发布建立新的生效快照；停用保留历史；回滚发布一个新版本。新增关系目标在发布前校验；停用被引用对象前阻止并说明依赖。

本体定义发布仅决定本体工作台读面使用哪个版本。现有技能和业务服务继续使用各自已发布配置，本轮没有把所有历史消费者切换为新定义仓库；不能据此声称业务执行已动态化。

## 部署初始化（尚未写入业务库）

配置有效 `DATABASE_URL`，在 backend 目录运行 `npm run db:apply:ontology`，只初始化本体所需表、索引和不可变历史触发器，不跑无关迁移或导入业务数据。完整 schema 迁移账本也登记了同一幂等增量。缺表时接口返回明确初始化提示。

服务复用兼容运行模式现有工作台登录及正式主体上下文；现有纯 PostgreSQL 模式尚未接入工作台登录的全局阻断保持有效，本次不新建第二套认证、不绕过该阻断。
