## 0. 十分钟先建立这张图

本仓库是 **LiTime KOL 建联工作台**。员工在会话里干活；页面只放资产。

三层不要混：

| 层 | 是什么 | 不是什么 |
| --- | --- | --- |
| **Codex harness** | `codex app-server`：thread / turn / Skill / MCP | Host TypeScript、`runStub`、前端编排 |
| **Host / 内核** | 会话 HTTP、PEP、确认发送、确认阶段、阶段机、一次拉往来 | 信件目录、缺口文案、口令正则、选 Skill、代组草稿 |
| **Skill** | `backend/skills/<id>/SKILL.md`：口令、必填、缺口、禁止事项、MCP 白名单 | 状态机、SMTP、正式阶段写入 |

员工端永远只有 **三扇门**（点了只预填第一句，不是三套运行时）：

| 门 | 预填 Skill | 代码 |
| --- | --- | --- |
| KOL | `stage_sop` | `frontend/src/agentConfig.ts` `AGENT_ENTRIES` |
| 审批 | `business_approval` | 同上 |
| 爬虫 | `creator_discovery` | 同上 |

铁律（改代码前默念）：

1. 点芯片 / 今天推荐 / 建议下一步 = **只预填**（`act=ask`），不起箱、不发信。
2. 生产执行走 **真实 Codex app-server**。`CODEX_MODE=stub` 仅测试。
3. **发送 ≠ 改阶段**。真发只走 Gateway；正式阶段只走 `hostConfirmStage`。
4. 报价芯片标签永远是 **「写报价邮件」**。报价只是「报价待确认」这一阶段的那封信。
5. 不要第四个智能体，不要在 Host 里再写 `STAGE_MAIL` / 推荐表 / 口令正则锁 Skill。

## 1. 怎么跑、怎么测

本机：

```bash
npm i -g @openai/codex
codex login          # 或在仓库根 .env 写 OPENAI_API_KEY
chmod +x scripts/start.sh && ./scripts/start.sh
```

浏览器：http://127.0.0.1:8765  

没有 Codex、未登录时，写信必须报持久错误，**不得**用模板假信顶上。

测试：

```bash
cd backend && npm test          # 强制 CODEX_MODE=stub
cd frontend && npx tsc --noEmit
cd frontend && npx playwright install chromium && npx playwright test
```

Playwright 自己起 stub 服务（默认 `8876`），不要和 `start.sh` 的 real Codex 抢端口。细节见仓库根 `README.md`。

## 2. 一次任务怎么走完（Codex harness）

把 Dify 词换成本仓库的词：Skill ≈ Chatflow，Thread ≈ conversation，Turn ≈ 一次 Run，Item ≈ 节点输出，MCP ≈ 工具节点。对照表在 `README.md`。

### 2.1 员工侧（不起箱）

1. 三扇门：`frontend/src/pages/Agents.tsx`
2. 输入框 / `/` 点技能 / 芯片：`frontend/src/components/ComposerDock.tsx`
3. 会话页：`frontend/src/pages/Chat.tsx`（缺口芯片不锁 `email_compose`）
4. 提交：`POST /api/sessions/:sid/messages`，`act=ask`（`frontend/src/api.ts`）
5. Host 拒绝 `act=go` 发消息（`go` 只改路由）

### 2.2 Host 开闸（不干业务）

6. 入口：`backend/src/host/api.ts` `POST /sessions/:sid/messages`
7. 已锁 Skill（芯片 `intent` / 任务卡）→ 不再猜。自由文本才 `backend/src/tasks/recognize.ts`
8. `backend/src/host/intent.ts` **只抽 handle / 邮箱**，禁止正则把口令锁成某个 Skill
9. 否决：邮箱必须出现在用户字或已绑发件箱；发信时再走 `backend/src/host/pep.ts`
10. `dispatch` → `backend/src/worker/runner.ts` `runWorker`

### 2.3 Codex turn（真正干活）

`runWorker` 选择：

- `CODEX_MODE=stub` 或 `compose_preview_only` → `runStub`（仅 CI / 预览）
- 否则 → `runCodex`

`runCodex`（同文件）+ `backend/src/worker/codex.ts`：

```text
写 box（AGENTS.md + CONTEXT.md + 当前 SKILL.md）
→ spawn `codex app-server`
→ initialize → account/read（缺账号则 account/login/start）
→ skills/extraRoots/set → skills/config/write
→ thread/resume（同会话续改）或 thread/start（新信）
→ turn/start（Skill path + outputSchema）
→ 按 Skill 白名单调远程 MCP
→ turn/completed → 杀箱
```

协议说明：`docs/codex/README.md`。线格式是换行 JSON，**不含** `jsonrpc:2.0`（MCP 线才带 2.0）。

Item 解析：`backend/src/worker/parse.ts`  
允许类型：`create_draft` / `task_result` / `propose_stage` / `crawl_plan` / `create_approval` / `text` / `list_overdue` / `note`

### 2.4 映回会话（仍不发信、不改阶段）

`backend/src/host/api.ts` `mapWorker`：

| Item | 会话消息 | 说明 |
| --- | --- | --- |
| `create_draft` | `email_card` | 可改草稿；发送前必须人确认 |
| `task_result` | `task_result_card` | 写信会再贴 `compose_loop` |
| `propose_stage` | `confirm_stage_card` | 只提案；人点确认才写阶段 |

写信缺口：Host **加载** Skill 契约，不自建目录。

- 契约原文：`backend/skills/email_compose/SKILL.md` 里的 ` ```email-compose-contract `
- 加载：`backend/src/skills/email-compose-contract.ts`（`stageMailSpec` / `composeGapHint`）
- 贴卡：`backend/src/host/compose-loop.ts` `attachComposeLoopCard`

报价待确认、人没写金额：

- 输入框 placeholder：`写报价邮件 @红人 金额 [USD]`
- 第一颗芯片：**补上金额**（预填 `把金额改成 [USD]`，不锁技能）
- 有缺口时不要建议「核对预览后回复「确认发送」」

### 2.5 人确认之后（才碰真实世界）

| 人做的 | 闸门 | 文件 | 效果 |
| --- | --- | --- | --- |
| 确认发送 | L2 | `backend/src/gateway/send.ts` `sendDraft` | 真发；**阶段不变** |
| 确认阶段 | L3 | `hostConfirmStage`（`host/api.ts`）+ `gateway/starry.ts` 本地缓存；人确认后 Host 调远程 `changeLifecycleStage` | 写正式 `stage_code` |
| 驳回阶段建议 | L3 | `hostRejectStage`（`POST /sessions/:sid/confirm-stage` `{ rejected: true }`） | 关确认卡；**不改**正式阶段、不写远程 |
| FACT_AUTO | 内核 | `kol-journey.ts` `tryFactAdvance` | `autoLegalTargets` 推下一格，不走人确认 `legalTargets` |

Worker **禁止**自己 `sendDraft` 或写阶段。打开会话才向 Starry **拉一次**往来（`kol-journey.ts` `syncKolSessionMail`）；摘要是另一条线（`mail-summary.ts`）。写信 / 确认发送 / 记状态不要再 pull。

```text
点芯片（预填）
  → POST /messages act=ask
  → Host 开闸 / 否决
  → Codex app-server：thread + turn + Skill + MCP
  → Item → 结果卡 + 草稿
  → 人点「确认发送」才 Gateway
  → 人点「确认阶段」才 hostConfirmStage
```

## 3. 改需求时改哪一类文件

| 你想改的 | 改这里 | 不要改这里 |
| --- | --- | --- |
| 某封信的短名 / 口令 / 要点 / 缺口文案 | `backend/skills/email_compose/SKILL.md` | `compose-loop.ts` 里再写一张表 |
| 新业务能力 | 新增 `backend/skills/<id>/SKILL.md` + catalog + 测试 | 旁路 REST、前端直接调发信 |
| 阶段能不能迁 | `backend/src/stages.ts` + 测试 | Skill 正文「建议下一步」 |
| 发信拦不拦 | `backend/src/host/pep.ts` + `gateway/send.ts` | Worker / Skill HTTP |
| 会话 chips 有几颗 | `kol-journey.ts` `collabActions`：本阶段信件 + `stage_sop` + `confirm_stage`（异常前置 `risk_scan`） | Host 再塞回复分析 / 画像 / Deal Memory |
| 今天推荐空位 | `home-board.ts` 用 `taskDefinitions()` 垫 | 再写 `CATALOG_RECS` |
| 未发送续改 | `result-revise.ts` + 同一 thread `resume` | Host 正则二次改金额语义 |
| 员工端文案 / 布局 | `docs/UX-*.md` 然后前端 | 员工界面出现 MCP / Codex / 线程 |

## 7. 常见改法（照着做）

### 新增一个 Skill

1. 建 `backend/skills/<id>/SKILL.md`，YAML `id` 与文件夹同名，写清 `mcp`、`required_inputs`、禁止事项（发信 / 改阶段）。
2. 需要市场可见则 `in_market: true`。
3. 在编码规范要求的测试里加合同（至少：catalog 能扫到、Host 不能旁路写库）。
4. 员工端入口若要出现在三扇门或芯片里，走已有预填，不要新开第四门。

### 改「报价待确认」这封信

只改 `backend/skills/email_compose/SKILL.md` 契约里 `QUOTE_PENDING` 与缺口表。  
芯片标签保持 **写报价邮件**。Host `compose-loop.ts` 只加载，不复制目录。

### 改发信或改阶段

发信：`pep.ts` → `gateway/send.ts`。  
阶段：`stages.ts` 合法性 + `hostConfirmStage`。  
Skill 只能 **提出** `propose_stage` / 让人说「确认发送」。

### 追问未发送草稿

走 `result-revise.ts`：同一 `thread/resume`，只改点名的字段。人说「再写一封」或点阶段芯片才新开。

## 8. 禁止清单（接手最容易踩）

- 生产路径 `isEmailMcpTask → runStub`，或 Host 函数直出 `email_compose` / SOP / `confirm_stage` 提案。
- 在 `compose-loop.ts` / `intent.ts` / 前端恢复 `STAGE_MAIL`、`STAGE_NEXT`、`CATALOG_RECS`、口令正则锁 Skill。
- Worker 调 `sendDraft` / `sendConversation` / 写 `stage_code`。
- 打开会话以外的操作再拉一遍 Starry 往来。
- 员工界面渲染 MCP / Codex / 线程 / Host。
- 点推荐就开跑、就把发送当成改阶段。
- 缺 Codex 时用 `email-templates.ts` 假信顶上。
- 报价芯片改成别的文案；缺金额时锁死 `email_compose`。
