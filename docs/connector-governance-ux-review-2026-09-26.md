# 连接器配置 UI/UX 评审与改造说明

**日期：** 2026-09-26  
**范围：** 管理端「连接器枢纽」与连接器详情页  
**受管目录：** `MediaCrawler MCP`、`Starry KOL MCP`

> 本文基于提供的加载态、枢纽、详情、工具审批、凭据与授权截图，以及仓库实现进行评审；同时记录已落地的改造。

## 2026-09-26 决策更新：改为通用 MCP 管理

后续产品要求明确连接器是平台能力，管理员需要添加任意受管 MCP，而不只维护两条内置连接器。因此本文原先“固定两条受管 MCP”的建议由 [`superpowers/specs/2026-09-26-mcp-connector-admin-governance.md`](superpowers/specs/2026-09-26-mcp-connector-admin-governance.md) 取代。当前实现使用统一配置器、凭据保险库、连接测试、逐工具风险审批和范围授权；内置 Starry/MediaCrawler 保留为目录种子与业务适配器，不再各自拥有配置向导。

## 结论

旧界面的核心问题不是“信息太多”，而是把**历史别名、任意接入能力、运行时技术参数、凭据、人员授权与审计**并列放在一个管理任务里。结果是管理员无法快速回答三个关键问题：

1. 现在究竟有哪些被批准的连接器？
2. 哪一条真的完成了验证、可以启用？
3. 谁以什么身份改过什么？

此外，加载未完成时被当成“尚未挂接”、原始英文异常、`TODO`、以及 `usr_sriphy` 内部标识，都会直接削弱高风险配置场景中的信任感。

本次改造将连接器页收束为**固定两条 MCP 的受管目录**，并用「保存接入 → 测试连接 → 审阅工具 → 设置访问 → 启用」组织流程。技术信息仍可追溯，但不再抢占首屏。

## 改造前评分（10 分制）

| 维度 | 评分 | 主要问题 |
|---|---:|---|
| 信息架构与目录边界 | 4 | 任意新增 MCP/HTTP、历史别名、业务系统连接并列，目录边界不可信。 |
| 治理正确性与可审计性 | 3 | “已配置”不等于可用；启用与验证脱钩；异常和身份呈现不可靠。 |
| 管理员工作流效率 | 4 | 详情纵向堆叠接入、JSON、工具、凭据、授权、审计，缺少下一步。 |
| 数据密度与可读性 | 6 | 表格基础合格，但把“最近错误”和技术 TODO 放在每行，扫描负担过重。 |
| 无障碍与本地化 | 5 | 表单基础较好；但有空操作表头、中英文混杂、状态依赖管理员自行推理。 |

## 已落地的设计与数据改造

### 1. 固定受管目录与历史数据清理

- 服务端白名单只接受两条记录：`claw`（**MediaCrawler MCP**）和 `starrykol`（**Starry KOL MCP**）。
- 启动迁移会：
  - 将已有的 `kolclaw` 授权并入 `claw`；将 `starry`、`emailmcp`、`enterprise_mail` 授权并入 `starrykol`；`admin` 统一收敛为 `write`。
  - 删除其他连接器记录及其级联运行时配置、工具策略与授权数据。
  - 删除失效连接器相关的运行时审计记录。
  - 保留两条正式 MCP 的规范名称，首次迁移后将其重置为“待配置”，避免旧的“已配置”绿灯误导。
- 管理 API 拒绝创建任意连接器、删除正式连接器、向目录外连接器授权或保存配置。
- 员工连接器使用面与技能枢纽也只展示这两条正式 MCP。

> 本实现将用户所说的 “median crawler mcp” 按项目既有命名解释为 **MediaCrawler MCP**。

### 2. 可验证的状态模型

旧的“已配置”同时表示“有引用、可用、可能已启用”，语义不成立。现在的管理员可见状态为：

| 状态 | 说明 | 可执行的下一步 |
|---|---|---|
| 待配置 | 尚未保存运行时接入草稿 | 保存接入 |
| 待验证 | 已保存新配置或凭据引用 | 测试已保存配置 |
| 验证失败 | 最近一次 MCP 工具目录测试未通过 | 修正后重试 |
| 已验证待启用 | 测试通过，但尚未启用 | 审阅工具、设置访问、启用 |
| 已启用 | 已启用受管连接器 | 持续查看验证和治理历史 |
| 已停用 | 显式停用 | 重新验证后再启用 |

保存配置会自动取消启用状态并变更为“待验证”；探针结果会记录验证时间、工具数和无秘密错误码。只有状态为“已验证待启用”时，界面与 API 才允许启用。

### 3. 渐进披露的信息架构

**枢纽表格**聚焦扫描：

`连接器｜接入状态｜最近验证｜工具治理｜授权人数｜最近变更｜操作`

详情页首屏只回答当前上下文和下一步；随后采用可展开分区：

1. **接入、测试与工具治理**（默认展开）
2. **安全与凭据**
3. **访问控制**
4. **历史与审计**

运行时接入已固定为 MCP。原先默认露出的 HTTP/OpenAPI 编辑器不再是正式目录的可达路径；环境变量映射、Secret 引用等保留在“高级技术配置”中。

### 4. 凭据与权限的可用性修复

- “凭据保险库”清楚标为全局安全资产；在连接器中先显示上下文引用，再按需展开保险库。
- 员工权限从每行三个并列按钮改为单个选择器：**无访问 / 只读 / 可写**。
- 表格明确显示“有效权限”；文案持续提醒“可写不等于外发、改阶段或绕过 Gateway”。
- 个人 Starry 邮箱绑定保留在个人设置，组织配置页只解释边界，避免管理员误以为可查看或编辑个人秘密。

### 5. 错误、审计和文案可信度

- 移除管理面向用户暴露的 `TODO：后端尚未提供 last_error`。
- 将 `The user aborted a request.`、网络连接失败等常见原始异常映射为中文、可行动的提示。
- `usr_sriphy` 迁移为唯一可见身份 **`sriphy`**：迁移用户、授权、所有权与审计显示；新的审计写入也会规范化该历史内部 ID。
- 运行历史不再把整个 JSON payload 串行化渲染，避免未来意外暴露 URL、参数或敏感引用。
- 所有表格动作列有明确列名，状态文字不只依赖颜色。

## 后续建议（未在本次范围内）

1. **工具发现快照**：为每次发现持久化工具名称与 Schema hash，才能严格判断“所有新增或变更工具是否已审阅”。目前未批准的工具保持默认拒绝，已降低风险，但还不构成完整的工具变更对账。
2. **批量授权**：当员工数增加后，可将两条 MCP 合并为人员×连接器矩阵，并支持按团队筛选、批量赋权与权限来源说明。
3. **凭据生命周期**：在保险库增加“引用关系、最近轮换、将到期、替换引用”的明确安全运营视图。
4. **审计筛选**：提供按连接器、主体、操作类型和时间筛选的审计页；内部 ID 与受限技术详情只在按需展开时显示。
