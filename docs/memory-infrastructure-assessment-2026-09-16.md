# 从 KOL 工作台到记忆驱动基础设施：愿景与落地分析

2026-09-16。依据本轮用户描述、当前工作区源码和现行规范。此文件为架构提案；不声明已实现或已上线，也不替代现行宪法。简版见 [十条宪法草案](constitution-v2-draft.md)。

## 结论与愿景边界

愿景合理，能够分阶段实现：平台负责通用机制，业务包定义行业对象与动作；记忆服务提供跨会话事实和索引；模型在需要理解、生成、规划和权衡时参与。用户看到同一个助理入口，底层可以选择查询、工具、后台提取或复杂推理四种路径。

需要将“系统不写入任何业务逻辑和数据”准确表述为：**平台不硬编码行业规则，不内置客户业务事实；平台可以托管按业务契约定义的数据，也可以连接外部权威数据源。** 若连运行时状态都不允许持久保存，就无法可靠实现任务恢复、独占归属、14 天回收、权限撤销和记忆索引。将这些状态放到外部工具服务也可以，但不会消除其存储和一致性责任。

知识库描述制度和做法；技能处理语义和业务决策；可执行策略表达需要精确执行的条件；工具负责访问或修改事实；记忆保存有出处的事实投影、经历、偏好和摘要。不能只将“14 天回收”写进一段知识库文字，期待模型每次稳定执行。

本次应用 context-engineering-advisor 的上下文边界与按需检索方法：事实持久保存，但每次只检索当前决策所需的信息；不采用把全部记忆常驻提示词的方式，也不把向量数据库当作所有记忆的必选存储。

## 执行应按动作拆分

| 路径 | 做什么 | 是否需要模型 / Thread/Turn | 示例 |
|---|---|---|---|
| 快速查询 | 精确过滤、检索、读取已存结果 | 不需要模型，不开 Thread/Turn | 我的红人、我的待办、上次邮件摘要、已有风险 |
| 确定动作 | 校验参数和授权，调用工具或事务命令 | 不需要模型；有副作用时仍执行权限和授权检查 | 完成待办、领取对象、发送已确认草稿、审批决定 |
| 后台提取 | 增量抽取事实、标签和摘要 | 可用一次有界模型调用，不需要员工打开对话；非语义字段不需要模型 | 新邮件摘要、任务完成总结、识别新的风险证据 |
| 深度推理 | 理解模糊意图、规划、生成、权衡 | 使用 Agent 执行；Thread/Turn 是当前实现选择 | 写信、建联策略、谈判建议、内容审查、风险处置方案 |

后台提取和复杂推理可以共用当前模型适配器，没必要为不同路径各建一套智能体框架。即便后台提取暂时使用 app-server，命中摘要的读取请求也不应启动它。

“是否深度思考”与“动作风险”是两条独立维度：读一份复杂分析可能需要深思，发送已经确认的草稿通常不需要再推理，但仍需严格执行授权。工具内部可能自行调用模型，平台不能把这种工具调用宣传为零模型成本。

| `creator_status_update` | `/记备注 @红人 内容=…`：明确事实可直接存取 | 模糊陈述可先提取候选；正式字段更新需命令，不能只更新摘要 |
| `creator_owner_update` | `/转交 @红人 给=员工`：权威关系和变更索引 | 明确转交无需深思；自动分配可按策略，复杂负载权衡可由模型提议 |

| `creator_contact_decrypt` | `/联系方式 @红人`：查授权与密文引用 | 无需深思，必须按敏感动作执行；明文不进入广泛可搜的共享摘要 |

## 记忆的数据模型与快速检索

产品可以统一称为“记忆”，基础设施至少要区分以下内容：

| 信息 | 应如何保存 | 为什么 |
|---|---|---|
| 事实与对象元数据 | 结构化记录或权威工具引用 | 平台、方向、地区、粉丝、任务状态可精确过滤；每类字段明确权威来源 |
| 归属与访问关系 | 支持原子更新的关系记录 | 决定谁能看、谁能写和何时到期，不依赖模型判断 |
| 经历与事件 | 可去重、可追溯的事件记录 | 证明发生过什么；支持修复投影和恢复工作；保留期限按策略执行 |
| 摘要、画像推断、偏好 | 带证据、适用范围、源版本和更新时间的文档 | 支持跨会话复用，区分事实、员工确认和模型推断 |
| 查询索引 | 结构化索引 + 全文索引；有需要再补语义索引 | 精确检索与相似性检索用途不同，向量相似度不能决定任务状态和归属 |

通用元数据建议为 `tenant_id`、`object_type`、`object_id`、`source_ref`、`source_version`、`observed_at`、`updated_at`、`visibility_ref`、`content_kind`。摘要再记录覆盖的事件范围与生成版本；“红人平台、方向、画像”等放在业务对象 schema 中，不写成所有业务都必须有的平台字段。

同一红人跨平台、跨合作需要稳定主体 ID 与别名映射；不能仅凭昵称、邮箱本地部分或员工姓名绑定。谁负责某次合作与谁拥有整个红人的独占权限也应分开，独占范围由业务策略明确。

查询流程：登录身份 → 当前对象权限约束 → 已发布查询定义 → 结构化 / 全文 / 可选语义检索 → 读取允许的原文或摘要 → 展示来源、覆盖时间和更新状态。已知按钮或快捷指令不需要模型。任意自然语言不应承诺零模型：只有明确命中的指令别名和参数才直达查询，模糊意图使用轻量解析或澄清；平台不新增一批 KOL 专用正则来伪装通用能力。

“公海、待办、红人”等别名由业务包注册到通用 `query` / `command` / `extract` / `reason` 执行类型，并声明输入、数据源、权限、字段投影、时效策略与模型需求。查询只能绑定已授权的查询模板 / 工具，不能让用户或模型直接拼接任意数据库语句。

已知内容可直接返回，过期摘要注明覆盖时间并后台更新；没有摘要时明确说“尚未生成”，可提供生成入口。权限失效必须立即影响服务端的后续访问，不能等待全文 / 向量索引的异步刷新。摘要服务缓存应包含租户、主体 / 可见范围和版本，不能仅用红人 ID 做跨用户复用。

实现上可先复用现有关系库和增量读模型，无需立即拆多种数据库。SQLite 的 [FTS5 官方文档](https://www.sqlite.org/fts5.html)支持全文检索，但中文词语检索须单独验证分词和召回；不能默认英文切词适合中文。读写模型分离可以共用数据库，跨存储更新则需处理事件重复和同步延迟，见 [Microsoft CQRS 文档](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)。

## 建联、独占、14 天回公海

这是当前最需要确定性执行的业务规则，应由 KOL 业务包声明、通用关系与事件机制执行。平台懂“对象的排他关系和到期条件”，KOL 包定义“红人、员工、邮件往来和 14 天”。

建议的完整事件链：

1. **建立排他关系前先确定对象。** 必须有稳定红人 ID。若两人同时请求建联，在发送前以原子方式取得临时排他预留，避免两封邮件都已发出才争夺归属。
2. **依据业务定义确认建联。** 点击生成话术、创建草稿、收藏或加入候选跟进均不等于已经建立联系。“首次发送成功”还是“首次收到有效回复”代表正式建联，必须写进业务策略。本文以首次成功发送作为演示口径，未将此解释写入正式配置。
3. **确权并记录事件。** 依据工具回执确认归属和有效联系时间，写事件；普通其他员工不能通过列表、搜索、直接 ID、邮件、摘要、附件或分享访问该对象。管理审计例外由明确授权配置决定，不默认所有管理员都能读全部正文。
4. **新往来更新到期时间。** 按本轮“没有邮件往来”的字面口径，使用任一方向的有效邮件时间更新 `expires_at = last_valid_contact_at + 14 天`。草稿、失败发送、重复同步不算新往来；自动回复、退信和群发是否计入须在业务配置中明确。若目标是防止员工单方面反复发信占有，应改用“有效回复 / 双向互动”口径，而不是悄悄改变当前表述。
5. **持久调度并复核。** 到期工作项跨服务重启保留。执行前重读当前归属版本、最近有效邮件和数据同步覆盖范围；不能因为邮件连接器离线或同步落后，就把“没读到新邮件”当成“没有新邮件”。数据不确定时延后回收并提示异常。
6. **释放独占并发布公海投影。** 满足条件后原子释放归属、使旧授权失效，并刷新索引和到期任务。回公海释放的是当前独占关系，不删除历史、不自动改为“合作失败”，也不终止合同、履约、付款等事实。
7. **重新分配。** 公海中的允许字段对符合组织 / 品牌规则的员工可见；接收分配或领取后原子建立新归属。原员工的私人笔记、邮件正文和历史摘要不应因“回公海”全部公开；必要交接内容按业务策略单独授权。

关键实现条件：

- 使用事件 ID、消息 ID 和版本避免重复续期；以事件实际发生时间更新最近联系时间，不能按迟到消息的接收时刻重新计时。
- 回收与新邮件并发时须复核版本；已重新分配后的迟到邮件不能自动将对象夺回原员工，需要对账或人工处理。
- 外发超时而结果未知时保持待核实，先查询回执，不能立刻释放预留并让另一员工重复发信。
- 若 Starry 是归属权威源，须确认其支持条件更新 / 原子领取，或所有写入都服从同一权威服务；两个独立“负责人”存储相互覆盖无法保证独占。
- 若平台之外仍有人用可见全部红人的 Starry 账号操作，单靠本平台无法实现全系统不可见；需要远端 ACL 配合，或收敛访问入口。这是端到端成立的必要条件。
- 对象权限变更也要作用于旧会话、模型缓存和附件；已读取到旧内容的模型上下文不能继续作为新权限下的输入，必要时重新构建执行上下文。已被人下载的文件无法事后收回。

关系式授权是可行的技术基础：例如 [OpenFGA 的角色与权限建模](https://openfga.dev/docs/modeling/roles-and-permissions)将用户、关系和对象关联起来。此处引用的是设计方法，并不要求本项目立即引入 OpenFGA。

上述规则仍有上线前需由业务配置明确的参数：确权事件、独占是公司 / 品牌 / 合作哪一层、有效往来口径、是否覆盖履约中对象、公开与交接字段、重新分配方法。十条宪法不应锁定这些参数。

## 相对旧宪法的变化

旧愿景本来就承认中台与声明式业务，因此这次不是全面否定旧架构。主要变化是执行方式、记忆地位和宪法厚度。

| 主题 | 原来的规定 / 当前实现 | 新愿景建议 | 处理方式 |
|---|---|---|---|
| 产品身份 | [总纲](00-platform-charter.md)与[产品宪法 §4.2](CONSTITUTION.md)明确 KOL 是试点 | 保持平台身份，进一步剥离行业代码和对象字段 | 保留原则，补实现边界 |
| 所有生产读写走 turn | [技术宪法 §4](technical-constitution.md)要求生产读写经 Codex turn 调 MCP，快捷入口只锁 Skill | 查询、明确命令和事件可不经 turn；复杂语义交给模型 | **明确修改旧限制**，不将授权快速路径称为旁路 |
| 唯一 harness | 技术宪法将 Codex app-server 固定为唯一 harness | 宪法规定通用执行契约；当前仍可选 Codex 作为实现 | 将供应商与协议选择降为技术决策 |
| 全结果必须含 Thread/Turn | 总纲和技术宪法把它们设为所有结果追溯要求 | 所有操作有请求 / 事件 / 执行 ID；模型操作才附模型执行标识 | 保留追溯，取消无意义的会话依赖 |
| 记忆地位 | 手工记忆注入、业务缓存、邮件摘要分散 | 统一记忆访问契约、对象索引、时效、来源与权限 | 新增平台原则；复用既有数据，不重复造全量副本 |
| Host 不做业务调度 | 技术宪法禁止 Host 选 Skill、拼业务结果 | 仍禁止行业决策硬编码；允许通用查询分发与事件 / 策略执行 | 澄清“通用调度”与“业务决策”的区别 |
| 权限和自动化 | [产品宪法 §5](CONSTITUTION.md)对正式和敏感变更要求当次确认；[权限规范](org-permissions.md)有公司级管理范围 | 允许有明确范围、期限和版本的持续授权；普通员工可见范围依当前对象关系动态变化 | **自动回收改变权限，需先发布授权策略**；不可让模型临时越权 |
| 行业状态 | KOL 阶段、发送与阶段分离在平台宪法正文占较大篇幅 | 通用原则是副作用独立；KOL 的 15 阶段和 14 天规则进入业务包 | 行业规则下沉，保留其业务有效性 |
| 数据与知识 | 当前 `collaborations`、特定品牌、SOP、模板和阶段判断仍在 TS 中 | 行业对象 schema、规则、提示与视图由业务包 / 权威工具承载 | 分步迁移，不能只把代码改名成工具就算业务无关 |
| UI 与能力清单 | 产品宪法包含 16 项能力、具体路径、Tab、滚动、视觉链和 CTA 约束 | 十条宪法只保留工作连续、结果真实和能力边界 | 目录、设计系统、无障碍和页面约束保留在产品 / 设计规范，不因降级而删除 |
| A–K 多重权威 | [LAW-MAP](LAW-MAP.md)按领域设多份最终权威 | 一份短宪法 + 可执行契约 / 业务包 + 工程与设计规范；ADR 只记变更原因 | 若采纳需同步旧正文和校验入口，不能让新旧冲突长期并存 |

当前代码已经有首页和任务直接读取数据的路径，因此旧“所有生产读取都走 turn”与实现也不完全一致。新宪法应承认并规范授权快速路径，而不是继续让规范和代码各说一套。

具体需要补齐的隔离问题包括：`/pipeline`、`/projects`、`/cron/risks` 的合作读取未按新的独占关系过滤；`openKolSession` 按合作 ID 复用会话，没有按当前员工限定；邮件摘要和同步状态存在全局 / 合作级缓存。这里是源码识别到的新目标差距，不等同于已做真实环境越权验证。

## 可行性与迁移顺序

| 阶段 | 交付 | 验收边界 |
|---|---|---|
| 1. 固定宪法与契约 | 十条原则、执行四路径、权威数据源、业务包边界、记忆与归属契约 | 改成 7 天等业务参数只改策略；新增业务不要求改 KOL 正则 / 页面判断 |
| 2. 打通快速读取 | 我的任务、我的红人、任务摘要、邮件摘要四个已授权查询；复用现有存储构建索引 | 命中查询无 Thread/Turn 和生成调用；权限变更后旧索引不泄漏；可显示时效 |
| 3. 完成归属与事件闭环 | 独占预留、确权、邮件事件、持久到期任务、公海投影和重新分配 | 两员工同时建联只有一个成功；14 天回收不误处理同步故障；重启和重复事件不丢动作 |
| 4. 后台语义记忆 | 增量邮件、任务和合作摘要，证据关联、失效与重建 | 修改原文、纠正误关联、换负责人、删除来源时摘要和权限正确更新；模型失败不影响已存查询 |
| 5. 逐步提取业务包 | 将业务 schema、品牌、阶段、SOP、评分、推荐和视图语义迁出内核 | 以第二个小业务验证复用，不能只改文档宣布通用平台完成 |

可先在同一服务、同一数据库实现这些边界。第一阶段并不需要新的向量库、完整事件溯源架构或多套 Agent。每个业务写入和待处理事件可在本地事务中一起落库，再由持久工作进程消费；远端写入用幂等键、回执和对账处理，不能声称与本地更新处于同一个数据库事务。

建议的试点目标（待实际数据量、部署和负载测试验证）：命中本地快捷查询的端到端 P95 ≤ 300 ms；权限变化在提交后立即影响服务端后续读取；摘要变更采用单独的后台时效指标。统计命中率、源事件延迟、摘要覆盖与准确率、越权拒绝、重复动作次数、模型成本。不要在未经测量时承诺“毫秒级覆盖所有查询”。

现有实现可复用任务事件、邮件同步与摘要、技能声明、Gateway 和权限机制。主要工程量在统一身份与归属、让所有读取路径服从相同权限、可靠事件处理和业务规则迁出内核。真实外部 MCP 的归属条件更新与事件可用性仍需契约验证；本轮只读扫描没有对生产数据执行建联、回收、分配或权限变更。

## 宪法应短，执行契约不能含糊

建议使用 [十条草案](constitution-v2-draft.md)作为唯一顶层原则候选。产品能力目录、UI / 无障碍规范、工具协议和业务策略继续保留，但不另称“宪法”，也不重复发明顶层原则。

采纳时再一次性同步 `00-platform-charter.md`、`CONSTITUTION.md`、`technical-constitution.md`、`LAW-MAP.md` 和引用它们的发布校验；原有“所有读取必须经 turn”“所有结果必须带 Thread/Turn”等冲突条款需明确替换。十条文本缩短的是决策原则，不削弱对权限、一致性、来源与可验证性的要求。
