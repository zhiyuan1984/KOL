# 邮件技能：知识模板、编辑草稿与确认发送

**作者：Manus AI**

**实施基线：** `b879be3e00a1ba6c6df14ce0f42bda9f0557c6b7`，保留其祖先 `089a952` 已实现的邮件阶段契约、知识引用、会话互动及草稿结果卡。

## 实际使用流程

用户在现有输入框选择“写合作邮件”。Host 读取已经选定的合作对象和正式阶段；初步接触对应首封建联，不再把缺失阶段默认为初步接触。技能负责流程，信件底稿来自已启用、已发布且适用的知识库模板。技能规则仍由 `backend/skills/email_compose/SKILL.md` 提供。[1]

模板唯一适用时直接预填；同等适用的模板超过一份时显示候选，必须由用户选择。即使模板尚有变量未填，也显示可编辑的主题与正文。没有合作对象或适用模板时保留输入并提示补齐，不调用模型编造模板。

用户编辑后提交，中栏继续使用现有会话和任务消息流，右栏展示草稿及“确认发送”。右栏先保存修改，再读取服务端当前快照。确认弹窗展示发件人、收件人、抄送、主题及完整正文。点击确认前不调用实际发送接口；取消只关闭弹窗。聊天中的“确认发送”只引导用户查看右栏，不构成发送许可。

## 数据与接口

| 接口 | 作用 | 写入边界 |
|---|---|---|
| `POST /api/email-compose/prepare` | 确定合作上下文，选择已发布知识快照，返回编辑稿与缺失字段 | 不创建任务、会话、草稿或外部邮件会话 |
| 现有任务创建、运行与会话消息接口 | 接收 `knowledge_id` 和 `compose_input` | 生成或更新本地草稿，不发送 |
| `PUT /api/drafts/:id` | 保存用户修改并递增确认修订号 | 已发送、发送中或结果不确定的草稿不能修改 |
| `GET /api/drafts/:id/actions` | 返回完整发送快照与 `confirmation_version` | 只读，不绑定收件人，不建立发送尝试 |
| `POST /api/drafts/:id/send` | 确认当前版本并执行网关发送 | 必须携带 `confirmation_version` 与 `request_id`，不能夹带正文修改 |

编辑正文通过结构化输入传递，而非重新从提示词中猜测：

```json
{
  "intent": "email_compose",
  "knowledge_id": "已选模板ID",
  "compose_input": {
    "mode": "edited_draft",
    "knowledge_version": 1,
    "context_version": "prepare接口返回的上下文版本",
    "subject": "用户编辑后的主题",
    "body": "用户编辑后的完整正文",
    "variables": {},
    "source_draft_id": null
  }
}
```

`knowledge_id` 保持在原有顶层字段中。`compose_input` 固定本次使用的已发布版本，并保护人工编辑主题和正文。模型返回另外一份信件时，持久化草稿及结果卡仍采用人工提交内容。上下文变化或正文尚有占位符时返回明确错误，不静默更换收件人、阶段或模板。

知识表增加 `published_version`。运行时读取审批快照，不直接读取知识表中的最新编辑正文。知识编辑不会自动成为发布版本；旧选择器也使用相同的已发布快照。内置模板种子和既有发布历史补齐对应的发布指针。

## 发送安全与回执

发送前再次检查对象权限、技能权限、连接器写权限、知识适用范围、现有 PEP 规则及真实网关条件。`mail_send_attempts` 在事务中占用草稿，避免并发请求重复发送。同一确认版本和请求号重试时复用已保存回执；另一请求号不能重新发送已占用的草稿。[2]

成功回执先持久化，再刷新往来记忆。供应商响应不确定时标为 `send_unknown`，停止自动重发。必须先核实供应商回执，不能把“请求失败”当成“邮件一定未发送”。发送不推进正式合作阶段。

`mail-authority.ts` 提供进程内网关授权上下文。模型输入 `confirm_send=true` 或直接执行适配器不能代替网关授权；Codex 的现有工具白名单继续生效。适配器单元测试使用内部授权包装是测试隔离，不代表聊天文本拥有发送权限。

## 真实发送尚需配置与确认

**本次自动回归全部使用 Stub 或本地 HTTP 接口，没有对真实收件人发信。已连接的邮箱 MCP 可做只读查询，但不会自动把凭据传给克隆仓库中的应用进程。**

生产环境必须配置真实的品牌发件白名单。新增环境变量 `BRAND_MAILBOX_LT`、`BRAND_MAILBOX_RO`、`BRAND_MAILBOX_PQ`；未配置时保留原来的示例地址以兼容测试，但真实网关明确拒绝示例发件地址。只应配置已经在企业邮箱服务验证且归属该品牌的地址，不应将任意地址填进白名单。

其余真实运行配置继续复用项目现有的 Codex、Starry/MCP 连接与鉴权机制，以及 `LIVE_REMOTE_SIDE_EFFECTS` 和已有测试对象、测试收件人允许名单。不得为了跑通而绕过登录、对象权限、审批或允许名单。[3]

本轮真实邮件适配器仅确认了**单收件人、不带抄送、不带附件**的外发载荷。供应商 `DirectSendRequest` 的抄送和附件契约尚未得到验证，因此真实网关拒绝这些组合，避免弹窗显示的对象与实际外发不一致；不会悄悄丢弃抄送。需要这些能力的报价邮件等场景必须先完成供应商契约集成。

真实验收还需要指定受控收件人和合作对象，并由用户确认一封完整邮件。应用代码上线、真实邮箱连通和邮件送达是三个不同的验收项。不能把本地 Stub 回执或直接调用连接器的发信结果当成改造后应用已经端到端上线的证据。

## 本地复现

```bash
npm ci --prefix backend
npm ci --prefix frontend
npm run typecheck --prefix backend
npm run validate:contracts --prefix backend
npm run build --prefix frontend
npm test --prefix backend
cd frontend
E2E_PORT=8891 npx playwright test \
  e2e/mail-compose-flow.spec.ts \
  e2e/mail-confirmation-flow.spec.ts \
  --workers=1 --retries=0
```

浏览器测试启动项目既有的隔离后端，真实外发适配器关闭。测试涵盖未知上下文、多候选选择、缺变量草稿预填、异步响应不覆盖编辑、提交失败保留正文、Home/Chat 共享契约、取消不发送、完整快照确认以及确认过期拒绝发送。

后端新增测试涵盖准备操作只读、品牌与阶段适用、权限、未发布编辑隔离、发布版本固定、正文保护、对象上下文过期、发送去重、发送中编辑锁、未知回执，以及非网关发送拒绝。原来依赖聊天文本直接外发的测试已改为右栏确认协议，未削弱权限断言。

## 发布与回退

发布前应备份生产数据库，并先在受控测试对象上验证新协议。后端和前端需要同批部署：旧前端直接发送空请求会被新网关拒绝，这是有意的协议升级。

数据库改动采用增量字段和新表，不需要删除已有知识或草稿。如果需要回退，优先回退前后端应用版本并保留发送尝试与回执。**不得通过删除发送尝试、清除 `sent_at` 或把 `send_unknown` 改回草稿来“恢复发送”**，否则可能造成重复邮件。没有把本地修改直接合入主线，也没有擅自改变生产权限或外发开关。
