# 新审批中心接入正式本体治理审批

## 范围与根因

用户反馈新审批中心 `/approvals` 找不到 `appr_eb5335a2b424`，旧审批入口可以看到。新中心只读取 v2 `review_instances`，原 `ontology_change` 审批仍保存在正式 `approvals` 账本。此次修复仅接入既有、按当前身份过滤的审批投影；不将治理单复制成公司评审实例。

基线为已运行的 `e592d5d64746c71742ab1c67d91e1be82b0a9e9e`。此补丁堆叠于 PR #246 的真实终审账号指派热修复之上；不合并 main，不发布尚未批准的本体变更。

## 审查记录

需求 → 平台产品经理负责入口完整性，前端专家负责呈现和请求恢复，测试经理负责权限投影、导航与重复提交回归 → CONST-04/05/06/08/10 → BIZ-02/03/14、TECH-FE-01/03、TECH-BE-02/03、TECH-TEST-02/03/04、IA §1.1 → **符合**：沿用后端允许动作及原单稳定 ID，权限、正式决定、审计和治理事实均不改 → 完成浏览器模拟回归和构建后限定发布前端产物，并用真实账号只读核对新中心。

## 实施契约

- 同一审批中心区分普通公司审批与平台本体治理审批；保持普通审批原 cursor。
- 四个页签映射至正式账本的 `inbox / mine / processed / all`，对当前旧 API 的 `unknown_box` 仅兼容回退至 `submitted / done / 无 box`，返回权限始终由服务端决定。
- 只接入 `kind=ontology_change`；不推断审批角色、不扩大管理员权限，不根据姓名生成授权。
- 原单详情在 `/approvals?id=<原审批 ID>` 恢复，支持刷新、返回与浏览器返回；原 `/reviews/<原审批 ID>` 地址继续读取同一单。
- 范围、变更摘要、引用、基线和目标摘要只读呈现；正式同意和驳回继续调用原 `/api/approvals/:id/decide`，绝不调用 v2 创建或 commands。
- 允许动作同时检查服务端 `can_decide` 与 `allowed_actions`；驳回原因必填；确认展示当前版本与材料。
- 同一确认未改的 payload 重试复用幂等键；驳回原因变更是新 payload。版本冲突和未知回执先重读正式状态并关闭旧确认，不自动重试。
- 新入口不新增撤回权。后端未提供 `withdraw` 允许动作，所以本轮不加入撤回动作；旧中心原功能保留。
- 列表与详情错误分别表达；一方数据源失败不能伪装为两源都空，详情重试重读原 ID。
