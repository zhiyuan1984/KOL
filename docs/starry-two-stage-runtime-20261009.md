## 已实现

1. 当前候选版本及调用者技能/连接器授权校验后，按精确主页或平台+稳定账号查重。严格模式遇到查重失败、非列表结构或多命中明确停止，不作为重新建档理由。
2. 真实编号存在时复用，不要求候选邮箱，也不调用新建档。
3. 新候选无真实联系邮箱时，返回 `import_creator_no_contact_email`，保留已存在的跟进，不发送无编号 CSV。候选数据只能来自确认时的采集快照，任意请求参数不能注入邮箱或编号。
4. 需要建档时，使用员工已绑定的 Starry 邮箱解析有效负责人 openId；缺绑定/负责人则停止，不选第一只邮箱、不捏造编号。
5. 每个正式阶段提交前重查发布 Agent、工具绑定、L3/write 策略、候选版本和归属，先 `addKolProfile`，后带“红人统一ID”的 `importKolProfilesFromCrawler`。联系邮箱只用于真实建档，不进入平台资料 CSV。
6. 将检查点写入现有 `discovery_runtime_imports.receipt`，无需生产 schema 迁移：`preflight` → `add_uncertain` → `profile_ready` → `succeeded`。
7. 建档成功而补资料失败，持久保留正式 UID，下一次确认仅补资料，不重复建档。建档超时/进程中断时只做精确核对，空结果仍报不确定，不盲目重建。
8. 补资料超时不能用旧档案存在冒充本次写入成功；回传编号与确认编号不一致则拒绝改本地归属。
9. 采集结果归一化保留源数据实际提供的联系邮箱，不生成邮箱，不改已有生产候选快照。

## 精确权限资产

`backend/scripts/enable-discovery-add-profile.mjs` 只新增/启用 `(creator_discovery, starrykol, addKolProfile)`，保留原有工具政策版本及其他技能绑定。要求批准标记、保存原配置、事务写入并记审计 `runtime.skill_tool.updated`。脚本不会调用任何真实 Starry 写工具；重复运行不再增版本或写重复变更审计。

## 测试与验收边界

相关单元回归覆盖：真实邮箱/负责人/工具授权、已有精确编号、缺邮箱零外部写入、建档成功后失败恢复、未知建档不重发、严格查重失败/歧义、回传编号冲突、补资料超时不误报。

PostgreSQL 集成回归覆盖：两段式真实编排与检查点、独立入公海不取得个人跟进、缺邮箱保留同一 follow_id、权限撤销、确认门禁、失败恢复、归属冲突、历史 uncertain 路径、评分复用。所有外部工具均使用测试替身，数据库用例使用独立模板克隆测试库。

真实 Starry 写入闭环尚未验收。本轮不会自动重新提交 Outdoor Boys；该候选此前没有真实邮箱，仍需通过授权采集来源得到真实邮箱，或找到已有正式编号后，用户重新确认入库。部署只证明代码、权限配置及服务健康，不证明这个红人已入库。
