# 本人邮箱错误展示与诊断追踪（2026-10-12）

## 需求与审查

需求：继续排查本人设置页“无法读取可用邮箱”，准确展示真实失败并开始修复。

主责：后端实现分类与审计；前端实现安全展示；测试负责权限、错误分类和无副作用回归。

依据：[CONSTITUTION.md](CONSTITUTION.md) CONST-04/05/06/08/10；[TECHNOLOGY.md](TECHNOLOGY.md) TECH-ARCH-04、TECH-FE-02/03、TECH-BE-01/07/08、TECH-TEST-02/03/04；[BUSINESS.md](BUSINESS.md) BIZ-02/04；[DESIGN.md](DESIGN.md) 状态、恢复和诊断展开层；[org-permissions.md](org-permissions.md) 使用与治理边界。

结论：符合。只修复诊断与安全呈现，不生成品牌事实、不授予新权限、不自动启用服务、不修改凭据、不发信。后端没有可靠证据时返回 unknown 类原因，不伪造具体故障阶段或过期状态。

## 已核验原因

2026-10-12 17:28 生产本人邮箱读取返回 503 `starrykol_not_configured`。但组织配置存在，版本 26；连接器为 `verification_failed`、停用，上次 14:35 管理测试错误为 `runtime_remote_unavailable`。历史测试未保留具体 5xx 状态，因此不能回填猜测或说远端当前仍在失败。

直接缺陷：健康函数将配置存在与启用合并，服务层报错不准确；前端只从 Error.message 取码，未消费 payload.detail.code；邮箱路由把远端分类覆盖为一个通用错误；结构化 MCP isError 丢失业务码。

Larry 设置投影品牌为空、unverified 是独立归属问题，不能用本次服务连接修复证明品牌核验或发送授权。

## 本 PR 实施范围（P0/P1）

- 健康元数据新增 `config_present/enabled/ready/verification_status/config_version`，保留旧 configured 的 ready 语义兼容；连接器记录不存在时明确返回未配置，不抛无关健康异常。
- 区分真正缺配置、明确停用、测试失败后停用；没有组织启用就不发起邮箱远端调用。
- 邮箱 probe 输出 `settings-error.v1` DTO，保留安全码、业务文案、恢复类型、阶段、UUID请求编号和是否尝试请求；传输阶段目前为 `remote_request`，不声称能够区分 MCP initialize 和具体业务dispatch。
- 回归 401/403/404/429/具体5xx/timeout/unreachable；Starry明确业务登录码保留。远端401不会退出本平台账号。未知错误不回显原文。
- 仅对 Starry `pageMailboxes` 的托管 isError 引入类型化业务异常，其他业务网关保持既有行为；显式失败优先于外层成功或列表；无列表的无效回包不伪装成功空邮箱。
- 每次本人 probe 记录现有 audit_events 的 started/completed/failed；仅存白名单元数据，不存原文、URL、请求参数、Cookie、Key、JWT或凭据引用；不增加新表或 migration。
- 管理端独立诊断接口 `/api/admin/starry-binding/diagnostics/:requestId` 在首轮只允许管理员查看**本人请求**；其他管理员请求也返回404。跨用户诊断权限未开放，避免用admin角色代替租户范围。
- 组织测试新增唯一request_id/run_id与具体upstream_status，记入既有审计，不修改历史记录；测试失败停用、成功不自动启用规则保持。审查追加：非测试环境误设stub不能返回演示邮箱；真实配置缺失/停用优先解释，否则拒绝模拟运行；隔离测试仍允许mock夹具。
- Settings白名单读取payload.detail，显示准确业务摘要、可展开说明和安全编号；候选探测开始清理旧选项，失败不能继续绑定陈旧候选；成功不自动选择，空列表为info。
- unverified显示“品牌归属待核验”；旧“重新验证”改“重新读取”，避免列表查询冒充指定邮箱验证；读取成功只重新加载设置上下文，不更新核验事实或默认值。
- 管理端明确“已配置 · 测试失败后停用”，标注历史结果；5xx文案不再断言与本方配置无关。
