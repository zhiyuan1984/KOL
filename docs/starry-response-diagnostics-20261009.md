# Starry 入库回包诊断增量修复（2026-10-09）

## 需求与范围

用户提供 `discovery-dedup-score-from-212cd3b6(9).patch`，要求 Starry 建档失败时审计保留回包，并将明确的业务错误原文反馈给员工；成功但没有编号时按真实平台账号核对。

服务器已包含大部分发现去重和评分功能，本次只补缺失的 Starry 诊断与缺编号核对，以及核对预算（20 秒 keyword、60 秒 listAll、100 秒总预算）。不整包覆盖，不执行 `deploy.sh --sync`，不覆盖服务器已有知识库、任务页面等未提交工作，不执行数据库迁移或正式外部业务写入。

## 审查记录

- **需求**：真实失败原因、可追溯回包、无编号核对。
- **主责角色**：后端专家；测试经理负责验证证据。
- **宪法条款**：CONST-05（不扩大正式动作授权）、CONST-06（保留事实来源）、CONST-08（变更审查）、CONST-10（不以模拟测试冒充真实验收）。
- **基本法条款**：BIZ-01/10（稳定身份、真实编号、独立导入）；TECH-BE-03（真实回执、不盲重试）、TECH-BE-07/08（凭据保护、审计与员工脱敏结果）、TECH-TEST-01/03/04（影响范围验证与回滚证据）。
- **结论**：符合。诊断只增加回包观察与明确错误处理；保留平台与账号精确匹配、跨平台拒绝及多命中拒绝，不改变权限、跟进归属或合作阶段。
- **下一步**：隔离环境测试通过后增量发布；由用户针对原候选再点击「加入公海」，使用新回执或审计完成真实业务验收。

## 实现要点

1. `addKolProfile` 和 `importKolProfilesFromCrawler` 保留解析后的 Starry 业务回包外壳，其余工具的归一化不变。
2. `success: false`、`ok: false`、错误 `code/errCode/status` 优先于回包内编号、已知编号与核对结果；明确拒绝不再绕去查旧编号后报成功。
3. 支持外层及 `data/result/text` 内层的明确错误标记；保留 `0/200/success/ok` 成功码兼容。
4. 有错误文案时反馈 `Starry 建档未成功：<原业务文案>`；无文案时反馈明确拒绝，不伪造原因。
5. 审计字段 `starry_response` 保留解析后的业务回包，凭据脱敏，含截断标记在内最多 2000 字符；这不是 HTTP 原始字节或 MCP 传输报文。
6. 成功回包缺少编号时只进行只读核对；查询不到或核对失败仍诚实返回无编号，并保留原始业务回包。
7. 不重复建档或导入，不发送邮件，不解密，不推进合作阶段。

## 验证边界

新增单元回归覆盖明确失败、不同码型、嵌套错误、失败与编号冲突、已知编号不能掩盖失败、成功深层编号、缺编号核对成功/失败、原回包审计、2000 字符限长及凭据脱敏。原核对用例继续覆盖跨平台与模糊昵称拒绝。

模拟工具回包测试不等同于原候选的真实 Starry 写入验收。本次没有选择或写入未明确授权的候选；部署后需用户重试原对象。
