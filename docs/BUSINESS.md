# 业务基本法：KOL 全生命周期

制定角色：KOL 业务专家。上位法：[CONSTITUTION.md](CONSTITUTION.md)。本文件定义业务含义；平台负责承载，后端负责并发和一致性实现。条款是目标规则，当前实施差距见 [TECHNOLOGY.md](TECHNOLOGY.md)。

## 对象、来源与权限

### BIZ-01 对象与关系

区分线索、KOL 画像、合作关系、员工跟进关系、任务、邮件、报价、合同、样品、内容、结算、审批和风险。KOL 使用平台及稳定外部 ID 识别；同名、昵称相似或邮箱前缀相同不能认定为同一对象。

合作关系表达 `公司 + 品牌 + 活动 + KOL`。报价、正式阶段、合同、私有邮件与效果归合作关系；同一 KOL 可以有多条合作关系。排他跟进关系单独定义作用范围，不用合作阶段或邮箱负责人字段代替。

### BIZ-02 权威数据源

业务专家为每类业务事实指定来源、有效期和冲突处理口径。沿用试点已确认的分工：Starry 提供 KOL 域事实；组织 registry 与已确认外部绑定提供试点组织授权事实；工具返回的名单不能自行生成组织权限。

| 信息 | 来源与使用要求 |
|---|---|
| 公司、成员、品牌、区域、负责人授权 | 已确认的组织/品牌 registry 及外部绑定，后续可接入业务指定的组织系统 |
| 正式 KOL 档案、邮件、邮箱授权、生命周期 | Starry 对应记录、工具回执及版本；本地缓存记录其来源，不另立主数据 |
| 发现线索和平台采集数据 | 采集批次与原平台链接；导入成功前不能冒充正式 KOL 档案 |
| 本平台创建的任务、审批决定和执行审计 | 相应任务、审批及审计记录；外部任务保留外部来源，不能强行合并为同一任务 |
| 制度、费用档、汇率、报表口径 | 业务专家指定的现行制度和可信数据源，保留生效日期与版本 |
| 新增排他归属和 14 天有效互动时间 | 由业务专家确定写入系统及有效证据；不能自动把现有 owner 字段当作完整归属事实 |

摘要、评分、推断和测试夹具都不是正式业务事实。来源冲突时展示差异，按已定义口径处理；未定义时交业务专家裁定。

### BIZ-03 组织授权

公司、组织、品牌、区域、对象和动作共同决定权限。公司成员、组织成员、品牌职责、任务负责人及审批人是不同关系；人员不作为组织树节点，跨部门不复制账号。

保留安培时代已确认政策：部门负责人拥有本公司全部品牌、区域的普通业务读写范围；普通员工不得继承该范围，高风险动作仍需对应确认及审批。具体人员与品牌值引用 registry，不写入平台代码。管理职责、排他归属和审批权分别校验。

### BIZ-04 身份与邮箱

实际发件箱必须属于员工获准使用的品牌及范围；收件人必须来自已核实的联系方式。不得默认第一只邮箱、编造联系方式、用名字或邮箱前缀匹配代替授权。

保留 TB 的现有例外边界：本地品牌登记已接受，远端绑定缺失时不得执行依赖该绑定的写操作，也不得回退到其他品牌或邮箱；不因此阻塞无关品牌或只读工作。正式外部身份尚未补齐的字段按影响单独处理，不推翻已有确认。

### BIZ-05 建联与排他跟进

业务认定的建联事件成功后，建立员工与 KOL 的有效跟进关系。在该关系适用范围内，其他普通员工不可查看、检索或获取该 KOL 的受限资料；管理人员仅按 BIZ-03 的明确授权访问。

收藏候选、导入档案、打开会话、生成草稿均不等于建联成功。具体成功证据及排他范围由业务专家补入规则；不得由模型、平台产品经理或后端自行解释。同一排他范围内不得出现两名同时有效的归属员工。

### BIZ-06 14 天无互动自动回公海

有效跟进关系在连续 14 天没有有效邮件往来后自动解除，KOL 回到公海，按公海范围重新可见并可重新分配。新的有效邮件往来更新计时依据；后台执行不依赖员工打开页面，也不逐次要求人工确认。

执行前必须复核最新互动及当前归属，旧定时任务不能解除已经续期或重新分配的关系。数据源不可用或未同步完整不能等同于“没有往来”。“有效往来”、计时起点、日历口径与时区由业务专家明确后才启用相关自动动作。

### BIZ-07 公海与移交边界

回公海只改变跟进归属及配置允许的可见性，不自动删除历史、不等于合作终止、不自动改变正式阶段。公海公开字段和重新分配规则由业务专家定义；不能默认公开旧邮件、合同、价格和员工私有笔记。

主动转交、离职移交、撤销归属与重新领取应记录前后负责人、原因、有效时间和授权来源。原员工、接手员工及其记忆索引同步适用新的权限范围。

## 全生命周期 SOP

### BIZ-08 阶段与字典

沿用 15 个正式主阶段及一个异常节点；展示时可以折叠为 8 段，不能用展示分组替代写入码。代码及标签如下，详细字段由业务配置维护。

| 阶段码 | 含义 | 必须区分的事实 |
|---|---|---|
| INITIAL_CONTACT | 初步接触 | 首次接触不代表对方有合作意愿；跟进归属另按 BIZ-05 判断 |
| INTERESTED | 已回复、有兴趣 | 普通致谢、收悉不等于有兴趣 |
| EVALUATING | 合作评估 | 收集画像、受众和媒体包不等于谈妥合作 |
| QUOTE_PENDING | 报价待确认 | 询价、收到报价与认可报价不同 |
| NEGOTIATING | 商务谈判 | 金额、交付、授权、时间需分别核实 |
| PLAN_PENDING | 方案待确认 | 请求确认不等于双方已确认 |
| CONTRACTING | 合同签署 | 合同发送、审核与签署不同 |
| SAMPLE_PENDING | 待寄样 | 产品型号、数量与收件信息应符合寄送条件 |
| SHIPPED | 已发货 | 需要运单或明确发货证据，计划发货不算 |
| TESTING | 已签收、测试中 | 物流签收与本人确认分开记录，不捏造本人反馈 |
| CONTENT_PLANNING | 内容策划 | 记录 Brief、核心卖点及禁止表述 |
| CONTENT_REVIEW | 内容审核 | 提交初稿或仍有修改意见不等于审核完成 |
| PUBLISH_PENDING | 待发布 | 排期不等于已上线 |
| PUBLISHED | 已发布 | 核实发布证据、链接及交付完整性 |
| SETTLING | 结算中／已付款 | 收到发票、申请付款、付款成功分开记录 |
| exception | 异常旁路 | 暂缓、争议、拒绝、流失、取消等保留具体类型与原因 |

`COMPLETED` 作为结算后的结果，不增加为主阶段。远端旧码由适配器映射，不能改变业务含义。

### BIZ-09 SOP 内容与知识

每阶段说明目标、前置事实、所需资料、允许动作、完成证据、风险、审批、失败处理及人工接管。品牌策略、发现与评估、建联与谈判、合同与履约、内容审核、发布、效果复盘均纳入业务包。

保留长期合作场景：联盟邀请与链接配置、素材使用授权、复投、暂缓重启、终止及善后。开通联盟不等于产生订单；自然传播授权与付费广告授权分开；终止后仍处理样品、费用和素材责任。这些场景不强行增加主阶段。

### BIZ-10 发现与导入

发现、画像和筛选依据可追溯平台数据；评分注明依据、版本和不确定性，不能编造联系方式。筛选选项来自实际字典，提交稳定码，展示名称。

采集是可查进度、取消、重试的异步作业，采集完成只形成候选。员工确认后才导入正式库；按外部 ID 与来源批次去重，逐项记录成功、失败和真实 ID。部分成功不整批重做，缺邮箱不能通过编造邮箱解决。

### BIZ-11 草稿与发送

生成、改写和预览邮件不发送。沿用试点英文主题与正文、中文内部译文的草稿约定；切换语言依据明确任务或业务配置，内部译文不得意外发送。员工可修改草稿，确认对象必须是最后编辑版本。

发信前展示发件箱、收件人、主题、正文、附件及关键商务信息；缺少当前动作必需信息才补问，首次问候不强求报价金额。确认后由网关发送并取得真实回执；回执不确定时不得宣布成功或盲目重复发送。发送不改变正式阶段。

### BIZ-12 正式阶段变更

使用独立的 `confirm_stage` 动作，明确目标码、目标名称、证据及预期版本。人可以相邻前进、跨阶段前进、回退和进出异常；跨阶段、回退、进出异常必须写原因，不能只提供“下一阶段”一个目标。

进入 PLAN_PENDING、CONTRACTING、CONTENT_REVIEW、PUBLISH_PENDING、SETTLING 时还需相应审批。当前 Policy 要求正式阶段写入人工确认；自动边只是候选路径，不构成自动写入授权。未来启用事实自动写入时，需发布对应业务规则：只能基于已证事实按允许边推进，不跨过未满足前置、不替人纠错，不从终态异常自动恢复。

远程接口只支持相邻写入时，由技术适配处理或明确返回不支持，不能把物理限制改写为业务禁止跨阶段。

### BIZ-13 回复理解与风险

阶段判断证据优先级为正文明确动作、附件和链接、履约字段、邮件主题。输出证据、建议阶段、不确定性、风险及下一步；建议不直接改正式状态。

失联须结合实际互动日期，延期须结合原期限、原因和新计划，内容风险须说明未满足事项。“以后有空”不等于永久拒绝，个人突发事件不直接判违约。业务风险状态与 BIZ-06 的归属到期分别判断。

### BIZ-14 业务审批与敏感动作

发信、导入、解密、正式阶段修改、破坏性删除及其他生效动作应声明风险、确认要求、审批人和证据。L1 只读、L2 草稿、L3 正式或敏感动作是风险分类，不等于每项都走相同组织审批。预授权自动回公海按 BIZ-06 执行。

费用审批必须明确申请人、金额、币种、用途、制度版本、必要汇率及其日期和来源。采用业务指定的现行公司制度；公开搜索到的通用制度不能替代公司制度，固定代码金额或模型记忆不能补缺。报价确认与费用审批是不同事项，Agent 不得代人批准。

### BIZ-15 合规与履约

具体品牌、地区、平台的内容要求、广告披露、产品表述、素材使用、排他、合同及付款要求，应由业务专家以有来源和生效时间的规则发布。缺少规则或依据时标明缺口，不允许模型声称“已合规”。

审核应针对具体交付版本；实质内容、金额或授权条件改变后，旧审批不能自动覆盖新版本。审批拒绝记录理由；普通取消操作不强制套用拒绝流程。

### BIZ-16 任务与跟进

员工待办、跟进任务、风险任务应有负责人、对象、依据、期限、状态、摘要与下一步。邮件中的承诺、合同期限和风险事件可按发布规则创建或更新任务；未授权的 AI 建议保持候选状态。

任务完成依据任务验收条件；关闭会话、发送一封邮件、解除跟进关系都不自动完成关联任务。人工转办保留历史与责任变化。

### BIZ-17 报表与效果

预算、预计支出、合作进度、转化、履约、ROI 和人员工作量等指标必须定义范围、统计期、币种、来源、计算口径及更新时间。已发生、预测和模型解释分开；预算报告不执行付款或预算调整。

汇总、导出和快速查询仍服从当前数据权限。源数据不足时报告缺口，不用模型填造金额、订单、效果或员工绩效。

### BIZ-18 KOL 记忆索引

KOL 索引包含稳定 ID、平台、方向、画像、来源和更新时间；跟进索引包含员工、归属范围、关系状态、有效互动与到期信息。合作、邮件、任务、审批及报告摘要按各自对象关联，不将某次合作的价格当作 KOL 永久属性。

邮件摘要记录参与方、时间范围、关键约定、未决问题、下一步及原邮件引用；任务摘要记录目标、进度、风险和结论。正式状态、权限和金额必须能回到权威记录核验，不能只从摘要取值决定生效动作。
