# 本体的六个构件：定义与实例

> 整理时间：2026-10-01
> 口径说明：以下六个构件为讲解用拆分。Palantir 官方为四件套（对象类型/属性/链接类型/动作类型），其中事件归为对象类型的一种（"entity or event"），规则落在 Function 里。跟业务方讲语义时用六件套，跟 Palantir 对话时用四件套，意思一致。
> 实例统一用一套业务场景串联：客户A（深圳XX电子有限公司，编号 C-0088）、订单 SO-2026-1001、销售张三、财务经理李四。

---

## 1. 对象（Object）

**定义**：业务世界里的"名词"——一类有唯一标识的事物。Palantir 官方："An object type defines an entity or event in an organization." 区分**类型**（schema，如"客户"）与**实例**（如"客户A"）。

**实例**：
- 对象类型「客户」→ 实例：客户A（深圳XX电子有限公司，C-0088）
- 对象类型「订单」→ 实例：订单 SO-2026-1001
- 对象类型「设备」→ 实例：产线B的3号贴片机
- 对象类型「员工」→ 实例：张三（销售代表）

---

## 2. 属性（Property）

**定义**：对象类型的特征描述。Palantir 官方："A property defines the object type's characteristics." 每个属性有数据类型、有值、有数据血缘（来源系统、口径、新鲜度）。分**基础属性**（存进去的）与**派生属性**（算出来的）。

**实例**：
- 客户A.信用等级 = "A"（基础属性，来自 CRM）
- 客户A.逾期金额 = 128,000 元（派生属性，由规则实时计算）
- 订单 SO-2026-1001.状态 = "待审批"（基础属性，来自 ERP）
- 订单 SO-2026-1001.金额 = 560,000 元（基础属性）
- 3号贴片机.累计运行时长 = 1,203 小时（基础属性，来自 MES）

---

## 3. 关系（Link）

**定义**：两个对象类型之间的有向关联。Palantir 官方："A link type defines the relationship between two object types." 有基数（一对一/一对多/多对多），多随时间变化。

**实例**：
- 客户A —「下达」→ 订单 SO-2026-1001（一对多）
- 订单 SO-2026-1001 —「包含」→ 产品 12V100Ah × 200 件（多对多，关系上带"数量"）
- 张三 —「负责」→ 客户A（2026-01-01 起有效）
- 3号贴片机 —「属于」→ 产线B
- 供应商S —「供应」→ 物料磷酸铁锂电芯

---

## 4. 事件（Event）

**定义**：已经发生的**事实**，不可变、带时间戳、按时间有序。是对象状态变化的唯一合法来源——属性不被随手改掉，而是由事件触发规则重新计算（事件溯源）。

**实例**（按时间顺序）：
- 2026-10-01 09:00：「回款到期未到」事件（客户A，订单 SO-2026-1001，金额 128,000 元）
- 2026-10-01 09:01：「客户A被冻结」事件（由冻结动作产生）
- 2026-10-02 14:30：「催款函已发送」事件（张三执行）
- 2026-10-03 10:15：「回款已到账」事件（金额 128,000 元）
- 2026-10-03 10:16：「客户A已解冻」事件

链条：事件 → 规则 → 动作 → 新事件，每一步的"为什么"都可回放。

---

## 5. 规则（Rule / 约束）

**定义**：业务世界的"法律"。分**派生逻辑**（由其他数据计算得出）与**约束校验**（什么条件下允许/禁止什么）。

**实例**：
- 派生：客户.逾期金额 = SUM（该客户所有"已逾期"订单的未回款金额）
- 派生：客户.风险等级 = IF 逾期金额 > 100万 THEN "高" ELSE IF > 10万 THEN "中" ELSE "低"（客户A当前为"中"）
- 约束：订单金额 > 50 万，必须走「审批订单」动作
- 约束：客户存在逾期订单时，禁止为其创建新订单（或需财务总监特批）
- 约束：库存 < 安全水位时，该 SKU 自动标记「需补货」

---

## 6. 动作（Action）

**定义**：唯一能"写回"现实的出口。Palantir 官方："An action type defines how an object type can be modified." 每个动作规定输入参数、执行逻辑、**权限检查**、副作用（写回源系统）、**审计留痕**。铁律：**所有修改都必须走动作**。

**实例**：「冻结客户」
- 输入：客户ID（C-0088）、冻结原因（"逾期超30天"）、申请人
- 权限检查：仅财务经理及以上可执行，张三（销售）调用会被拒绝
- 执行逻辑：校验该客户确实存在逾期 → 将客户.状态置为"已冻结"
- 副作用：写回 ERP，冻结该客户的新订单受理
- 审计：记录"2026-10-01 09:01，李四（财务经理）因逾期超30天冻结客户A"
- 产生事件：「客户A被冻结」

同理：「审批订单」「创建补货单」「发送催款函」「解冻客户」都是动作。

---

## 六构件对照表

| 构件 | 回答的问题 | 性质 | 实例（一句话） |
|---|---|---|---|
| 对象 | 有什么 | 名词，静态 | 客户A、订单 SO-2026-1001 |
| 属性 | 什么样 | 形容词，静态/派生 | 客户A.逾期金额 = 128,000 元 |
| 关系 | 怎么连 | 动词（连接），半静态 | 客户A 下达 订单 SO-2026-1001 |
| 事件 | 发生了什么 | 事实，不可变 | 10-01 09:00 回款到期未到 |
| 规则 | 该怎样 | 法律，始终有效 | 逾期超 30 天 → 冻结客户 |
| 动作 | 能做什么 | 操作，受治理 | 冻结客户（财务经理权限） |

记忆口诀：**名词、形容词、连词、过去时、法律、动词**。
