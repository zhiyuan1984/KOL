# KOL 业务对象规则（Rule）清单

> 整理时间：2026-10-01
> 对照材料：[本体六构件-定义与实例.md](本体六构件-定义与实例.md) §5「规则」——规则 = **派生逻辑**（由其他数据计算得出）+ **约束校验**（什么条件下允许/禁止什么）；运行链条为 **事件 → 规则 → 动作 → 新事件**。

## 一、规则构件口径与项目法规的对照

### 1.1 「派生逻辑」的项目落点

| 六构件的派生口径 | 项目法规中的对应条款 | 对照说明 |
|---|---|---|
| 由其他数据计算得出 | BIZ-06（14 天计时）、BIZ-17（指标必须定义范围、统计期、币种、来源、计算口径及更新时间） | 项目法要求派生值写清口径与更新时间；口径缺失即报缺口 |
| 派生值须可追溯 | BIZ-10（评分注明依据、版本和不确定性） | 派生必须携带证据与版本，不得编造 |
| 推断类输出（模型判断） | BIZ-13（证据优先级、不确定性）、PROD-AGENT-04（模型判断记为「推断」，只有匹配来源证据才记为事实） | 推断是派生的一种，不自动成为正式状态 |
| 摘要与索引 | BIZ-18、PROD-AGENT-05／06／07 | 摘要绑定来源版本，可回读权威记录 |
| 汇总类（成本／用量） | PROD-PLAT-08 | 缺价格来源时只显示用量，不得以估算金额冒充账单 |

### 1.2 「约束校验」的项目落点

| 六构件的约束口径 | 项目法规中的对应条款 | 对照说明 |
|---|---|---|
| 什么条件下允许／禁止什么 | BIZ-04／05／10／11／12／14／15／16；[stage-transitions](../business-rules/stage-transitions.md) §3／§4 | 业务条件分布在对象、SOP 与阶段边各处 |
| 规则必须被执行 | CONST-03（确定的权限、审批和状态规则必须被程序执行）；TECH-BE-02（统一提交闸门） | 约束不能只靠模型自觉遵守 |
| 执行前核验与留痕 | TECH-BE-02／03、TECH-BE-08 | 版本、确认、审批、幂等、审计 |
| 责任、适用条件、可观察结果 | CONST-10 | 规则三要素，缺一不可 |
| 机器可执行 | stage-transitions §7（节点、边、原因和审批要求必须进入契约校验与发布门禁） | 机器配置与正文等价才可发布 |

### 1.3 泛例 → KOL 对照（六构件示例在本项目有无对应）

| 六构件的泛例 | KOL 项目的对应 | 状态 |
|---|---|---|
| 派生：客户.逾期金额 = SUM（已逾期订单未回款） | 无同构对象；最接近的是 14 天归属计时（BIZ-06）与报表指标（BIZ-17） | 计时口径部分空白；报表公式空白（见 §七） |
| 派生：客户.风险等级 = IF 逾期金额 > 100 万 THEN「高」… | 风险标签（延期／内容／失联；业务风险与归属到期分别判断，BIZ-13） | 判定原则已定义；现行正文未给出数值阈值 |
| 约束：订单金额 > 50 万必须走「审批订单」 | 进入 PLAN_PENDING／CONTRACTING／CONTENT_REVIEW／PUBLISH_PENDING／SETTLING 需叠加组织审批（stage-transitions §3）；费用审批要素见 BIZ-14 | 阶段审批已定义；金额分级依赖的费用制度来源为空白 |
| 约束：客户存在逾期订单时禁止为其创建新订单 | 排他范围内不得出现两名同时有效的归属员工（BIZ-05）；远端绑定缺失时不得执行依赖该绑定的写操作（BIZ-04） | 已定义（TB 例外按 BIZ-04 边界执行） |
| 约束：库存 < 安全水位 → 自动标记「需补货」 | 到期自动作业（BIZ-06 与 TECH-BE-05）；自动阶段边只能走主链 +1 或侧出口（stage-transitions §4） | 已定义；自动动作范围受更严限制 |
| 动作：冻结客户（权限检查／副作用／审计／产生事件） | `confirm_stage`、发信、导入、解密、归属变更、破坏性删除 | 闸门与留痕见 §5.9；审计字段见 TECH-BE-08 |

### 1.4 与三条宪法原则的关系

- **CONST-03**：约束校验类规则必须有程序执行点（网关、前置校验、阶段机器配置），不能只写在文档和提示词里。
- **CONST-05**：读数据、写草稿、执行正式动作分清；明确授权可覆盖已定义范围内的自动任务，但不扩大授权、不代人审批。
- **CONST-10**：每条规则都应能回答「谁负责、什么条件、可观察结果是什么」；本清单按此给出责任角色、条件与校验点；空白项如实登记，不代拟。

## 六、事件 → 规则 → 动作链条（KOL 实例）

1. **归属到期：** 新邮件往来（事件）→ 更新计时依据（D-01）→ 连续 14 天无有效往来 → 复核最新互动与归属（C-12）→ 释放归属（动作）→「归属已自动释放」事件 → 公海重新可见（C-14）。
2. **采集导入：** 员工确认后启动采集（动作）→ 采集完成（事件）→ 形成候选（C-16）→ 员工独立确认每批 → 网关导入（动作，C-17／C-18）→ 回执与真实 ID（事件）。
3. **发送邮件：** 人确认末版（动作前确认，C-25）→ 网关发送（动作，C-26）→ 真实回执（事件）；发送事件不写阶段（C-27）。
4. **阶段推进：** 回复邮件等证据（事件）→ 阶段建议与不确定性（D-02）→ 人 `confirm_stage`（动作，C-28～C-30）→（如需）组织审批 → 写入与审计（事件）；自动边只能 +1 或侧出口（C-31）。

以上链条中的「为什么」（证据、规则版本、确认人）均可按 TECH-BE-08 与 org-permissions 的审计字段回放。

## 八、实施级参考（非业务法）

- **机器配置与发布门禁：** 运行时阶段配置必须完整表达节点、边、原因和审批要求，并进入契约校验与发布门禁；机器配置与正文不一致时不得发布（stage-transitions §7）。规则配置的承载机制（注册、校验、预览、发布、停用、版本与回滚）见 PROD-PLAT-03。
- **工具风险目录与真实调用：** L1／L2／L3 工具分档、`sendEmailNow` 只能经用户确认后的 Gateway 提交、`changeLifecycleStage` 必须经 `confirm_stage` 提案后由 Host 写入，见 [07-mcp-data-contract.md](../07-mcp-data-contract.md)。
- **物理 ≠ 产品：** Starry 相邻 hop、逐格 walk、原生码映射是适配器物理限制，不得改写产品边（stage-transitions §6、07-mcp「物理适配」）。
- **物理门槛口径：** MediaCrawler 工具本身无 min-followers／min-views／min-score；门槛只在 Host 预览与写入前复核（07-mcp）。
- **实施与验收状态不写入本清单：** 实施状态以 [implementation-registry.md](../implementation-registry.md) 为准；测试与发布证据按 TECHNOLOGY TECH-TEST-01～04。
