# 概念落地对照表：总表

> 整理时间：2026-10-01（v3：知识库选型定为 Markdown + Git + 向量检索）
> 本篇是《企业智能体与本体论研究笔记》的拆分文件之一，给出全部概念的落地载体对照。
> 技术选型：codex harness 工程 + WikiSkill（经验知识）+ Markdown/Git 知识库（文档知识）+ 记忆（事件表+工单表+摘要）。

---

## 一、选型说明

- **codex harness**：agent 运行工程，承载 agent 定义、执行循环、上下文组装、skill 加载。
- **WikiSkill**：Google Research 2026-08 发布的技能进化框架（论文 arXiv:2608.27454），承载**经验知识**——raw（轨迹）→ wiki（patterns，永不回滚）→ skills（可执行 skill）。
- **文档知识库**：Markdown + Git 仓库 + harness 端向量检索。团队全工程师、文档全 Markdown：md 文件入库，版本管理天然就是 Git（PR 评审、历史、回滚），harness 端接向量检索供 agent 查。
- **记忆**：事件表（业务事件）+ 工单表（任务记录）+ 摘要（压缩层）。

---

## 二、WikiSkill 的正确理解

> WikiSkill 不是"人写 wiki 文档给 agent 当 skill 用"，而是**把 agent 执行经验自动编译成持久知识、再从知识里生长出可执行 skill** 的框架。管的是**经验知识**，不是文档知识。

### 三层架构

1. **raw/（原始轨迹层）**：只读不可变。每次任务的完整交互历史——推理思考、工具调用输入输出。
2. **wiki/（持久知识层）**：轨迹编译成的结构化知识——`patterns/`（成功策略/失败模式）、`log.md`、`skill-impact.md`。**永不回滚**。
3. **skills/（程序技能层）**：可执行的过程性知识。每个技能含 `SKILL.md` + `PURPOSE.md`（记录该 skill 为解决 wiki 里哪个 pattern 而存在）。**可回滚**。

### 进化循环

Inference（跑轨迹，禁读 wiki）→ Wiki Maintainer（提炼 pattern）→ Skill Proposer（ReAct 提案，禁重提被拒改法）→ 验证门控（只回滚 skill，wiki 保留）。

### 为什么文档知识不能进 WikiSkill

1. 写入者冲突：wiki/ 只接受轨迹提炼，塞入人工文档会污染进化循环；
2. "永不回滚" vs "政策会过期"：政策 v3→v4 旧版必须失效，语义冲突；
3. 溯源链断裂：skill ← pattern ← trace，政策文档接不上这条链。

文档知识的三种正确用法：冷启动输入（SOP → 第一版 SKILL.md）、执行时引用（skill 写"按《退货政策 v4》执行"，不抄全文）、建模原材料（文档 → 本体对象/规则）。

## 三、总表：概念 → 落地载体 → 最简方案

| 概念 | 落地载体 | 最简方案 |
|---|---|---|
| 任务 | 工单 | 工单系统，任务即工单 |
| 本体 | 对象注册表 | Excel/YAML + Git 版本管理：对象、属性、来源、口径 |
| 对象/属性 | 数据库表 | 对象类型=表，属性=字段 |
| 关系 | 外键/关联表 | 先外键，复杂网状再上图库 |
| 事件 | 事件日志表 | 时间+类型+主体+载荷（JSON） |
| 规则 | 规则配置表 | 条件-动作表 + 定时跑批；约束写进动作 API 前置校验 |
| 动作 | API 接口 | REST API + 权限中间件 + 操作日志 |
| Skill | WikiSkill skills/ 层 | `SKILL.md` + `PURPOSE.md`，从 wiki/patterns 生长，可回滚、可溯源 |
| 智能体 | codex harness 工程 | 模型 + prompt + skill + 工具，不自研框架 |
| 知识库（文档） | Markdown + Git + 向量检索 | md 入库，Git 管版本（PR 评审/历史/回滚），harness 端向量检索供 agent 查 |
| 经验知识 | WikiSkill（raw/wiki/skills） | 轨迹→patterns→skill 进化，wiki 永不回滚 |
| 记忆 | 事件表 + 工单表 + 摘要 | 业务记忆三件套；wiki/patterns 可作经验记忆补充 |
| 实时上下文 | harness 上下文组装 | 任务触发时按模板查表拼 prompt |
| 调度系统 | 派单规则 | 工单派单规则（skill 标签匹配+负载轮询）+ 定时扫超时升级 |
| 执行系统 | codex harness 执行循环 | 推理→调工具→收反馈 |
| 接入系统 | 连接器 | 每个源系统一个 API 适配器 |
| 控制系统 | 权限表+审批+审计 | RBAC 权限表 + 现有审批流 + 操作日志表 |

## 四、收敛：17 个概念 → 6 个载体

1. **codex harness 一框多用**：agent 定义、执行循环、上下文组装、skill 加载、向量检索——智能体、执行系统、实时上下文、文档检索落地时是同一个工程。
2. **Git 一库多用**：文档 md、SKILL.md、对象注册表 YAML 全放 Git，版本、评审、回滚走同一套 PR 流程。这是全工程师团队的红利。
3. **WikiSkill 三层一体**：经验知识的完整闭环——raw 存轨迹，wiki 存提炼的方法论，skills 存可执行能力。
4. **事件表一表三用**：触发器（调度看它）、账本（控制记它）、记忆源（回忆查它）。
5. **工单表一表三用**：任务（干什么）、调度（派给谁）、承诺账本（摘要的原材料）。
6. **PURPOSE.md 是审计神器**：每个 skill 回溯到"为解决哪个 pattern 而存在"，变更有理由、有记录，满足控制系统的账本要求。

## 五、知识形态与载体总览

| 知识形态 | 回答 | 载体 | 例子 |
|---|---|---|---|
| 结构知识 | 世界是什么样 | 本体（注册表+表+规则表） | 客户对象、"逾期金额"算法 |
| 文档知识 | 书上怎么写 | Markdown + Git + 向量检索 | 退货政策、操作手册、合同 |
| 经验知识 | 这事该怎么做 | WikiSkill（raw/wiki/skills） | "催收先查全貌再定话术" |
| 事实知识 | 发生过什么 | 事件表 + 工单表 + 摘要 | 回款记录、处理历史 |
| 隐性知识 | 老员工脑子里 | 人 → 待 SOP 化 | 老师傅的直觉 |

**承载分散，访问统一**：harness 做统一检索路由——问事实查表，问方法查 wiki/patterns，问政策查文档库。agent 永远只面对一个入口。

**知识飞轮**：隐性（人脑）→ SOP（文档）→ SKILL.md（冷启动）→ raw（轨迹）→ patterns（提炼）→ 新版 skill（进化）。每一轮执行都在给企业知识加砖。

---

## 六、冷启动与落地顺序

1. **先立三张表**：对象注册表 + 事件表 + 工单表——地基。
2. **再通连接器**：接 1-2 个核心源系统，事件流先跑起来。
3. **文档入库**：第一个场景的 SOP 写成 md 进 Git，人先用。
4. **人写第一版 skill**：SOP → SKILL.md，跑出 raw 轨迹。
5. **harness 上岗 + WikiSkill 接管进化**：规则表、动作 API、向量检索同步上。
6. **最后加摘要和调度规则**：量起来后，摘要压缩、派单规则、超时升级跟上。

---

## 七、四条军规

1. **先人后机**：skill 先让人跑通 SOP，再给 agent，再让 WikiSkill 进化。
2. **一表多用**：事件表、工单表能复用的绝不另起新表。
3. **买的不造的**：工单、审批用现成；自研只留对象注册表、规则表、连接器、harness。
4. **一个场景打透**：第一个场景跑通进化闭环之前，不开第二个。
