## 0. Link 定义（引自本体六构件 §3）

> 两个对象类型之间的有向关联。Palantir 官方："A link type defines the relationship between two object types." 有基数（一对一/一对多/多对多），多随时间变化。

书写格式沿用其示例：`源对象 —「关系动词」→ 目标对象（基数；约束）`，并补一列「依据」，保证每条 Link 可回溯到现行正文。

三点口径说明：

1. 六构件严格区分「属性」与「关系」；凡在 KOL 项目里以**值/枚举**形式承载、但对关系图有意义的连接（如阶段的当前值、风险标签），本篇按 Link 记录并注明承载方式。
2. 关系分正向与**负向（禁止性连接）**两类；负向关系单列 §3.9，因为「发送不推进阶段」这类禁令本身就是最重要的业务连接之一。
3. 对象命名沿用[《KOL业务对象清单》](KOL业务对象清单.md)清单 B：本清单的「KOL」即其 B2「KOL 画像」，「线索 / 候选」即 B1「线索（发现候选）」，「跟进关系」即 B4「员工跟进关系」；两处不一致时以对象清单与 `docs/` 正文为准。

## 1. 与宪法法规及六构件通用示例的对照

### 1.1 六构件通用示例 → KOL 落点

六构件讲解稿用「客户—订单—产品—设备—供应商」的通用例子。KOL 项目没有这些对象，逐条对应如下：

| 六构件通用示例 | KOL 项目对应 | 说明 |
|---|---|---|
| 客户A —「下达」→ 订单（一对多） | KOL —「建联 / 排他跟进」→ 员工 的**跟进关系**（BIZ-05） | KOL 项目无「客户 / 订单」对象；建联成功后才建立有效跟进关系，「收藏候选、导入档案、打开会话、生成草稿」都不等于建联成功 |
| 订单 —「包含」→ 产品 ×200 件（关系带"数量"） | **合作关系** —「承载」→ 报价 / 合同 / 样品 / 内容 / 结算 / 私有邮件 / 效果（BIZ-01） | 商务与履约事实挂在合作关系上；价格、阶段、邮箱、合同、负责人、ROI 不挂全局 KOL |
| 张三 —「负责」→ 客户A（2026-01-01 起有效） | 员工 —「排他跟进」→ KOL（自建联起有效；14 天无有效往来自动解除） | 负责人 / 执行人 / 审批人是不同关系，不可合并成一个 `owner_id` |
| 3号贴片机 —「属于」→ 产线B | **邮箱** —「品牌归属」→ 品牌；**组织单元** —「上级」→ 上级组织 | 结构归属类关系的对应物 |
| 供应商S —「供应」→ 物料 | **采集批次** —「产出」→ 候选线索；**连接器** —「提供」→ MCP 工具 | 供给 / 产出类关系的对应物 |
| 事件 → 规则 → 动作 → 新事件 | 邮件 / 履约事实（签收、发布、付款）→（证据优先级 BIZ-13）→ 建议阶段 → confirm_stage / 确认发送 → 新事件与审计 | KOL 侧承认同一链条，但正式状态只能由唯一写入口改，发送永不写阶段 |

补充：六构件「所有修改都必须走动作」「事件不可变、带时间戳」在 KOL 项目的落点是——确定的权限、审批和状态规则由程序执行（CONST-03）；唯一官方阶段写入口是 `confirm_stage`（BIZ-12）；外发 / 导入 / 解密 / 删除执行前必须确认并留有回执（CONST-05、BIZ-14）。

### 1.2 与宪法法规的对照要点

| # | 本体口径（研究笔记） | 本项目法条 | 对照结论 |
|---|---|---|---|
| 1 | 关系 = 两个对象类型之间的有向关联，有基数 | org-permissions §关系模型（六类关系不得合并成 `owner_id`）；BIZ-01（合作关系 = 公司 + 品牌 + 活动 + KOL） | 一致；本项目另有排他唯一性（C-08）与 `owner_id` 禁令（N-04） |
| 2 | 关系多随时间变化 | BIZ-05/06（建联起效、14 天到期）；组织成员关系的任期（A-02） | 一致；时间维由业务条款规定，不由模型推断 |
| 3 | 动作是唯一写出口；事件是状态变化的唯一合法来源 | CONST-03；BIZ-12（`confirm_stage` 唯一官方写入口）；BIZ-13（建议不直接改正式状态） | 一致；正式阶段写入另受 Policy 人工确认 |
| 4 | 通用模型之外的附加治理约束 | CONST-05；BIZ-11/12/14；docs/AGENTS.md §5（发送 ≠ 阶段、L1–L3 闸门、回执） | 附加约束，单列负向关系 §3.9 |

## 3. Link 清单

缩写：**ORG** = `../org-permissions.md`；**ST** = `../business-rules/stage-transitions.md`。基数：`1→N` 一对多、`N↔N` 多对多、`N→1` 多对一；「备注」标记：〔规则空白〕= 条款已登记待补、〔物理适配〕= 远端限制、不得升格为产品法。

### 3.1 域 A：组织、成员与授权

| # | Link | 基数 | 约束与时变 | 依据 |
|---|---|---|---|---|
| A-01 | 员工 —「company_membership（公司成员关系）」→ 公司 | N→1 | 用户属于哪个租户；跨部门不复制账号；人员不是组织树节点 | ORG §关系模型/§层级；BIZ-03 |
| A-02 | 员工 —「organization_membership（组织成员关系）」→ 组织单元 | N↔N | 主组织 / 协作组织、任期和岗位 | ORG §关系模型 |
| A-03 | 组织单元 —「parent（上级）」→ 组织单元 / 公司 | N→1 | 组织树；部门负责人关系以已确认组织证据和 registry 绑定为准 | ORG §层级 |
| A-04 | 员工 / 组织单元 —「brand_scope_membership（品牌范围）」→ 品牌 + 区域 | N↔N | 可服务哪些品牌和区域；部门负责人按公司政策自动为全部范围；普通员工不得继承 | ORG §关系模型；BIZ-03 |
| A-05 | 员工 / 角色 —「responsibility_assignment（职责分配）」→ 业务域 / 品牌 / 活动 | N↔N | 对目标和规则负责；如 `resp:kol_business_owner` → `user:liu_min` | ORG §关系模型；org-registry.yaml |
| A-06 | 员工 / 团队 —「task_assignment（任务分派）」→ 任务 / 工作项 | N↔N | 当前执行责任；人工转办保留历史与责任变化 | ORG §关系模型；BIZ-16 |
| A-07 | 员工 / 角色 —「approval_assignment（审批权）」→ 动作 / Policy | N↔N | 某次高风险动作的审批权；管理职责、排他归属和审批权分别校验；角色 ≠ 数据范围 | ORG §关系模型/§角色；BIZ-03 |
| A-08 | 员工 —「starry_binding（个人邮箱绑定）」→ 邮箱 | 1→N | 个人设置维护；未指定发件箱时的默认解析起点，仍须品牌与范围核对通过 | ADR-2026-09-28；BIZ-04 |
| A-09 | 邮箱 —「brand_affiliation（品牌归属）」→ 品牌 | N↔N | 邮箱按品牌登记（LT/RO/PQ）；远端缺 TB 时不回退到其他品牌或邮箱 | domain-objects §2.4；BIZ-04 |
| A-10 | 邮箱 —「responsible_owner（负责人）」→ 员工 | N→1 | 负责人状态：在职 / 已移交 / 停用；已移交保留记录 | domain-objects §2.5 |
| A-11 | 技能授权 —「granted_to（授予）」→ 员工 / 角色 | N↔N | **人员授权唯一单位＝技能**；连接器 / MCP 工具不按人授权；管理员也不能绕过运行时闸门 | ADR-2026-09-27；PROD-PLAT-05；CONST-05 |

### 3.3 域 C：归属、跟进与公海
