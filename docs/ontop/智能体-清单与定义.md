## 一、口径：什么算一个「智能体」

研究笔记 §三 给出的企业定义是：**以模型为决策核心，以企业本体、知识、实时上下文和记忆为认知基础，通过 Skill 与受治理的动作完成业务任务，并接受权限、审计和人类责任边界约束的软件系统。**

落到本项目，这个定义拆成三个可核验的部分。

### 1.1 判定四问（四问全「是」才是运行体智能体）

| # | 判据 | 出处 | 本项目落点 |
|---|---|---|---|
| 1 | **有被委托的目标与交付**——能执行、干活、交付，不只是回答问题 | 李开复核心判据；OpenAI「代表用户独立完成任务」 | 任务、工作项、运行记录、成果分开保存（PROD-AGENT-08、PROD-AGENT-09） |
| 2 | **下一步由模型动态决定**，而不是走固定代码路径 | Anthropic《Building Effective Agents》：由代码编排的是 Workflow，由模型决定下一步并掌控工具的才是 Agent | 判据的分水岭在本项目可观察：有工具、可多步、由入口决定是否思考 = 智能体（CONST-07、PROD-AGENT-01）；Host 锁定 task_type、单次调用、`mcp` 为空 = 工作流（**本仓实例见 §四 A2**） |
| 3 | **有认知底座四件**：本体（地图）+ 知识 + 实时上下文（导航）+ 记忆 | 李开复「大脑 / 地图 / 导航」；CONST-06 | 对象与规则（见对象、属性、关系、事件、规则五份清单）、知识库、按任务组装的上下文、KOL 索引与跟进索引（BIZ-18） |
| 4 | **有受治理的动作与责任边界**：权限、审计、人批准、留痕 | 综合定义「接受权限、审计和人类责任边界约束」；CONST-05、BIZ-14 | L1 只读 / L2 草稿 / L3 正式或敏感动作；确认、审批、幂等与回执；Agent 不得代人批准 |

### 1.2 两条本项目独有的结构性约束（决定「不能怎么数」）

- **共用一份运行内核**：Agent 不拥有独立运行时，所有 Agent 共用同一个平台内核与 Codex harness，只通过配置改变能力、数据范围和策略（CONST-03、TECH-ARCH-03「Agent 不等于独立进程」、[domain-objects.md](../domain-objects.md)）。因此智能体是**配置**，不是进程；数量不随部署、租户或品牌增长。
- **对外能力面只有技能**：连接器、MCP 工具与 API 是平台内核能力，只对技能与后台任务开放；人员授权只对技能（CONST-02 2026-09-27 修订、PROD-PLAT-04/05、ADR-2026-09-27）。因此**不得按工具或按部门应用各数一个「智能体」**。

### 1.3 一条排除（李开复的批判）

> 「没有企业知识地图，所谓智能体只是给通用模型加了一层很薄的外衣。」

只给通用模型套一层提示词、没有本体与记忆、也回答不出「它改变哪个交付物」的，**不算智能体**，只能算提示词模板或固定流程；把它登记成智能体属 CONST-10 禁止的「用文档、占位页面或模拟结果冒充能力」。

### 1.4 四层计数：回答「有多少个」

本仓把四类不同的东西都叫「智能体 / Agent / 专家」，所以先分层、再计数（依据见 §四～§七）：

| 层 | 是什么 | 计数判据 | 现值 |
|---|---|---|---|
| L0 | **运行内核**：模型 + Codex harness + 本体 + 记忆 + 工具与闸门 | 不是智能体；全平台唯一一份 | **1 套** |
| L1 | **运行体 Agent**：调模型、跑 turn、产交付物、有运行记录与成本 | 发布包 `agents/<id>/manifest.yaml` 且 status=production；是否**符合定义**另按 §1.1 四判据逐条判定 | 发布包 **2 个**；按判据符合定义的 **1 个**（`agent:kol`），另 1 个是绑定载体（§四 A2） |
| L2 | **岗位身份（数字员工 / 岗位专家）**：面向员工的召唤面，含入口契约与技能包 | 发布包 `experts/<id>/manifest.yaml` 且 status=published | **3 个** |
| L3 | **责任角色**：CONST-04 的决策与立法角色，可以由人或专家 Agent 承担 | 宪法角色表；须标明以哪个角色作决定 | **9 个**（当前 0 个由 Agent 承担） |
| L4 | **数字团队**：编排层 | 有表面才算交付（ia §2 #3 预留） | **0 个**（仅 6 条候选登记，无表面） |

**一句话结论**：**符合智能体定义、能干活能交付的运行体只有 1 个——`agent:kol`。** 仓库里还有第二个 `agent:*` 发布包（`agent:workspace-planner`），但按 §1.1 四判据逐条判定，它是 **Host 编排的受限工作流**（单次模型调用、`mcp` 为空、无副作用），`agent:*` 身份在那里承担的是**技能运行绑定与成本归属**，不是「又一个智能体」；员工可召唤的岗位数字员工 **3 个**；数字团队 **0 个**（预留未实现）；宪法责任角色 **9 个**，目前全部由人承担。

## 二、定义设计：定义卡与准入门槛

### 2.1 定义卡（每个智能体必须能回答的八项）

| # | 字段 | 回答什么 | 本项目依据 |
|---|---|---|---|
| 1 | id 与命名 | `agent:<slug>` / `expert:<slug>`，版本与状态位 | 发布包必须声明 ID、版本、责任人、范围、依赖（TECH-ARCH-04） |
| 2 | 目标域与交付物 | 它改善哪个交付物或哪张报表 | 李开复追问；PROD-AGENT-08 |
| 3 | 认知底座范围 | 读哪些本体对象、哪些知识、哪些记忆 | CONST-06、PROD-AGENT-04/05/06/07、BIZ-18 |
| 4 | 技能包 | skills + workflows | domain-objects；BUSINESS 技能覆盖表 |
| 5 | 入口契约 | 从哪几类入口被唤起（思考 / 快捷 / 后台 / 受控命令） | CONST-07、PROD-AGENT-01、TECH-ARCH-02 |
| 6 | 责任边界 | 可写范围、L1–L3 分档、需确认或审批的动作、是否允许外部写入 | CONST-05、BIZ-14、07-mcp 工具风险目录 |
| 7 | 组织与范围 | org × brand × region，成本归属 | org-permissions；PROD-PLAT-08 |
| 8 | 发布门与证据 | 发布状态、评价集、暂停与恢复、验收证据 | TECH-TEST-01~03、CONST-10 |

定义卡的作用是：**同一份字段既能定义一个 `agent:*`，也能定义它的岗位投影 `expert:*`**——二者共享第 1～7 项，L1 多一层运行与成本归属，L2 多一层面向员工的召唤文案与入口。

### 2.2 准入门槛（回答「以后该不该再多一个」）

| 新增对象 | 门槛 | 不满足时 |
|---|---|---|
| L1 运行体 | 新的目标域 **且** 新的责任边界 | 只是给现有 Agent 加技能，不加智能体 |
| L2 岗位身份 | 新的入口契约或岗位责任（不能只是换一组提示词） | 只是快捷提问集合 |
| L3 责任角色 | 由用户修宪（CONST-09 编号固定，删除保留废止记录） | 不得自行增设 |
| L4 数字团队 | 有表面，且编排真的产出交付物 | 即 ia §4 禁止的「专家团假导航」 |

**李开复式追问**：这个新智能体改变哪个交付物或哪张报表？答不出来就不立新智能体——这正是他对「几百个客服、法务、财务 Agent 却改变不了财报」的批评。

**反向也成立**：为绑定技能、归集成本或挂发布门而需要一个 `agent:*` 命名空间时，那只是**技术登记**，不构成「多了一个智能体」；此时应写明它是工作流载体（本仓实例：§四 A2），避免治理面把登记数当成智能体数。

## 三、与宪法法规的对照要点

| # | 研究笔记口径 | 本项目法条 | 对照结论 |
|---|---|---|---|
| 1 | 能执行、干活、交付，不只是回答 | PROD-AGENT-08（任务与对象分开）、PROD-AGENT-09（排队/执行/失败/取消可见）、TECH-ARCH-02（三种调用链） | 一致；本项目把「交付」落成运行记录 + 成果 + 终态与恢复入口 |
| 2 | 下一步由模型动态决定，而非代码路径 | CONST-07（两类入口、两类界面）、PROD-AGENT-01（入口决定路径，路由类型显式登记） | 一致；快捷指令、受控命令、后台事件明确不是「模型思考」 |
| 3 | 记忆、实时上下文是智能体的组成部分 | CONST-06、PROD-AGENT-04～07、BIZ-18 | 一致；记忆保存可复用偏好与摘要，读取时遵守当前权限并保留来源与版本 |
| 4 | 本体（企业业务语义）是地图，缺失则只是薄外衣 | CONST-02、PROD-PLAT-03、domain-objects | 一致；本项目的地图由对象注册表与业务规则承载（见五份清单），项目/活动实体仍是 Phase 2（implementation-registry PROJ-01） |
| 5 | 多智能体讨论、辩论、碰撞出更第一性原理的答案 | **无对应条款** | **规则空白**：现行 PRODUCT 只规定单会话 Agent 交互；数字团队为预留能力。本清单只登记，不代拟 |
| 6 | AI 不能担责；DRI 管理一批 AI 员工 | CONST-05（明确授权可覆盖已定义范围内的自动任务，模型不得扩大授权、代人审批）、CONST-04（同一人兼任仍须标明以哪个角色作决定） | 一致；本项目把「担责」落成确认、审批、审计与责任角色 |
| 7 | Agent 不拥有独立运行时 | CONST-03、TECH-ARCH-03 | 一致；本项目进一步规定共用 Codex harness，不按业务搭第二套推理循环 |
| 8 | 对外能力应是可治理的能力，而非一堆工具 | CONST-02（2026-09-27 修订）、PROD-PLAT-04/05、ADR-2026-09-27 | 一致；人员授权只对技能，连接器与工具不对员工暴露 |

**补充**：李开复「地图 / 导航 / 操作系统」三件在本项目对应 **本体与规则（地图）→ 按任务组装的上下文与记忆（导航）→ Host + Codex harness + 闸门（操作系统）**；三者是 L0 内核的组成，不是智能体本身。

## 四、清单 A：`agent:*` 发布包（登记 2 个；按定义符合 1 个）

**先分清两件事**：`agent:*` 发布包是**登记事实**（仓库全量扫描 `find . -name manifest.yaml` 只有下列两个），而「是不是智能体」是**行为判定**（§1.1 四问）。二者不必一致——**判据 2 正是分水岭**。

| 发布包 | 登记 | 按四问判定 | 结论 |
|---|---|---|---|
| `agent:kol` | status=production | 四问全中（有工具、可多步、受治理动作齐备） | **运行体智能体** |
| `agent:workspace-planner` | status=production，`kind=platform` | 判据 2、4 不满足，判据 3 部分满足（`mcp: []`、`side_effects: none`） | **Host 编排的受限工作流**；`agent:*` 身份承担技能运行绑定与成本归属 |

| 定义卡字段 | 内容 | 证据 |
|---|---|---|

**四判据逐条判定（这是本节的关键）：**

| # | 判据 | 实际情况 | 证据 |
|---|---|---|---|
| 1 | 目标与交付 | 只产 `today_brief`（封面 + 展示行），**明令禁止创建正式待办**，写入的是展示记忆 / artifact | `backend/skills/today_plan/SKILL.md:6,27,67` |
| 2 | 动态决策 | **不满足**：Host 锁定 task_type（路由注释 `Locks the scope's plan task_type … Never from-text`），执行体是一次 `runWorker` 调用，输出被动词白名单与逐条覆盖校验约束 | `backend/src/routers/home-today.ts:43-44`、`backend/src/host/today-plan-run.ts:212-219` |
| 3 | 认知底座 | **部分满足**：只读本人正式任务 / 记忆 / 发现批次；三个技能 `mcp: []`，SKILL.md 明写「不直接使用 MCP 或知识库」 | 三个 SKILL.md frontmatter |
| 4 | 受治理动作 | **不满足**：`side_effects: none`、`external_writes: denied`、无 policy；只有「禁止」清单，没有写回现实的动作 | 发布包 + SKILL.md |

**结论**：它是 **Host 编排的受限工作流**（预定义代码路径 + 单次模型调用 + 严格 schema + 无工具 + 无副作用），符合 Anthropic 对 Workflow 的定义，**不符合本页 §1.1 的智能体定义**。它在 `agent:*` 命名空间里的实际作用有三：**技能运行绑定**（技能的 `runtime_agent_id` 指向它）、**成本归属**（`cost_events.agent_id`）、**发布门**。

**它不是调度系统**：本项目的调度是 Host 的入口路由与技能匹配（ADR-2026-09-23「Host 管路由、pack 装配、闸门与持久化」）；它不下发任务、不派单、不创建待办，自己反而是**被调度的一次作业**。

**说明**：它服务的是「个人层面的当下工作」，不是李开复所说的「老板 AI / 一号位决策 AI」。一号位决策类能力若要立项，属新的目标域与新的责任边界，须先按 §2.2 与 CONST-09 走基本法修订，不得以已有 Agent 冒名。

**登记缺口**：它的 3 个技能全部落在 BUSINESS 覆盖表「未登记入口口径」的 8 个技能之内（见 §九 #5），因此员工端技能目录对它显示「待业务专家补齐」；这是口径缺口，不是运行缺口。

## 五、清单 B：岗位身份 / 数字员工（3 个）

员工端 `/agents` 的文案是「数字员工」；机器可读发布资产是 `experts/<id>/manifest.yaml`。PROD-PLAT-02 明确：**数字员工是岗位身份，Agent 是能力组合，技能是可复用动作，任务是工作目标；不得互相替代**；[domain-objects.md](../domain-objects.md) 据此定义 DigitalEmployee 与 Agent（Agent 是面向一个业务目标的可发布能力组合，不拥有独立运行时）。

| id | 岗位 | kind | 入口契约（primary_entry） | 入口技能 | 技能包 | 边界（发布包原文要点） |
|---|---|---|---|---|---|---|
| `expert:kol` | KOL推广 | business | `think`（进入思考会话） | `stage_sop` | 9 个 | 「不发信、不改正式阶段」 |
| `expert:crawler` | 爬虫工程师 | collector | `job_console`（任务控制台，不建会话） | `creator_discovery` | 1 个（+ 工具 `mediacrawler`） | 「只形成候选人，由员工确认后才导入；不导入正式库、不发信、不创建合作承诺」 |
| `expert:approver` | 审批员 | governance | `approval_queue`（审批队列，不建会话） | `business_approval` | 1 个 | 「模型不得扩大授权、代人审批或把建议当作决定」 |

**三点观察：**

1. **岗位的真正区别是「入口 + 责任」，不是模型能力**——三者共用同一份内核与 harness；三个 `primary_entry` 值恰好把「模型思考」「异步作业」「人决定」分开，与 PROD-AGENT-01 的四类路径一一对应。召唤岗位只建绑定会话，不发信、不写阶段（`POST /api/experts/:id/summon`）。
2. **两个岗位没有思考会话**：`job_console` 与 `approval_queue` 类的召唤会被拒绝（409），因为这两类工作的入口是作业控制台与审批队列，而不是聊天。这本身是 CONST-07「两类入口」在岗位层的实现。采集作业的闸门（`policies/discovery_crawl.yaml`：`side_effect=true`、`requires_confirmation=true`、`tenant_concurrency=1`、禁止境内平台）也挂在采集路径上，而不是挂在任何 Agent 发布包里——**异步作业的边界归岗位与入口，不归运行体**。
3. **岗位身份不等于授权来源**：`expert:approver` 只是「处理审批队列」的岗位身份，审批权来自审批链与授权，不来自岗位本身；`expert:*` 也不构成任何授权单位（授权单位是技能）。

## 六、清单 C：责任角色（CONST-04，9 个）

宪法 CONST-04 明确：下列角色「**可以由人或专家 Agent 承担**；同一人兼任时仍需标明以哪个角色作决定」。

| 角色 | 有权决定 | 边界 |
|---|---|---|
| 平台产品经理 | 员工端、管理端、系统设置端的通用功能与产品验收要求 | 不定义 KOL 归属、期限、业务授权或业务事实来源 |
| UI/UX 专家 | 平台布局、导航交互、视觉规范、组件呈现与无障碍 | 不修改业务规则；不替模型固定每次回答内容 |
| 智能体产品经理 | 员工与 Agent 的交互、回答组织原则、记忆管理与入口契约 | 不定义 KOL 业务语义、审批权和事实真伪 |
| KOL 业务专家 | 业务对象、关系、动作、SOP、规则、报表、业务权限、审批及权威数据源 | 不指定后端并发或事件一致性的实现方案 |
| 架构师 | 前后端组件选型、模块边界、系统调用关系与接口分工 | 不决定业务权威数据源；不接管后端并发与一致性方案 |
| 前端专家 | 前端代码、组件实现、交互状态和前端技术细节 | 不在页面重写业务权限、审批和阶段判定 |
| 后端专家 | Host、app-server 接入、MCP、API、记忆存储、并发、事务与事件一致性 | 实现已定义规则，不自行发明业务口径 |
| 项目经理 | 任务分发、里程碑、依赖、关键节点和交付跟踪 | 协调决策，不替其他角色改规则 |
| 测试经理 | 测试策略、Agent 评价、回归范围和验收证据 | 验证规则，不用测试案例创造业务规则 |

**与岗位专家的区别（两者都容易被称为「专家」）：**

- **责任角色决定规则**（可以立法、可以裁定空白），**岗位专家执行任务**（只做事、不立法）。
- 当前 9 个责任角色**全部由人承担**：宪法允许委派给「专家 Agent」，但今天没有任何一个 `expert:*` 承担 CONST-04 的立法职责——`expert:approver` 是执行审批的岗位，不是 CONST-04 的决策角色。
- 因此「智能体数量」若按「能立法的智能体」计，现值是 **0**。
